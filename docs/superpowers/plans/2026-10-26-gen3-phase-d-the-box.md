# Gen 3 phase D: the box — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Gen 3 box runs the 3.0 stack headless as an appliance: provisioned by one script and checked by one verify, the engine and the server under a service user of their own, the PIN pepper in the box's secret store, systemd supervising with the guard's lifecycle rules, logs kept on the box, a health command, deploys with the previous build kept, and our own PTP follower replacing dantesync after a measured comparison.

**Architecture:** camera-box's working pattern, not an image: the stock Ubuntu 26.04 the box already runs, plus `scripts/gen3/provision.sh` (idempotent, write and enable only) and `scripts/gen3/verify_box.py` (read-only acceptance). The engine hosts the device as in phase C; the device's clock becomes a choice, `dantesync` (phases B–C) or `ptp`: a receive-only PTPv1 follower thread inside the same process that keeps PTP time as its own model of `CLOCK_MONOTONIC_RAW`, never steering the kernel clock. systemd stays the supervisor; failures that keep a unit down raise an alarm unit. Deploys go into one of two slots, so the build before stays on the box.

**Tech Stack:** Rust (workspace toolchain 1.98.1); `iem-dante` (GPL-3.0-or-later; parts adapted from dantesync, MIT, at `aa2d045`) with no new crate (libc, mio, socket2 are in already); `iem-server`'s pepper; systemd (units, `LoadCredentialEncrypted=`, `systemd-creds`, `OnFailure=`, `RestartMode=direct`), journald, systemd-timesyncd, sudoers; bash for provision and deploy, Python for verify, the guard and the drivers; GitHub artifact attestations.

**Spec:** `docs/superpowers/specs/2026-10-24-gen3-linux-dante-design.md` (§3 constraints, §4 camera-box and dantesync, §5.1 shape, §5.2 timing, §5.4 phase D, §5.5 clock, events, names, §5.6 testing). Ticket #72. Phase C: `docs/superpowers/plans/2026-10-26-gen3-phase-c-engine-on-linux.md`, `.claude/rules/gen3.md`. Supervision: `.claude/rules/guard.md`; secrets: `.claude/rules/security-baseline.md`; live: `.claude/rules/live.md`, `.claude/rules/soak.md`.

## Choices made in this plan

1. **The appliance shape: provision and verify on the stock OS, no image of our own** *(my call, from camera-box's actual practice)*. camera-box's fleet runs on `create-usb-linux.sh` (a debootstrapped Ubuntu with SSH and DHCP only) plus `setup-device.sh` (the sole provisioning path: it writes files and `enable`s, never starts anything live) and `verify-device.sh` (lettered read-only checks); its ro-root squashfs `build-image.sh` is a "long-term target" the fleet never moved onto (#301 there). The box already runs a clean Ubuntu 26.04 debootstrapped onto its SSD (#72, 2026-10-25). So here: **from scratch** = a minimal Ubuntu 26.04 with OpenSSH and the admin user holding the dev box's key (the 2026-10-25 way, or the stock server installer), then `provision.sh`, then `deploy.sh --pins`; no installer script of ours in phase D, because one could only be exercised by wiping the box from the stick at the box itself, and code that is never run is not shipped. **Upgrade** = `deploy.sh` for the stack, a `provision.sh` re-run for the box's configuration, OS packages by hand in dev time (the kernel is held and unattended upgrades are off, camera-box #295: an appliance never gains a kernel by itself; phase F changes the kernel deliberately). **Rolled back** = only the previous stack build, kept in the other slot (choice 6); no OS rollback (the owner's no-rollback rule). Taken from camera-box: the provision/verify pair, write-and-enable-only, kernel hold, no unattended upgrades, journald only (rsyslog purged, #762 there), byte-verified deploys of CI artifacts. **Not taken in phase D:** the read-only root (camera-box needs it for USB sticks that die and rigs switched off at the wall; the box has a SATA SSD, every state write of ours is a temporary file and a rename, and a ro root turns every deploy into a remount window, camera-box #1405/#1407; revisit in phase G with the rack's power practice), off-box log shipping (choice 4), a NIC/IRQ/CPU plan (phase F). **At boot in phase D:** the OS, sshd, journald and the box's one time owner (timesyncd with our follower, or dantesync); nothing of the stack. The engine, the server and the standalone device stay disabled until phase G (design §5.5: "ide event" takes the experimental device off the network, and a boot during an event must not put it back).
2. **Our own PTP follower replaces dantesync, proven against it on this box** *(design §5.2/§5.5, made concrete)*. **What it is:** a thread `dante-ptp` inside the process that hosts the device (the engine, or the standalone device), `SCHED_FIFO` 50 (dantesync's priority, above our TX/RX at 45 and the pump at 40). It binds UDP 319 and 320 on 224.0.1.129 **without `SO_REUSEADDR`** (so it cannot start beside dantesync, which binds them with it, and dantesync cannot start beside it: one PTP owner per box, design §3), joins the group on the Dante interface, reads kernel software receive stamps (`SO_TIMESTAMPNS`, dantesync's level, design §5.2), pairs each Sync with its Follow_Up from an allowed grandmaster (the device config's allowlist, the role of dantesync's `gm_allowlist`), and sends nothing: no Delay_Req, Announce or Sync (never a grandmaster, design §5.5; like dantesync it measures no path delay, so PTP time trails by the one-way delay as today). **The clock model:** PTP ns = ptp0 + (raw − raw0)·(1 + rate), raw = `CLOCK_MONOTONIC_RAW`, which no NTP slew moves; the wall clock is left to systemd-timesyncd against the fleet's NTP master, so nothing fights NTP (design §2 anti-goal). `sleep_until` converts back to a `CLOCK_MONOTONIC` deadline (the raw clock cannot be slept on; NTP's slew bounds the error at 500 ppm of one wait, at most 0.17 µs for a pump block). **The servo** (pure, adapted from dantesync): each second the window's least error over its pairs (queueing and interrupts only ever delay a receive stamp, so the minimum is the cleanest sample); a window off its recent median by more than 6 MADs and 20 µs is rejected (dantesync's spike filter, MAD-based), three rejected in a row are accepted (a real change); a PI on that error adjusting only the rate (dantesync's `ptp_phase_lock` form, its integrator the learned rate; the first rate from a line fit over the first four windows, dantesync's `freq_step::fit_line`); every update re-bases the model at its own instant, so the clock never steps; an error above 1 ms for 3 windows, or another grandmaster's time base, re-anchors (the epoch counts it and the media threads re-align, as phase B's tracker); no allowed pair is holdover on the learned rate, and past 120 s the clock is lost (not ready: nothing sent) until it re-acquires; 10 s of silence re-joins the group, then 30, 60, 120, 300 s apart (dantesync#112). **Proof:** sequential on this box, under the same load, judged by the packets: every Dante audio packet carries its sender's PTP-locked media time, so the least lateness of a second (our now minus the packet's stamp, in ns) of a flow from the IEM card's spare HIL TX measures our clock against the grandmaster's with no tool of either side in between. Live 1 runs 30 minutes on dantesync's clock, Live 2 the same 30 minutes on ours. Side by side on one box is out (design §3: "dantesync and our own Dante clock never run side by side on the same box"), and no second box of ours is on that network. **What keeps dantesync:** ours fails Live 2 when it re-anchors, holds over more often than dantesync's time server failed us, or its wander (p99 − p1 of that least lateness) exceeds dantesync's by more than one sample (10 417 ns at 96 kHz), or its slope exceeds 5 ns/s. Then `provision.sh --clock dantesync` and `source = "dantesync"` put the box back as it was, the numbers go on #72 and the follower's live gate moves to phase F. **Recommendation:** build it now, as the design says. The evidence is not decisive for keeping dantesync: its under-load problems (4 time-server replies past our 200 ms bound in 10 minutes, holdovers of 1–3 s; NANO → LOCK with spike rejections rising from 15 to 40 in about a quarter hour; #72, 2026-10-26) come from the IPC hop and from its kernel-frequency steering, which our in-process, non-steering follower does not have, and audio was never affected either way. The 18 s without grandmaster packets during a Dante Controller restart would reach ours too: the 120 s holdover and the re-join cover it. Until Live 2 passes, `source = "dantesync"` stays the default and the dantesync path stays in the code.
3. **Supervision: systemd carrying the guard's lifecycle rules** *(design §5.1's call, made concrete)*. The guard's engine exits (`guard.md`): 0 stays down; 2 and 3 stay down with an alarm (`RestartPreventExitStatus=2 3`, phase C); any other restarts with a backoff of 1, 2, 4, 8, then 10 s (`RestartSec=1`, `RestartSteps=4`, `RestartMaxDelaySec=10`) and three in ten minutes is a crash loop that stays down with an alarm (`StartLimitIntervalSec=600`, `StartLimitBurst=3`). **Alarms:** every unit of the stack has `OnFailure=iem-alarm@%n.service` with `RestartMode=direct`, so the alarm unit runs only when a unit stays down (`start-limit-hit`, exit 2 or 3, a stop that passed its bound), never per restart; it writes one journal line (`iem-alarm`) and calls `iem-server notify --to alarm`, the guard's own path to the engineer's devices. **I8:** `SendSIGKILL=no` and `TimeoutStopSec=10` on every unit, the alarm unit too; a stop past the bound leaves the process running, the unit fails and that is an alarm. **Event signals:** unchanged from phase C: "ide event" runs `systemctl stop iem-server iem-engine iem-dante` on the box from the dev box, and nothing starts the stack at boot. **Not carried in phase D:** the prod pin and the on-box lifecycle ("a reboot in prod goes live on the pin"): the box is not prod before phase G; the slots of choice 6 are the deploy side's previous/current. The guard's exit 75 (state folder busy) is no special case under systemd, which never runs two engines of one unit; a 75 counts toward the crash loop.
4. **Logs and health** *(my call)*. **Logs:** journald persistent on the SSD (`Storage=persistent`, `SystemMaxUse=1G`, `MaxRetentionSec=30day`), rsyslog purged; every unit's output is the journal; the previous boot's journal survives a reboot (`journalctl -b -1`). No off-box shipping: camera-box ships to its venue's editing box because its sticks die mid-run; here the only other host is the dev box, which is never a runtime dependency (owner: runtime self-contained). **Health:** a command, not a port: `iem-dante-dev health` on the box (in the bundle, versioned with it) prints one numbers-and-fixed-words JSON line and exits 0 healthy, 1 degraded or failed, 3 stopped. It reads the three units' systemd states, the device's control socket twice a second apart (clock, pump, flows), and the server's `/api/version` on loopback (its build against its own). The dev box reads it over ssh; deploy reads it back after a start; the server, its routes and the engine protocol stay unchanged (G3). **The owner** reads alarms on the phone once the box serves HTTPS (Web Push needs a secure context; the box serves plain HTTP since phase C choice 4): a #72 checklist item for phase E/G. Until then the alarm's `notify` reports 0 devices, and the agent reads `journalctl -t iem-alarm` and `health` and reports on #72.
5. **A service user and the box's secret store** *(the phase C plan's decision 4 risk, resolved; my call)*. A system user and group `iemmixer` (no login, no home) runs the engine, the server, the standalone device and the alarm unit (`User=` in the units: not site data, so no drop-in any more); the admin user is in its group, which opens the device's control socket (0660 in a 0750 runtime folder) to `ctl status`, the live guard and health; everything else of the service user's (site folder, secrets, state) stays its own. **The pepper:** a systemd credential, the Linux counterpart of the PC's DPAPI: 32 random bytes made on the box straight into `systemd-creds encrypt --name=pepper --with-key=auto` (sealed with the TPM2 when the board has one, else the root-only host key), stored root-only as `/etc/credstore.encrypted/iemmixer-pepper`, never written in clear; systemd decrypts it into the server's private credentials folder at each start (`LoadCredentialEncrypted=`), and the PIN commands get it the same way through `systemd-run`. The server reads `$CREDENTIALS_DIRECTORY/pepper` when systemd provides one and never falls back to the plain test file there. `jwt_secret` and `vapid_private` stay owner-only files of the service user, as on the PC, where only the pepper is DPAPI. **Band data:** phase D still runs the public synthetic band; after Live 4 the box may hold band data (phase E's decision).
6. **Deploy: two slots, attested, from one commit** *(my call, inside the owner's no-rollback rule)*. Each bundle goes into `/opt/iemmixer/slot-a/bin` or `slot-b/bin` (the four binaries, `BUILD`, `SHA256SUMS`), the one the running build is not in, while the stack keeps running; then stop, one atomic switch of the `/opt/iemmixer/bin` link, start. The build before stays untouched in the other slot: `deploy.sh --back --sha <it>` switches back after checking its `BUILD` and sums. Nothing is ever deleted (phase C's real `bin` folder is moved aside once). CI attests the bundle's `SHA256SUMS` by digest (as the PC's zip), deploy verifies the attestation before anything leaves the dev box, and deploy refuses a checkout that is not exactly `--sha` with a clean tree, so units, configs, the test site and the binaries always come from one commit.
7. **Tests and live acceptance.** CI: the PTPv1 codec, pairing and the servo against a seeded simulation (a crystal off by tens of ppm, one-sided delay noise, load bursts, an 18 s silence, a grandmaster change, a 25 ppm step, two simulated hours); the follower thread against a stand-in grandmaster on loopback; the clock reads under `assert_no_alloc` and rtsan; the pepper's credential rules; health's verdict; the units' contents; deploy, provision and verify against stand-ins, every `sudo -n` line any tool sends checked against the one template provision turns into the sudoers file. Live: Live 1 provisions and runs the baseline on dantesync (30 min), Live 2 our follower (30 min, the pass rule of choice 2), Live 3 restart, the event's stop, a crash loop, an exit 3, the way back and a graceful reboot, Live 4 two hours (an event's length; no longer soak, owner) and the browser loop through the IEM card.

## Global Constraints

- **P6** (program spec): "Site data never enters the public repo: names, hosts, Dante channel numbers and real track names, PINs, keys." Here: the grandmaster allowlist lives only in `iemmixer-ops/site/gen3-device.toml` (`[clock] grandmasters`), the fleet's NTP master only in `iemmixer-ops/site/gen3-dantesync.json`; the box's address and admin user, `GEN3_UI_URL`, and the test PINs only in the private env (no sudo password anywhere: the admin keeps passwordless sudo on this test box until phase G, see Task 9); the service user's name `iemmixer` and the credential's path are not site data. Tests use `10.0.0.x` and invented words.
- **Dante rule** (CLAUDE.md, #72 2026-10-24): "Never change Dante subscriptions or any Dante device other than the IEM PC's own card. One exception: for a Gen 3 test, the card's spare HIL return inputs may subscribe to our own 3.0 device's test TX, never on a band member's channel, and the subscription is removed after the test." Our RX subscriptions are ours (design §5.6).
- **Clock** (design §3, §5.5): one PTP owner per box, dantesync or our follower, chosen by the device config and `provision.sh --clock`, never both running; the follower opens UDP 319/320 to receive only (this replaces phase C's "our device never opens UDP 319/320"); nothing under `crates/iem-dante/src/clock/ptp/` sends; our device can never be a grandmaster; the wall clock is NTP's (timesyncd) or dantesync's, never the follower's.
- **I7** (program spec): "RT contract: lock-free rings, atomics and fixed messages only; ≤ 512 commands per block; no allocation, lock, syscall or log; CI checks with `assert_no_alloc` and rtsan." It covers `FollowerClock::now_ns` (read by the pump, TX and RX threads) beside phase C's paths.
- **I8** (program spec): "Nothing is force-killed." Every unit has `SendSIGKILL=no`; no script here ends a process by force.
- **Owner's event signals** (CLAUDE.md): the only gate; never ask whether an event runs. Every script here refuses while `EVENT-NOW` exists; "ide event" stops the stack; nothing of the stack starts at boot. The box's reboots in Live 3 are dev-time work of this plan (graceful, `systemctl reboot`).
- **Tier 0:** no local cargo compilation. Each task ends with a push to `dev` and a green CI run (test, clippy, coverage floor, `mutants-list`) before the next builds on it. Deploys use the `gen3-bundle-<sha>` artifact, attested.
- **Licence** (design §3): "the engine binary is already GPL through `iem-limiter-mga` (D1a). Dante protocol code may live in a GPL crate the engine links … Server, UI and guard stay separate permissive processes." Code adapted from dantesync (MIT) keeps its MIT notice and names `dantesync` at `aa2d045` in its file header.
- **Self-contained runtime** (owner): nothing on the box depends on the dev box at runtime; the dev box only provisions, deploys and tests.
- **Logs** name counts, ports, opcodes, channel numbers and peer ids, never a name, an address or a MAC; the control socket's status and health are numbers and fixed words only.
- **No long soaks** (owner, 2026-10-10): runs are sized to an event, at most 2 h.
- **Versions:** `[workspace.package].version` on `dev` stays above `main` (dev `2.0.0-dev.44`, main `2.0.0-dev.43` at `a357d05`); after any merge, bump first.

## Review Focus

1. **The clock never steps or runs backward, and a moving network never re-anchors it.** Load bursts, a whole second of packets delayed, an 18 s silence and a crystal 100 ppm off keep it within 20 µs without a re-anchor; only a lasting 1 ms change or another grandmaster's time base re-anchors, once. Tests: Task 1 (servo simulation, `the_clock_never_steps`), Task 2 (stand-in grandmaster).
2. **One owner, receive only.** The follower refuses to start while anything holds UDP 319/320 (exit 2, an alarm, never a restart loop), and its code has no send. Tests: Task 2 (`binding_a_held_port_is_addr_in_use`, `the_follower_never_sends`), Task 3 (`a_held_ptp_port_is_a_setup_refusal_naming_no_address`).
3. **The pepper never falls back silently.** With systemd's credentials folder present, a missing, short or long credential and a plain test pepper beside it are errors before any port is bound; nothing is written. Tests: Task 4.
4. **Down means down, with exactly one alarm.** A crash loop, exit 2 or 3 and a stop past its bound each run the alarm unit once and leave the unit down; a clean stop or a restart runs none; nothing of the stack is enabled after provision or deploy. Tests: Task 5 (unit contents), Task 9 (verify's `boot`), Live 3.
5. **No mixed builds.** A slot's sums hold before the link moves; `--back` refuses a slot that is not `--sha`; the checkout is `--sha` and clean; an unattested bundle never leaves the dev box; a flag mid-deploy stops all three. Tests: Task 7.

## Risks

- **Software timestamps under our flows' load:** the box's NICs have no hardware clock; the same receive path made dantesync reject more spikes. The window's minimum and the MAD guard are built for that, and Live 2 measures it against dantesync under the same load; a NIC with a PHC is phase F's.
- **A grandmaster frequency step** (a Dante leader election): the simulation allows one re-anchor (a re-alignment of our flows). If Live runs show it, a frequency-step detector (dantesync's `freq_step`) is the follow-up, recorded on #72.
- **OnFailure with `RestartMode=direct`:** the units rely on systemd running the alarm only when a unit stays down; Live 3 Steps 3–4 read it. If a crash loop's `start-limit-hit` raises no alarm, the fix goes into Task 5's units before phase D closes.
- **A TPM-sealed pepper** dies with the board or a cleared TPM: every PIN is given again (`deploy --pins`; with band data, the engineer's reset). verify records which key sealed it.
- **The wall clock without dantesync** is timesyncd's; an unreachable NTP master leaves it free-running (logs, token expiry), never the audio.
