# E2E (Playwright, mock — no audio hardware)

- Specs import `test`/`expect` from `./support/fixtures`: an auto fixture fails any test whose browser console shows an error, a warning or a page error. A test that deliberately provokes a failed request declares exactly that message with `test.use({ allowedConsole: [/…/] })` in its own `describe`, with a comment saying why. Never a global allowance; where the message is an app bug, fix the app. Two or more patterns need the fixture-tuple form `test.use({ allowedConsole: [[/a/, /b/], { scope: "test" }] })`: Playwright reads a bare `[/a/, /b/]` as `[value, options]` and passes only `/a/` (the guard throws on a non-array).
- **Environment allowances:** the engineer page subscribes to Web Push, and Playwright's contexts are incognito, where Chrome has no Push API (it logs "does not support the Push API in incognito mode" and the page warns `[push] …`), so engineer-page describes declare both in the tuple form with that comment; a spec that provokes a refused WebSocket upgrade declares Chrome's exact "WebSocket connection to '…' failed" line. Nothing else.
- PINs come from `E2E_ENGINEER_PIN` / `E2E_MEMBER_PIN` via `./support/pins` (CI generates them per run and provisions them with `iem-server pin …`). No credential is committed.
- The e2e job runs the real engine on NullRt (`iem-engine run --site … --sine 1000`: a −20 dBFS sine on every input, so meters move and the band-activity banner comes up on engineer pages after ~5 s) and the server on its socket (`IEMMIXER_ENGINE_PIPE`), both with `config/test-site.toml`; `engine.log` and `server.log` are uploaded on failure. cloudflared is absent (the tunnel is Down, so members see the tunnel banner).
- **Engine state is shared by the whole run:** each spec changes only its own member's mix (mixer: member3, pins: member5, EQ/limiter: member4, presets/history: member6, engineer suites: the engineer's mix) and restores what it toggled. Helpers: `support/session.ts` (`openMixer`, `strip`, `tab`, `dragFader`, `menu`).
- Login budgets are shared by the whole run: tests that fail logins act as tunnel clients from their own `203.0.113.N` (`CF-Connecting-IP` from a loopback peer is trusted) and keep the total under 30 failures per origin.
- **UI login attempts wait for their response:** `const r = page.waitForResponse(…/api/auth POST…)` before typing, `(await r).status()` after, and the PIN dots cleared before the next attempt — asserting on a still-visible "Invalid PIN" races the request.
- **Service worker (`crates/iem-ui/sw.js`):** `HASH_RE` is Trunk's shape — `iem-ui-<hash>.js` and `iem-ui-<hash>_bg.wasm`, the hash an *unpadded* hex u64 (≤ 16 digits; 15 in about one build of 16). A `{16,}` pattern passes most builds and fails the PWA spec only when the build's hash is short; `pwa.spec.ts` checks the pattern against real build names.
- Live specs (real PC, audio) come back in S6/S7 through HIL in the private ops repo — never in public CI.
- **PINs are frozen on the E2E site** (`pin_changes = false` in `config/test-site.toml`, like every dev site before the cutover, P9): a PIN change or reset in the UI gets 409 with the Slovak reason (`pin-freeze.spec.ts`, which declares Chrome's `status of 409` line). A spec that needs a real PIN change must run against its own site, never unfreeze the shared one. PIN provisioning (`iem-server pin …`) is the CLI and stays open.
- **Alarm link:** the e2e job runs `iem-server alarm-link --ttl-h 1` after the PINs and exports `E2E_ALARM_LINK` (token masked); `alarm-link.spec.ts` takes it once (the whole run has one link), grants `notifications` and stubs `PushManager.prototype.subscribe` with `addInitScript`, then reads `alarm_subscriptions.json` next to `IEMMIXER_CONFIG` for the backend effect; its iPhone case sets an iOS `userAgent` and expects the Home Screen hint and no button.
- **Phone project:** `playwright.config.ts` runs `mobile.spec.ts` only in the `phone` project (iPhone SE 3rd gen geometry, 375 × 667, `isMobile` + `hasTouch` so `pointer: coarse` matches, `browserName: "chromium"` — the job installs no WebKit); the `chromium` project ignores it — a project-level `testIgnore` replaces the top-level one, so it repeats `**/live/**`.
- **Mixer-page specs share member3** (`header`, `layout`, `mobile` read-only; `layout` unmutes what it mutes); `mixer.spec.ts` uses member7 for the second IEM VOL persistence check and returns it to 0 dB (a fader double-click animates to the 0 dB default). A second tab of the same member (`secondTab` in `mixer.spec.ts`) checks its own console on `close`.
- **Dropping the mixer socket:** `page.routeWebSocket` before `openMixer`, `connectToServer()` while the "server" is up, close the route to drop it, close new attempts at once while it is down (close code 1000: the page-side mock forwards it to a native socket, which refuses 1001). After a drop the page retries at its next 2 s tick, then 8 s later, and gives up after `MAX_WS_FAILURES` (3) closes in a row until a State arrives, so let it back in before that second retry (`header.spec.ts`). Giving up is an inherited defect, not a contract: a page whose token is still valid stays on "Reconnecting..." until it is reloaded (`connection.rs` reconnect closure; `ws_fail_count` resets only on a State).
- **Fader values after a coarse move:** a drag step that crosses an integer dB shows the first integer it crosses, not where the finger landed, and a step down from an exact integer shows no change at all (`crossed_integer`). The value shown at release is the one the engine gets, so after a coarse last step the fader ends off the finger (an inherited lag, not a contract; a fast back-and-forth ending at 0.6 of the track ends near +12 dB). Assert a range or compare with the value read at release, never a computed target.
