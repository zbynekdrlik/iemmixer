# E2E (Playwright, mock — no audio hardware)

- Specs import `test`/`expect` from `./support/fixtures`: an auto fixture fails any test whose browser console shows an error, a warning or a page error. A test that deliberately provokes a failed request declares exactly that message with `test.use({ allowedConsole: [/…/] })` in its own `describe`, with a comment saying why. Never a global allowance; where the message is an app bug, fix the app. Two or more patterns need the fixture-tuple form `test.use({ allowedConsole: [[/a/, /b/], { scope: "test" }] })`: Playwright reads a bare `[/a/, /b/]` as `[value, options]` and passes only `/a/` (the guard throws on a non-array).
- **Environment allowances:** the engineer page subscribes to Web Push, and Playwright's contexts are incognito, where Chrome has no Push API (it logs "does not support the Push API in incognito mode" and the page warns `[push] …`), so engineer-page describes declare both in the tuple form with that comment; a spec that provokes a refused WebSocket upgrade declares Chrome's exact "WebSocket connection to '…' failed" line. Nothing else.
- PINs come from `E2E_ENGINEER_PIN` / `E2E_MEMBER_PIN` via `./support/pins` (CI generates them per run and provisions them with `iem-server pin …`). No credential is committed.
- The e2e job runs the real engine on NullRt (`iem-engine run --site … --sine 1000`: a −20 dBFS sine on every input, so meters move; no banner or notice reads them, #38: `engineer.spec.ts` checks that a loud stage shows none) and the server on its socket (`IEMMIXER_ENGINE_PIPE`), both with `config/test-site.toml`; `engine.log` and `server.log` are uploaded on failure. cloudflared is absent (the tunnel is Down, so members see the tunnel banner).
- **Engine state is shared by the whole run:** each spec changes only its own member's mix (mixer: member3, pins: member5, EQ/limiter: member4, presets/history: member6, engineer suites: the engineer's mix) and restores what it toggled. Helpers: `support/session.ts` (`openMixer`, `strip`, `tab`, `dragFader`, `menu`).
- **History (F14) on member6:** the modal fetches its list when it opens, so a `count()` right after the title shows can read 0 while the fetch is in flight (run 36371298924 read 0 of 2). Count from `GET /api/snapshots/member6`, `toHaveCount` that before acting, take a saved entry's id from the save's response (`saveNow` in `presets-history.spec.ts`) and delete it in a `finally`: the preset tests share member6's history.
- **The run starts from the engine's defaults:** no saved state, so every output (each mix's IEM VOL) is muted (`StateLost`) and input levels are off (−60). A test that needs a value sets it from a `MixerSocket` (`support/mixer-socket.ts`: `state()`, `send`, `applied()`) before it opens the page and restores what `state()` showed in a `finally` (mixer.spec.ts IEM VOL mute).
- **Main shows one own channel:** a member's first owned input (`view::channels`: member4 → mic4); other owned inputs (mic5) are on their category tab — `tab(page, "Mics")` before `strip(page, "mic5")`.
- **The limiter counter lags the limiter (X14):** it counts while the GR meter is below −1 dB, and that meter climbs back by a factor of e a second (~8.7 dB/s), so after a drive of ~20 dB it counts ~2.5 s more. Before a Reset that must stay at zero, poll `limiterActiveSeconds()` until two reads 500 ms apart agree.
- **Node sockets are `NodeWebSocket`:** never import `ws` as `WebSocket`. Playwright's transpiler rewrites every reference to an import, also inside a function handed to `page.evaluate`, which then throws "_ws is not defined" in the page; page-side code uses the browser's `WebSocket`.
- **App download failure (`app-load.spec.ts`):** the loader in `crates/iem-ui/Trunk.toml` (`pattern_script`) catches a failed bindings/WASM download and the shell shows `load-error` with Try Again. The spec aborts `iem-ui-<hash>_bg.wasm` with `serviceWorkers: "block"` (so the route sees the page's request, not the worker's) and declares Chrome's `ERR_CONNECTION_FAILED` line and Playwright's "Service Worker registration blocked by Playwright" warning.
- **Runner-side sockets (`support/wire.ts`):** a refused upgrade is checked from Node with `upgradeStatus` (the `ws` package sees 401/403; a page only sees "failed", and nothing reaches its console); `PageSocket` watches a page (Meters, TunnelStatus) or sets its mix, and `applied()` waits until every command sent before it is in the engine (the server runs a socket's commands in order, each until applied). The engine's listen taps are silent until a level lets the sine through: `soundInput` raises one input (and, for a member's tap, which is after the mix's mute, the mix output) and returns the undo. Owners: listen/diagnostics use hand2 in the engineer's mix and member8's mix; SOS additions member7 (alerts only); tunnel pages member9 (looked at only); talkback turns eng_mic's trim off (input-wide, restored) so its meter shows the talkback without the card's sine.
- **Launch options are worker options:** `test.use({ launchOptions })` only at the top of a spec file (in a describe Playwright refuses it). `talkback.spec.ts` feeds Chromium's fake microphone a 1 kHz WAV it writes to the temp dir; `tunnel.spec.ts` maps the public host `mixer.example.org` onto the CI server (`--host-resolver-rules`) for the LAN hint, and for Ok serves cloudflared's `/ready` on `127.0.0.1:20241` (the default `tunnel_ready_url`), waits up to 45 s for the server's 30 s poll, and waits after its last test until the tunnel reads Down again.
- Login budgets are shared by the whole run: tests that fail logins act as tunnel clients from their own `203.0.113.N` (`CF-Connecting-IP` from a loopback peer is trusted) and keep the total under 30 failures per origin.
- **UI login attempts wait for their response:** `const r = page.waitForResponse(…/api/auth POST…)` before typing, `(await r).status()` after, and the PIN dots cleared before the next attempt — asserting on a still-visible "Invalid PIN" races the request.
- **Service worker (`crates/iem-ui/sw.js`):** `HASH_RE` is Trunk's shape — `iem-ui-<hash>.js` and `iem-ui-<hash>_bg.wasm`, the hash an *unpadded* hex u64 (≤ 16 digits; 15 in about one build of 16). A `{16,}` pattern passes most builds and fails the PWA spec only when the build's hash is short; `pwa.spec.ts` checks the pattern against real build names.
- **The soak step (S7, #10), after Playwright:** the job runs `iem-soakclient` against the same engine and server (`--direct`, member9's mix, the engineer PIN through `IEM_SOAK_PIN`) for 600 s on a push and 120 s on a pull request, then `soak_verdict.py harness` checks its summary: complete, at most 3 gaps, no reconnect, ≥ 99 % of the expected listen frames, a meter frame. The client reads only (no mixer command, only `ListenStart`/`ListenStop`) and runs after every spec, so it shares no moment with one. The member listen tap is one slot: a spec that left another member's Listen running past its end would make the client's `ListenStart` answer `no_source` (no frames, red). Details: `.claude/rules/soak.md`.
- Live specs (real PC, audio) come back in S6/S7 through HIL in the private ops repo — never in public CI.
- **PINs are frozen on the E2E site** (`pin_changes = false` in `config/test-site.toml`, like every dev site before the cutover, P9): a PIN change or reset in the UI gets 409 with the Slovak reason (`pin-freeze.spec.ts`, which declares Chrome's `status of 409` line). A spec that needs a real PIN change must run against its own site, never unfreeze the shared one. PIN provisioning (`iem-server pin …`) is the CLI and stays open.
- **Phone project:** `playwright.config.ts` runs `mobile.spec.ts` only in the `phone` project (iPhone SE 3rd gen geometry, 375 × 667, `isMobile` + `hasTouch` so `pointer: coarse` matches, `browserName: "chromium"` — the job installs no WebKit); the `chromium` project ignores it — a project-level `testIgnore` replaces the top-level one, so it repeats `**/live/**`.
- **Mixer-page specs share member3** (`header`, `layout`, `mobile` read-only, except that `layout` unmutes what it mutes and `header`'s reconnect test toggles mic3's mute from a second socket and puts it back in a `finally`); `mixer.spec.ts` uses member7 for the second IEM VOL persistence check and returns it to 0 dB (a fader double-click animates to the 0 dB default). A second tab of the same member (`secondTab` in `mixer.spec.ts`) checks its own console on `close`.
- **Dropping the mixer socket:** `page.routeWebSocket` before `openMixer`, `connectToServer()` while the "server" is up, close the route to drop it, close new attempts at once while it is down (close code 1000: the page-side mock forwards it to a native socket, which refuses 1001). After a drop the page retries at its next 2 s tick, then 8 s, 15 s and every 30 s later (`lifecycle::backoff_delay_ms`), and never gives up while its token holds: after `MAX_WS_FAILURES` (3) failed sockets in a row each retry also GETs `/api/mixer/<page>` (a refused token goes to the login), and the count resets when a socket opens (`helpers::reconnect_step`). A route that closes an attempt inside its handler never opens it, so it counts as a failure. `header.spec.ts` keeps the socket out for four failures (the drop and three retries, the third being the first token check, which must not end the retrying) and lets the fourth retry in (~55 s after the drop, `test.setTimeout(120_000)`). It answers the token checks 502 with `page.route` on `/api/mixer/member3` while the server is gone, as cloudflared answers a tunnel page during a restart (no verdict on the token: only 401/403 send a page to the login, `api::token_refused`; the describe declares Chrome's `status of 502` line), and awaits the one after the reconnect with `page.waitForResponse` (200) before it asserts that the page is still `/member3`: an assertion right after the banner hides would pass before a redirect.
- **A socket held connecting:** a `routeWebSocket` handler that neither connects nor returns keeps the page's socket CONNECTING (Playwright's page-side mock opens when the handler returns); `ws.onClose` set in the handler sees the page's close (and stops Playwright forwarding it). `navigation.spec.ts` leaves a mixer page while a reconnect is held: the page's cleanup closes an open socket at once and a connecting one when it opens, because closing a native socket that is still connecting makes Chrome log "WebSocket is closed before the connection is established" (the mock cannot show that line, so the test checks when the close comes).
- **Fader values after a coarse move:** a drag step that crosses an integer dB shows the first integer it crosses, not where the finger landed, and a step down from an exact integer shows no change at all (`crossed_integer`). The value shown at release is the one the engine gets, so after a coarse last step the fader ends off the finger (an inherited lag, not a contract; a fast back-and-forth ending at 0.6 of the track ends near +12 dB). Assert a range or compare with the value read at release, never a computed target.
