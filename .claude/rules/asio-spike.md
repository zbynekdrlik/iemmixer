# ASIO host and the S1a spike (#3)

- `asio.rs` and `os.rs` are the crate's only unsafe code (`deny(unsafe_code)` at the root, `allow` on the two modules). Every driver call stays on the thread that created `Host` (`!Send`, COM STA; that thread pumps messages). A stream is freed only after `STREAM` is cleared and `IN_FLIGHT` is 0.
- **The S6 backend `AsioStream<P>`** sits beside the unchanged spike `Host`/`Running` (the example must keep compiling). One owner thread makes every driver call and pumps messages; the callback reaches the stream through its own `BACKEND` slot and `BACKEND_IN_FLIGHT` (`BUSY` is shared: one stream per process). Each open: I3 module holders (first open only, never after our own) → the preference window's `enter` (`Owner::pref`, one `prefwin::Window` for the stream's life: the first open writes 32, a reopen only reads it back) → open, info, `ChannelMap`, `admit`, `createBuffers` → `start` → the period from the first 32 sample positions (`owner::open_period`: 8 agreeing deltas anywhere decide Ok at once; another period or none refuses only once the ring is full or 1 s passed, so the verdict never depends on when the owner thread looks, and two warm-up misses still decide). A reopen carries the processor and its buffers (same pages, so `VirtualLock` holds) and sets the discontinuity flag. `RELEASED` is true while no backend host exists (the SEH filter waits ≤ 1 s for it); a callback stuck past `STOP_WAIT` parks the stream (never freed; its counters stay in `stats`). **The parked-engine test's hold** (#35, design §10 test #2; `.claude/rules/guard.md`): `raise_test_park` sets `SEH_HOLD` (never cleared) BEFORE the SEH test's exception, and the tick and `stats` load `SEH` first, so whoever sees the exception sees the hold. The tick's answer is `owner::seh_release(seh, hold, done)` (`Nothing` / `Release` = the fault and `release_for_good`, as before / `Hold`); `Hold` runs `Owner::hold_card`: the stream stopped like `finish` stops it (logged before and after `stop()`, so a driver that hung there shows in the log), then neither disposed nor released (the card forgotten, so `RELEASED` stays clear and the filter parks), the owner done (parked) like after a stuck callback, the preference window held. `owner::seh_faults(seh, hold)` keeps the held exception out of `faulted`, so the engine keeps running and reports `parked` until it ends (a `Shutdown` stops the stream as `Parked`, and the engine says `DriverParked`). Raised during a reopen, the old card's release may set `RELEASED` before the new open clears it, and the filter ends the process as without the hold. A `WM_ENDSESSION` dispatched from a pump inside an open or a finish cannot borrow the owner: it sets `release_pending`, and the owner stops that open (`AsioError::SessionEnd`) and releases for good right after. **The preference holds 32 while the card is held** (#9 2026-09-28: the first run on the PC faulted on its reopen budget ~110 ms after the open while `leave` wrote 64 back right after `createBuffers`; most likely the driver asks for a reset when the value changes while it is open): the window's `leave` runs only where the card is released and no open follows — `finish(.., Then::Release)` (a stop, a fault's release, the session end, the SEH release, a failed open's `start_stream`), `release_for_good` without a live stream, a failed first open (a failed `leave` joins the refusal as `PrefLeave`) and a failed reopen; `finish(.., Then::Reopen)` keeps it. `Owner::release_card` drops the host, then leaves, then drops the `ReleaseMark`: no open driver of ours sees the write, and `RELEASED` (which lets the SEH filter end the process) comes after REAPER's value is back. A parked stream keeps 32. A window still held when the owner thread unwinds is closed by `Drop` (a failed close in `pref_failure` and `start`'s refusal). Never write the preference while the driver is open. **Logging stays out of the callback:** `backend_message`/`backend_rate_change` may run on any thread (azo hands our `Callbacks` to the driver as they are), so they only count in the static `messages::Messages` (atomics, also without a stream; times on the owner's `BASE` clock, a `OnceLock`); the owner thread logs `MESSAGES.since(&mut seen)` every tick, after each open and at the release, plus each open (number, ms, measured period), each preference enter/leave, and each reopen with `owner::Asked` (reset request vs buffer size change from `Telemetry::take_requests`, rate, forced, stall) and `reset::BudgetState`; the over-budget fault text carries both. Its decisions live in `owner.rs`, `messages.rs`, `reset.rs`, `telemetry.rs` and `prefwin.rs` (portable, mutated); nothing in `asio.rs` is mutation-tested.
- The host never calls `set_sample_rate`, `set_clock_source` or `open_control_panel` (integrity scan, I2) and streams only at 96 kHz and the driver's preferred buffer (`format::admit`). Outputs are zeroed before `start()` and on every callback (A1).
- Decisions live in `format.rs`, `telemetry.rs`, `cpuset.rs`, `glitch_report.rs` (the report's glitch cap, the ns→QPC conversion, the trace-marker text `latency_report.py` parses: `iemmixer-glitch kind=<k> at_qpc=<n> emit_qpc=<n> freq=<n> value=<n>`) and `spike_run.rs` (every outcome's exit code, 5 unused since #38, the `--stress`/`--audio-cpus` rule, what a placement applied, the setup levers that fail a run, the hwlat gate and end) — portable, tested, mutated. The example still holds decisions of its own: the argument parser's rules, `Watch::poll` and `End::outcome` (their tests run on every OS, but the example is mutation-excluded); besides those it keeps the threads, the channel, the Windows calls and the JSON. The loops stay in the example, but their conditions are library calls (`keeps_busy`, `scan_ends`), so a `keeps_busy -> true` or `scan_ends -> false` mutant DOES hang the example tests `stress_threads_stop_when_dropped` and `hwlat_scans_only_on_its_cpu_at_time_critical`: such a mutant is killed within seconds by `spike_run.rs`'s own unit tests, and the nextest `mutants` profile (fail-fast with `terminate = "immediate"`, `slow-timeout` 2 × 5 s) ends the hung example tests. `asio.rs`, `os.rs` and the example are excluded from mutation. `asio.rs` and `os.rs` build only on Windows (`windows`, `asio-spike` jobs); the example builds on every OS (`[[example]] test = true`: `cargo test` runs its parser and harness tests, `examples/asio_spike/tests.rs`, on Linux too) and only its run path (`mod spike`) is Windows-only. So a new spike decision goes into a mutated module, or at least into a portable function of the example with a test, never only into `mod spike`. Avoid `>`/`>=` on values where both branches agree (equivalent mutants); pack disjoint bit-fields with `+`, not `|` (a `|`→`^` mutant is then equivalent and unkillable). Tier 0 means clippy first fires in CI, not locally: a descending `sort_by(|a, b| b.k.cmp(&a.k))` trips `-D clippy::unnecessary_sort_by` — write `sort_by_key(|x| Reverse(x.k))`. When implementing a frozen plan, re-check its anchors against the CURRENT tree (a later commit may have moved a struct field or added `Cargo.toml` features — "windows-sys gains features" means ADD, never REPLACE, or you drop the SEH-filter set `asio.rs` needs).
- **A measurement that would lie fails the run** (#32): a lever the report names but the spike could not apply ends the run with a non-zero exit and the error in the report, never a JSON note beside outcome `done`: the audio CPU Set (`refused`, 4), power throttling left on (`error`, 1, every mode before the card opens), a stress thread's CPU Set and the hwlat scanner's CPU or TIME_CRITICAL (`error`, 1). `process.stress_cpus` is what was applied (`null`, `{lps, ids}`, `{lps, error}`); the top-level `stress_cpus` echoes the request. `--stress` with `--audio-cpus` needs `--stress-cpus` (else the busy threads inherit the audio CPUs as process default), and `--stress-cpus` never overlaps `--audio-cpus`, with or without threads (the window driver refuses the same). Telemetry: `on_thread` runs before `on_callback` of the same callback and names the callback thread only after `WARMUP` (priming may run on the thread that called `start()`); a position step back is `position-back`, not a `position-gap` of the same magnitude; `GlitchLog` packs the kind in 3 bits (at most 8 kinds); each trace marker reads its own emit QPC.
- The driver's preferred buffer changes only through `spike_window.py set-buffer` and is restored with read-back before REAPER starts (whenever a write was recorded, even to the original value); `Invoke-SpikeBringBack` reads it again and refuses unless it is the original, or while `asio_spike` or its task runs. REAPER keeps its own value (owner, #3).
- **The preempt's first PC action (#15, the last lane):** `stop_first` writes the stop file and counts the spike in plain PowerShell (`plain_ps`/`plain_script`: no module, no stage, no bundle record), in place of the staged spike check and with its bound (60 s, `ignore`), so a stage that fails after it never leaves a spike on the card; the asio-spike job runs it on 5.1 (`tuning_window.py preempt-script`). A window with REAPER on the card gets the file too, and its closing unwind removes it.
- A spike may be starting when "ide event" comes: unwind always writes the stop file while the card is free, `Stop-SpikeGracefully` waits for the spike and its task, `Invoke-SpikeRun` and the spike itself refuse on an existing stop file. **Who removes `queue\stop` (F2 round 3, m1):** never a start — the run start's body, like every PC-changing body, begins with `step_guard` and refuses while the file exists (a start's `Remove-Item` over a slow ssh once undid a preempt's file). Only the unwind that CLOSES the window removes it, after the bring-back and the settle (`close_out` → `clear_stop`, kept while the spike or its task runs), and post-boot's close. An unwind that does not close (a spike not confirmed gone, a failed bring-back, reboot-prepare) keeps it, and so do the deadline stops (cmd_run's, `Invoke-SpikeRun`'s): until a closing unwind every changing step refuses ("the spike's stop file exists on the PC, but no flag here"), and `to-event` in an event-state window removes it. A new window's `preflight` also removes a stale one: no spike runs (its check), so a stop file then is what an earlier window left without a closing unwind (a process that died, a deadline stop); `clear_stop` under the lock, never while the "ide event" flag exists (the event path owns it), recorded as `preflight.stop_file`, a failed removal fails the preflight.
- A window opened after REAPER was already saved and quit uses `new --dev-time`: the card is `free` from the start (so `preempt`/`to-event` bring REAPER back), `preflight` then requires REAPER gone and no module holder, and `set-buffer`/`run` refuse before a passed preflight. To stay in dev time at the end, `set-buffer --frames <original>` (read back) and leave the window open; the next "ide event" pre-empts it.
- **No input level ends a run (#38, owner decision 2026-10-06: only the owner's signal is a gate).** Other devices on the Dante network feed the card's inputs, so a level says nothing about the band. The band guard (−50 dBFS, 3 s over `--activity-channels`), its `band-activity` outcome (exit 5, now unused), `telemetry::Watched`/`ActivityGuard`, `PC_ACTIVITY_CHANNELS` and a request's `activity_channels` are gone: `--activity-channels` is an unknown flag. `Watch` stops a run on the stop file or a rate change only, and once a second it reads every input's peak for the report: reports and progress files list `loudest_input_dbfs` and the five loudest inputs (`loudest_inputs`: channel from 1, index from 0, dBFS), as information. `to-dev` reads no meters before the save and quit. Real channel numbers never enter this repo (tests use the synthetic 101–124).
- **Reject-case tests must not be shadowed.** A negative test that one flag is refused supplies every mandatory input (`--frames` for `duplex`/`reopen`, `--cpu` for `hwlat`) — otherwise the case is rejected on the missing one first and passes for the wrong reason. Every bad case is otherwise VALID, failing only on the one flag under test.
- PC windows only in dev time. `~/.config/iemmixer/EVENT-NOW` = an event is on (created on "ide event", removed on "event skončil"); every wait of `spike_window.py` sees it within 2 s and pre-empts. Nothing is killed; a spike that does not stop is an owner alarm.
- Only the `asio-spike-<sha>` artifact of a green `dev` push reaches the PC (`fetch-bundle`; `SHA256SUMS` checked on the dev box and on the PC).
- `SpikePc.psm1` imports `GoldenPc.psm1` from its own folder (the bundle layout); run `Test-SpikePc.ps1` on Windows PowerShell 5.1 (CI `asio-spike`) after any PowerShell change.
- **The stage rule (#15, the review lane's findings of 2026-10-07).** The window sessions run elevated over ssh, and `PC_ROOT\bin` lies in the user's root, which any process of the user may change: no session imports a module from it. `sw.ps_script` reads SpikePc and GoldenPc (SpikePc loads it from its own folder) from `bin` once, checks each against `$iemSums` (`elevated_ps.sums_table`, from `bundle_sums`: the state's `bundle_sha` — `setup` records it before its PC call, every `new` keeps the last window's — and that bundle's fetched record under `RAW_DIR`, the green dev push's CI artifact with its `SHA256SUMS` checked at fetch — not attested, unlike the iemmixer zip; it must name the four modules; without one, or unreadable, every PC call refuses with `setup --sha` or `fetch-bundle`), stages it in `<elevated root>\bootstrap-stage` (`elevated_ps.staged`: written only when the stage does not already hold exactly those bytes admin-only, so sessions at the same time — a run's poll and a preempt — never rewrite under another's import and a loosened copy repairs itself; read back admin-only and checked again; an existing root or stage is only read back, never its DACL written again) and imports only the stage copy. `measure_import` stages IemTuning then IemMeasure after TEMP; the stop-only import stages IemMeasure alone (no TEMP, no IemTuning; a few file reads well inside the stop's bound). `golden_window.ps_script` stages GoldenPc checked against the file `setup` uploads (this box's copy). The CI scripts take the bundle's `SHA256SUMS` (`poll-script`/`analysis-script --sums`), and the analysis step checks that all four modules were imported from the stage. Never add an `Import-Module` of a path under `PC_ROOT` to a window body. Every composed script pins `PSModulePath` to Windows PowerShell's own folders before its first command (`elevated_ps.PIN`, on the try's line after the two preference assignments; raw setup calls start with it), and ssh starts `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe` (`elevated_ps.REMOTE`): iempc, the window sessions and golden alike. A program the session runs is staged too: `wpt-install` hands `Install-IemWpt` the stage copy of `adksetup.exe`.
- Site values (driver name, registry key, task names, handover values) only in `~/.config/iemmixer/asio-spike.env` and the ops runbook `docs/s1a-pc-runbook.md`.
- The S1c PC **tuning** window tools — `scripts/pc-tuning/` (`tuning_window.py`, `latency_report.py`, `IemTuning.psm1`, `IemMeasure.psm1`) and the `spike_window.py` unwind/`BUNDLE_FILES` extensions — and their gotchas (load-bearing import order, `BUNDLE_FILES` ↔ fixture/`verify_bundle` sync, StrictMode 5.1 array idiom, the graceful reboot / I8, `reboot-prepare` clean-stop gate, `cmd_undo` fail-loud) are in `.claude/rules/pc-tuning.md` (auto-loads on `scripts/pc-tuning/**` and `scripts/asio-spike/**`).
