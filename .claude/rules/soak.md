# Soak harness and verdict (S7, #10)

Design note `docs/superpowers/specs/2026-10-07-s7-hil-live-soak-design.md` §4 and §9, plan `docs/superpowers/plans/2026-10-07-s7-telemetry-soak.md` Tasks 5–10.

- **The client (`iem-soakclient`) reads only.** It signs in once as the engineer (its own token on the PC, the PIN login in CI: below), then opens one mixer socket (`/ws/<member>?token=…&proto=2`) and one listen socket (`/ws/audio`) on one member's mix, and counts. The only frames it sends are the listen socket's `ListenStart` and, at the end, `ListenStop`, then each socket's WebSocket Close: never a mixer command. Nothing in it ends a process. Without `--direct` it reads `/api/site`'s `lan_url` at `--base` and goes there. That URL must be `http://`: the client speaks no TLS, and LAN 443 serves an expired certificate (`not-http`). With `--direct` everything goes to `--base` itself (CI: the test site's `lan_url` is a placeholder).
- **The build check (#10 decision, 2026-10-07).** `--expect-build <40 lower-case hex>` is required. Before the PIN, a token or anything else is sent, the client reads `GET /api/version` at the origin it will use (the LAN URL, or `--base` with `--direct`; `net::check_build`) and goes on only when `names_build` holds: the answer's `git_hash` (the server's `git rev-parse --short HEAD` at build time, `iem_core::git_hash`) is at least `MIN_HASH` (7) characters and a prefix of the expected commit, as HIL v1's `Test-IemHilVersion` checks the server. Any other answer (another build, the predecessor app, which names its own commit, no version route, another shape) is `wrong-server`; no answer is `server-gone`. The login (CI) and both sockets then go only to that origin. The ops soak job passes the soaked SHA (its Task 10 draft needs the flag); CI's e2e step passes `git rev-parse HEAD`, the commit its server was built from, and is the one run of the check against the real server's `VersionInfo`.
- **No socket is opened twice (#10 decision, 2026-10-07).** Each socket is opened once (`net::hold`). One that cannot be opened ends the run at once (`server-gone`): a second try could reach whatever answers at that address by then. Its first close (the peer's Close too), an error on it, or a silence of `idle` ends the run (`connection-lost`, stderr and summary). A reconnect was red in the verdict anyway (check 11), so nothing of value is lost. There is no backoff and no give-up bound: the bound only measured how long a socket was tried again.
- **Each socket ends with its Close** (`Role::finish`, at the run's end and on the lost path as far as the socket still can): the listen socket's `ListenStop`, then a WebSocket Close (or the answer to the peer's), then reads (not counted) until the peer's Close, at most `close_wait` (2 s) plus one read's wait, then the drop. Once the peer's Close has come nothing is left unread, so on Windows the drop is a FIN and not a reset: a socket dropped with Opus frames still unread resets the connection, and the peer can lose the frames before it, the `ListenStop` (da22a8f's `windows` job: `the_sockets_go_to_the_lan_url_the_server_names` saw no `ListenStop`). The final summary is written once both sockets have ended.
- **The credential: exactly one of two (#10 decision, 2026-10-07: no band PIN in GitHub).** `credential` takes the flag or the variable; both (`IEM_SOAK_PIN` set at all, even empty, beside the flag) or neither is a usage error (exit 2) naming the two, never a value, before any request.
  - **PC: `--jwt-secret-file <path>`**, the server's `secrets/jwt_secret`. `read_secret` reads it as the server's `secrets.rs` does: UTF-8 text, trimmed (`Secret::from_text`); the trimmed text's bytes are the HS256 key, never base64-decoded. It is read first, before `/api/site`: missing, unreadable, not UTF-8 or blank ends the run `secret-unreadable` with nothing sent. It never creates the file (the server's first start does). After the build check `engineer_token` signs `{sub: "engineer", engineer: true, iat: now, exp: now + --seconds + TOKEN_MARGIN}` (600 s) with `jsonwebtoken` (the server's 11.1 and `rust_crypto` backend; `Header::default()`, HS256), as `iem_server::auth::issue_token` does; no `/api/auth`. The server reads a token only when a socket opens (`mixer_ws::claims_of`), so the margin covers the build check, the opens and the closes. `Credential` and `Secret` print no value (`{:?}` is `SecretFile(..)`, `Pin(..)`, `Secret(..)`); no error carries the path or the text.
  - **CI: `IEM_SOAK_PIN`**, the server's login (`POST /api/auth`) against the e2e job's own test server, as before.
  - **Trust.** Nothing new can read the secret: the soak runs as the user that already can (the ops runner's user, the server's); the token never leaves the PC (its sockets go to the PC's own LAN address). The predecessor app shares the secret (`iem-migrate band` copies it), so it would take a token signed here: the build check (`--expect-build`, before any token is sent) and the no-reconnect rule guard it as before. **Ops change still owed before the first PC soak (#10):** the ops `soak.yml` must pass `--jwt-secret-file` and remove its `IEM_SOAK_PIN` line entirely, not only the secret behind it: a variable set at all, even empty (a deleted GitHub secret), beside the flag is both credentials, exit 2. Then a band PIN change no longer touches the soak.
  - **One reading of the token.** The tests read a minted token back into `iem_core::AuthClaims` with the body of `iem_server::auth::extract_claims` (`DecodingKey::from_secret`, `Validation::default()`, which checks `exp`), not through `iem-server` itself (it embeds the UI's `dist` and would bring axum, tokio, reqwest and argon2 into the client's tests). A change to the server's tokens (algorithm, claims, key encoding, validation) changes `engineer_token` and that test with it. The fake server takes a token only when it verifies with its script's secret (`tests/fake_server/main.rs`, `upgrade` and `claims`; the tests are in `token.rs`): a token from another secret opens no socket (`server-gone`). The real server reads a client-signed token in CI's e2e step (its second run, below).
- **`iem-soakclient token` (S7 plan Task 23; #10 decision of 2026-10-08: no band PIN in GitHub for the live run either).** The ops `live.yml` job `pc-begin` mints the run's engineer token and one member token on the PC; nothing logs in, so the live run has no login budget to spend. `iem-soakclient token --jwt-secret-file <path> --sub <id> [--engineer] --seconds <n> --out <file>` (`mint.rs`; `main.rs` dispatches the subcommand before the soak's own arguments):
  - **The token**: `mint::token(secret, sub, engineer, now, seconds)`, `{sub, engineer, iat: now, exp: now + seconds}`, HS256 with the secret's bytes and `Header::default()`, as `issue_token`. It is the one signing path: `engineer_token` calls it with `seconds + TOKEN_MARGIN`. The tests read both kinds back with `extract_claims`'s body (`mint::tests`, `as_server` from `src/tests.rs`).
  - **The arguments** (`mint::parse_args`): `--engineer` exactly when `--sub engineer` (a member with it, or the engineer without it, is a usage error); `--sub` a member id as the site writes it (1 to 64 of `[A-Za-z0-9_-]`, `valid_member`), never checked against a site; `--seconds` 60 to 7200 (`MIN_TOKEN_SECONDS`, `MAX_TOKEN_SECONDS`), counted from the mint in `pc-begin`: the ops job asks for the run's length plus the hand-off to `browser` (the artifact upload and the job's start; e.g. 3600 + 600 s), which the soak's `engineer_token` covers with `TOKEN_MARGIN`; every flag once. A usage error names flags, never a value; `TokenArgs`'s `{:?}` shows only `engineer` and `seconds`.
  - **The token is never printed.** It goes only to `--out`: a NEW file (`create_new`: an existing file or a symlink is never written through or replaced, `token-unwritable`), owner-only (0600) on Unix; on Windows it inherits its folder's ACL, so the ops job writes it into a folder only its runner user may read (UNVERIFIED on the PC until that job's `icacls` check exists: a folder under `C:\` inherits `Users` read by default). A file that could not be written whole is removed. Stdout gets only `token-written`; stderr a usage message or a code. The secret is read first (`read_secret`, as for the soak): unreadable or blank is `secret-unreadable` and creates no file. The ops job writes each token into a fresh folder, hands it to `browser` in a private artifact of one-day retention, and `report` deletes it.
  - **Exit codes**: 0 the token in its file; 1 `secret-unreadable`, `token-unwritable` or `clock-unreadable` (a clock before 1970, `mint::unix_seconds`: never a token over since 1970) (`mint::MintError::code`, not a `Reason`: the soak's summary never holds them); 2 a usage error. Tests: `mint::tests` and `tests/fake_server/token.rs` (`the_token_subcommand_writes_the_token_to_its_file_and_prints_only_a_fixed_word`, which runs the binary).
  - **Trust: the same as `--jwt-secret-file`.** It runs as the user that already reads the secret (the ops runner's, the server's) and sends nothing anywhere. A minted token is a credential for its length: an engineer token reaches the engineer's console and Listen; the predecessor app shares the secret, so the live relay's build check before every open and its no-reconnect rule guard it as for the soak client. A member token is refused by the engineer-only routes.
  - **CI** (the `e2e` job's soak step, after the soak's two runs): mints an engineer and a `member9` token from the job's own server's secret into a `mktemp -d` folder, wants `token-written` alone on stdout and nothing on stderr, and reads `GET /api/audio/diagnostics` with each (curl takes the header from a file, so no token is on a command line): 200 for the engineer's, 403 for the member's (`routes.rs` `require_engineer`); the folder is removed on every exit (`trap … EXIT`).
- **The PIN, the secret and site values (P6).** The PIN comes only from `IEM_SOAK_PIN` (4 to 12 digits, read with `var_os`); `--pin` is refused. The secret only from the file `--jwt-secret-file` names. A usage error names flags, never a value, and `Args` is never printed (`{:?}` would show the member and the base). Stderr carries usage messages and reason codes; stdout carries the final summary as one JSON line. The summary holds numbers and fixed codes only: `error` is a `Reason` by type, so no error text, URL or host can reach it.
- **Reason codes** (`Reason::code`, the summary's `error`; the first one stays):
  - `site-unreadable`: `/api/site` could not be read or names no `lan_url`;
  - `not-http`: the `lan_url` is not plain `http://`;
  - `wrong-server`: `/api/version` at the origin answered without naming `--expect-build` (no login, no socket);
  - `login-refused`: any answered refusal (a status other than 200, an unreadable answer);
  - `not-engineer`: the login is not the engineer's (the listen socket is engineer-only);
  - `server-gone`: the build check or the login got no answer, or a socket could not be opened (a refused upgrade too; no second try);
  - `connection-lost`: an open socket closed, failed or stayed silent for `idle` before the end;
  - `cpu-sets`: the CPU Sets could not be set (no login; that summary is written);
  - `secret-unreadable`: the `--jwt-secret-file` is missing, unreadable, not UTF-8 or blank: nothing was sent, not even `/api/site`; that summary is written. Also a token that could not be signed with it, after the build check (not seen with HS256).
  - A new code goes into `soak_verdict.HARNESS_REASONS` in the same change: `test_the_harness_reason_codes_are_the_clients_own` reads `Reason::code`'s arms from `lib.rs` and wants the same set.
- **Bounds** (`net::Limits::default`, the consts of `net.rs`):
  - `write_every` 60 s: the summary is handed to the writer, and once more at the end.
  - `read_timeout` 500 ms: a reading thread sees the end of the run within it.
  - `idle` 10 s: a socket that sent nothing that long ends the run (`connection-lost`), so a half-open socket, or a server that stopped serving it, ends it too. The real server sends meters every 100 ms, and repeats `no_source` every 5 s only while a STARTED listen hears nothing (`listen_ws.rs`). A refused `ListenStart` (the member tap held by another mix) answers `no_source` once and the socket then stays silent, so the run ends `connection-lost` about 10 s after it, with one `no_source` and no frame.
  - `close_wait` 2 s: at its end a socket waits at most that long (and one read's wait) for the peer's Close.
  - Each HTTP request (`/api/site`, `/api/version`, the login) at most 10 s (`HTTP_WAIT`). Each socket's connect, handshake and write at most 5 s (`OPEN_WAIT`): `tungstenite::connect` has no bound, so the client connects with its own timeout and then calls `tungstenite::client`.
  - No thread polls: the clock sleeps on a condition variable.
  - `--seconds` is 1 to 36000 (`MAX_SECONDS`, the ops soak job's 600 min; the plan's `soak.yml` asks for `hours·3600 + 180` s, at most 9 h). The run's clock starts at the first open of either socket; the run is complete `--seconds` after it.
- **Exit codes** (`main.rs`):
  - 0: the whole run, with its final summary written;
  - 1: a run that ended early (its code on stderr), or whose final summary could not be written (`summary-unwritable` on stderr, even after a whole run: without the file the run is no evidence);
  - 2: a usage error (both credentials or neither too).
  - A failed write before the end never ends the run (a reader may hold the file on Windows); the next write tries again. `write_summary` writes `<out>.tmp`, syncs it and renames it over `<out>`, so a reader sees the last whole summary, never a part.
- **CPU Sets** (`--cpu-sets 256,257`, Windows only; elsewhere a usage error): `iem_win::power::set_cpu_sets` places the process on the S1c profile's housekeeping CPU Sets before the sign-in (P10), as the engine places itself. The `windows` job's clippy step is the first compile of that path; its test step runs the crate's tests, the fake-server ones included, on Windows sockets. `main.rs` (argv, env, CPU Set and file glue) is excluded from mutation as a whole file (`.cargo/mutants.toml`, as the guard's mains are): its `#[cfg(windows)]` call is not compiled on the Linux runners. Its exit codes are checked by `tests/fake_server/`, which runs the binary; its decisions stay mutated in `lib.rs`, `mint.rs`, `net.rs` and `tally.rs`.
- **Windows' socket after a receive timeout.** A read that waits out `read_timeout` returns `WouldBlock` on Unix and `TimedOut` on Windows. Both count as a wait, and the socket is read on (`net::waited`). Microsoft documents a socket whose receive timed out (`SO_RCVTIMEO`) as indeterminate: data can be lost when the timeout cancels a receive at the moment it completes. Not seen on the PC yet; the `windows` job's fake-server tests are the first runs on Windows sockets. On the PC such a loss would break the WebSocket stream; tungstenite then returns an error, and the run ends `connection-lost` (red). An unexplained `connection-lost` in a PC soak points here first.
- **Defender.** `Set-IemDefenderExclusion` gives every root `.exe` of the active bundle a Defender process exclusion by full path (`bundles\<sha>\`), so `iem-soakclient.exe` gets one too: the attested, summed copy that runs on the PC (P5).
- **"Ide event" during a PC soak: settled on #10 (2026-10-07, before any PC soak), both parts, defence in depth.** After "ide event" the predecessor app serves the band's usual address (P9), where the client's sockets go, and it accepts the token the client holds (`iem-migrate band` imports the predecessor's JWT secret); it answers a member's `ListenStart` by muting every other member's send to the engineer's REAPER mix until a `ListenStop` or a disconnect (`reaperiem`, the `/ws/audio` handler), and its `no_source` repeats keep that socket from going idle. So: (1) no socket is opened twice, and the switch's first close of either socket ends the run `connection-lost` (above); (2) the client starts only at a server that names `--expect-build` in `/api/version`, which the predecessor never does (`wrong-server`). The ops verdict maps the PC job's `left-dev` record to `cancelled` whatever `soakclient.json` holds. Whether the client outlives the runner after the guard's Ctrl-Break is UNVERIFIED (plan Task 10); with (1) a client left running ends at the switch's first close all the same.
- **Counting** (`tally.rs`, pure). A listen frame counts only when Opus decodes it to 960 samples per channel (the engine's `FRAME_48K`). Anything else is a decode error, and no frame for the gap clock. The server encodes every tap frame the engine sends, with no silence suppression, so a silent mix still streams frames.
- **The summary** (`Summary`, `SCHEMA` 1, rewritten every minute and at the end; struct-level `#[serde(default)]`):
  - `schema`, `build` (`GITHUB_SHA` at build time, else `local`), `complete`;
  - `seconds`: since the first open;
  - `frames`; `expected_frames`: one per 20 ms from the first frame to the end, that one included;
  - `decode_errors`;
  - `gaps`: a wait over 60 ms between two frames, or from the last frame to the end; a run without a frame is one gap as long as the run;
  - `max_gap_ms`: the longest wait without a frame, a gap or not;
  - `first_frame_ms`: `ListenStart` to the first frame;
  - `meter_frames`: `Meters` events on the mixer socket (`classify` reads the tag first, whatever the data's shape);
  - `reconnects`: always 0 since #10's decision (no socket is opened twice); kept so schema 1 and the verdict's check 11 stay as they are;
  - `no_source`: `AudioStatus` `no_source` answers;
  - `error`: the reason code, or null.
- **The verdict** (`soak_verdict.py`, pure, stdlib). `report` is the ops `soak.yml` report job's step. It reads the PC job's record directory: `result.json`; `polls.jsonl`, one `{"t", "exit", "status"}` per `iemmode status` poll; `soakclient.json`. It prints one JSON object (`conclusion`, `summary` posted as `soak/iem-pc`, `first_failure`, `numbers`). Every check runs, so the numbers stay complete; the first failure leads `red: <it>; <numbers>`. The 12 checks, in order (`test_red_names_the_first_failing_number_in_order`):
  1. polls exist; each has exit 0, mode dev, no switch and an engine (a line that is no JSON, cut short or a status `iemmode` could not answer, is an unreadable poll; blank lines are skipped);
  2. every engine runs the SHA, all under one engine pid;
  3. the poll times are finite and never go back, span the hours (8), and have no hole over 300 s;
  4. missed +0;
  5. resets +0 (4 and 5 count last poll minus first: counts before the first poll never count);
  6. both histograms in the first and the last poll, their top above 347 µs, no bucket gone back;
  7. late: intervals of 347 µs or more (the S1a p99.9 at B = 32) at most 2 ‰ of the soak's intervals;
  8. the callback's own time at p99.9 at most 83 µs: the upper edge of the bucket at rank ⌈0.999·n⌉, in integer math, at least 1 (`iem_audio_io::hist::quantile_us`'s rule);
  9. the harness is complete and ran the hours;
  10. no gap;
  11. no reconnect;
  12. at least 99 % of the expected listen frames, and at least one frame (gaps are measured between frames, so gaps 0 alone cannot tell a thinned stream from a full one).
  - Information only, never deciding: the 1.5-period `late` counter and `overruns` (last minus first), the last poll's `process_max_us`, and the `tuning drift:` alarms raised during the soak (each id once).
- **Shown values round toward red**: a value never reads as its bound. Polled hours round down at 0.01 h, a hole up at 0.1 s, the late share up at 0.001 %, the harness's seconds down at 0.1 s, the frames' share down at 0.01 %; the p99.9 is a bucket's upper edge. `report` prints strict JSON (`allow_nan=False`): a NaN raises there and never reaches the job.
- **The report mapping** (`report`; "ide event" never makes red):
  - `cancelled`: a cancelled PC job, a failed PC job that left no record (the guard may stop the runner mid-job), or a record whose reason is `left-dev`. `result.json` is read first, so a left-dev run stays cancelled whatever `soakclient.json` holds. An unreadable `result.json` of a cancelled PC job is cancelled too.
  - `failure`: a PC job that succeeded or was skipped and left no record, `red: pc job <result> left no record` (the job writes `result.json` first and uploads it `always()`, so a broken report lies behind it: the first 8 h soak's report read an empty folder, #10); any other PC failure, `red: pc job <result> (<reason>)`; an unreadable `result.json` otherwise.
  - Else the verdict. A harness file that holds no JSON is check 9's "the harness summary is unreadable".
- **Reason-code sets.** A code is printed only when known. `PC_REASONS` (`finished`, `left-dev`, `not-finished`, `bundle-not-active`, `no-client`, `harness-did-not-end`) are the ops `soak.yml` job's `result.json` reasons; `HARNESS_REASONS` are `Reason::code`'s. A new code in the ops job or in the client goes into `soak_verdict.py` in the same change, else the summary prints `unknown` or leaves it out.
- **CI's harness check** (`soak_verdict.py harness`, `_ci_check`; the `e2e` job's soak step, `.claude/rules/e2e.md`). It runs the checks 9 to 12 with CI's bounds (`--min-seconds N-1`, `--max-gaps 3`), then wants `meter_frames > 0`. CI's run against the real server is the one place that proves the client reads the server's `Meters`; the PC verdict does not judge meters (`test_the_ci_step_needs_a_meter_frame_the_pc_verdict_does_not`).
  - The step runs after Playwright: `--direct` at the job's server, `--member member9`, `--expect-build "$(git rev-parse HEAD)"` (the job's server reports `git rev-parse --short HEAD` of the same checkout), the engineer PIN from `E2E_ENGINEER_PIN` through `IEM_SOAK_PIN`, 600 s on a push and 120 s on a pull request. Then a second run of 30 s in the PC's mode: no `IEM_SOAK_PIN`, `--jwt-secret-file` the job's own server's (`secrets/jwt_secret` next to `$IEMMIXER_CONFIG`), its summary `soakclient-secret.json` checked by the same harness check (`--min-seconds 29`): the one place a real server reads a token the client signed before a PC soak does.
  - The verdict runs even when the client ended early, so the log names what failed. The step fails when a verdict or a client failed (a client's exit code counts only once its verdict passed; a failed first verdict ends the step before the second run). The step's own `timeout-minutes` (15) makes a hung client a failed step, not a cancelled job, so the summary is still uploaded on failure.
  - `--max-gaps 3` is the hosted runner's tolerance for scheduling stalls; the PC verdict wants 0. Record the measured gaps of the first ten push runs on #10, and lower the tolerance if they stay at 0.
- **Known effects while a soak runs.**
  - The soak's page socket on the member's mix keeps that mix's solo past the 10 s grace (`solo.rs`: `SoloJanitor` counts any page connection on the mix). Not changed.
  - The member listen tap is one slot (`listen_ws.rs`): while the client listens to its member's mix, an engineer's Listen to another member's mix answers `no_source`.
  - So the ops soak listens to a member not active in dev (`SOAK_MEMBER`), and CI's to member9 after Playwright.
- **Drift.** The design's 10-minute drift poll does not exist: `iemmode` has no tuning-state request. The guard's own check runs hourly (`DRIFT_EVERY`), and its `tuning drift: …` alarms ride on every poll; the verdict counts them as information.
- **`dispatch-soak`** (`iempc_soak.py`, plan Task 8, Review Focus 7; `iempc dispatch-soak --sha <bundle> [--hours N]`; iempc.py passes itself in as `ip` and keeps the call site only, #36). The soak changes no guard state, so the command only dispatches the ops `soak.yml` with this box's gh (`-f sha -f branch -f run -f hours`) for the bundle the PC already runs. Any refusal dispatches nothing. In order:
  1. Before any call: dev time (`Spec(dev_time=True)`: the EVENT-NOW flag at the start refuses), a full SHA, `--hours` 1 to 9 (default 8; `HOURS_MAX`: the ops job's 600 min hold 9 h of polls plus the client's start and end; the ops `verify` job wants `^[1-9]$` too), and no soak of that SHA in this dev entry yet. The record is `<state>/soak.json`, `{"soaks": [{sha, branch, run, hours, entry, at}]}`, the newest 200 kept; one of another shape is an error to check by hand, never read as none. The entry is the count of `iempc dev` and `iempc switch-test`'s dev leg (`current_entry`), with its known limit: a dev entry the guard makes by itself is not counted.
  2. `iemmode status` (a new flag abandons it and runs the event path, exit 10). `soak_refusal` (pure) wants `ok`, mode dev, no `switching`, no detail part starting with `HIL job` (an unknown shape of it refuses too), the detail's second part `bundle <SHA>` (`active_bundle`: `daemon::status_text` writes `mode <m>; bundle <sha>|no bundle; …`, so a later note never stands for the bundle), an engine object whose `build` is the SHA, and `parked` and `faulted` exactly `false`.
  3. `green_run` (P5): a successful push run of `ci.yml` for the SHA on dev or main, with its `bundle` and `attest` jobs. Its id and branch are what `soak.yml` gets; the ops `verify` job checks them again.
  4. The flag again, right before the dispatch: one that came during the gh waits refuses (exit 1). A failed step once a new flag exists runs the event path instead (`Spec(pc=True)`).
  5. `gh workflow run soak.yml`, then the record: a failed dispatch records nothing. A failed ops soak run of the same SHA and entry is repeated with `gh run rerun <id> -R <ops repo>` (the same verified inputs), never a second dispatch.
  - A soak of this dev entry that may still run (its hours plus `RUN_MARGIN_S`, an unreadable record counts) also refuses `dispatch-live`, `activate`, `dispatch-hil` and `trace` before any call (`iempc_live.refuse_overlap` and `refuse_while_running`, `.claude/rules/live.md`; one whose time, hours or dev entry cannot be read names `soak.json` to check by hand) and `switch-test` after its status read (`iempc_switch`); `iempc dev` and `iempc event` never wait for it.
  - Tests: `test_iempc_soak.py` on `iempc_test_support.Base` (`FakePc`, `FakeGh`). Every guard is tested on both sides; no Python mutation gate runs in CI, so a new guard needs its own refusal case.

## The 72 h NullRt soak: dropped (owner, 2026-10-10)

- An event lasts at most 2 h and the PC has no 72 h between events; the owner dropped the 72 h NullRt soak as waste. The tool (`scripts/soak/`), its tests and the CI artifact are removed. A 5.2 h run before the stop showed no memory growth and flat fds and threads (numbers on #10, 2026-10-10). The PC's 8 h soak above remains the long-run evidence.
