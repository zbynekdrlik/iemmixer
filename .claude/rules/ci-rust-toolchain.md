# CI Rust toolchain

- **Pinned toolchain** in `rust-toolchain.toml` (1.98.1 + rustfmt, clippy, llvm-tools-preview, wasm32). Every job runs `rustup toolchain install` first. Bump it in its own commit: a new stable can add clippy lints (e.g. `byte_char_slices`: write `*b"OIEM"`, not `[b'O', …]`) — read the lint name in `gh run view --log-failed` before editing code.
- **`--locked` everywhere:** cargo commands in CI use `--locked`; the UI builds with `trunk build --release --locked`; any `cargo install` in CI MUST be `--locked` (an unpinned trunk once pulled a broken CSS dependency with zero UI change). Tools come prebuilt from `taiki-e/install-action` at pinned versions.
- **`Swatinem/rust-cache` on every cargo job.** Linux jobs exclude `iem-tray` (Tauri); the `windows` job lints and tests it (DPAPI), the `bundle` job builds it with the other release binaries (`.claude/rules/guard.md`). A Windows `run:` step holds one cargo command: pwsh returns only the last native command's exit code.
- **Mutation gate:** `.cargo/mutants.toml` (profile `mutants`, nextest, excludes with reasons); PR-only, diff-scoped, each shard ≤ 20 min. Shards are 0-based (`--shard k/n`, `n = strategy.job-total`); the shard count is the length of the `shard:` matrix in `ci.yml`. The `mutation-warmup` job builds the `mutants` profile once and saves the dependency cache (`shared-key: mutation`) that every shard restores; shards run `--copy-target=true` after a no-op warm-up so each mutant rebuilds only workspace crates. `mutants-list` (every `dev` push) counts the next PR's diff-scoped mutants and fails when they need more shards than the matrix has at `MUTANTS_PER_SHARD` — resize the matrix before opening the PR. An overrun is a setup bug: add shards or narrow scope (fallback: `--in-place --jobs 1` with more shards), never raise the timeout. Both mutation steps set `NEXTEST_PROFILE=mutants` (`.config/nextest.toml`: fail fast and end running tests at the first failure, run the dedicated bounded tests first (`priority = 100`), and end any test after 10 s — `iem-server` 30 s, its suite takes up to 10 s under shard load — as failed, so a mutant that hangs every test is CAUGHT even when the hung tests starve the bounded ones of test threads) and pass `--timeout 60` (with `--baseline=skip` cargo-mutants otherwise allows 300 s per mutant). **A catch by a timeout is provisional (#23):** after the run `scripts/mutants_recheck.py` reads `mutants.out` (outcomes.json + each caught mutant's log); a mutant whose first failing test nextest ended (TIMEOUT, fail-fast's SIGTERM/SIGKILL) or whose log names no failing test is tested again, `--jobs 1`, with the `mutants-recheck` profile (60 s per test, cargo-mutants `--timeout 120`): caught again stays caught (a timeout there is a hang), a survivor fails the gate (exit 2), a recheck timeout exits 3; the sweep reports its survivors. The recheck selects by name (`--re ^<name>$`) AND by the mutants' files (`--file`): cargo-mutants 27.1.0 tests every struct-field deletion mutant whatever `--re`/`--exclude-re` say (upstream cargo-mutants#632, open), so a recheck of one mutant once tested 51 and another shard ran out of job time (#32, CI run 37466176804). A field deletion it tests anyway in a selected file is only noted; any other unselected mutant is still an error. Drop the file limit's tolerance once #632 is fixed upstream and the pin moves past it. Every caught mutant is printed with the test that caught it. `mutation-warmup` runs the unmutated suite once under the `mutants` profile: a test failing there would make every mutant of its package look caught, and its PASS lines are the per-test durations to set a package's bound from (≥ 3× its slowest time, below cargo-mutants' 60 s); a test that awaits a lock, semaphore or queue wraps it in `tokio::time::timeout` so a mutant that blocks fails fast (CAUGHT) instead of TIMEOUT. UI survivors: move pure logic into helpers with native tests; exclude only browser-only functions (web_sys, WebSocket/JS closures, Leptos component bodies) per function in `exclude_re`, with a reason. cargo-mutants 27.1 does not apply `exclude_re` to "delete field … from struct … expression" mutants — kill those with a test. It skips a module only under a plain `#[cfg(test)]`: `#[cfg(all(test, unix))]` gets mutated, so test-only modules split it into `#[cfg(test)] #[cfg(unix)]`. `cargo mutants --list --in-diff <diff>` parses without compiling: use it to count the next PR's mutants and to check an `exclude_re` before pushing. `crates/iem-core/build.rs` and `crates/iem-tray/build.rs` key their rerun on `GITHUB_SHA` when there is no `.git` (cargo-mutants' scratch copy), so `BUILD_TIME` does not force a full rebuild per mutant. The full sweep is `mutation-full.yml` (on demand).
- **Advisories: cargo-deny and osv-scanner** (`supply-chain` job). cargo-deny reads RustSec only; GitHub advisories that never reach RustSec (the 2026 openssl ones, jsonwebtoken's type confusion) are caught by `osv-scanner scan source --config osv-scanner.toml` over `Cargo.lock`, `fuzz/Cargo.lock` and `e2e/package-lock.json` (it also sees crates outside cargo-deny's target graph, e.g. Tauri's build-time plist/quick-xml). Every ignore carries its reason, in both `deny.toml` and `osv-scanner.toml` when both tools report it; an alias GHSA id is listed next to its RUSTSEC id. The osv-scanner release binary runs locally (no compilation): scan before pushing a lockfile change.
- **Lockfile updates (`cargo update -p`, local, no compilation).** Update the Tauri family as one release: `tauri` X.Y needs `tauri-runtime` X.Y (#9 2026-09-28: tauri 2.11.1 accepts tauri-runtime ^2.11.1, resolved 2.12.0 and did not compile in the `windows` job; only that job builds the tray). A `cargo update` may re-resolve range requirements of unrelated crates (`windows-sys = ">=0.52, <=0.61"` and the like) to older versions already in the lock: compare `git diff Cargo.lock`, keep those edges as they were (`cargo metadata --locked` must pass), and run `scripts/check_engine_deps.py` (the engine's closure changed through them once: `windows-targets`).
- **Every `uses:` is pinned to a full commit SHA** with a `# vX.Y.Z` comment; `scripts/check_integrity.py` fails otherwise. Pins and crates are updated by hand in their own commit on `dev` (no Dependabot version PRs: they would create `dependabot/*` branches).
- **Required checks** on `main` are regenerated from the job list and the matrix length whenever shards change (S0 plan, Task 15 Step 6); a skipped required job counts as passing, so every job a required job `needs` is itself required.
