# Gen 3: our own Dante device (#72; design `docs/superpowers/specs/2026-10-24-gen3-linux-dante-design.md`, plan `docs/superpowers/plans/2026-10-25-gen3-phase-a-dante-device.md`)

- **The crate.** `iem-dante` is GPL-3.0-or-later (parts adapted from teodly/inferno at `9767558`; each adapted file names its origin in its header) and never a dependency of `iem-engine` in phase A (`scripts/check_engine_deps.py` stays clean). Modules: `device` (the config and the persisted names, Dante's name rules), `wire` (the 10-byte request/response header), `arc` (UDP 4440, below; `arc::gaps` counts what it refuses or leaves unanswered), `cmc` (UDP 8800: the 0x1001 advertisement), `info` (UDP 8700: the info requests and the heartbeat, below), `announce` (the mDNS records and the `Announcer` behind a two-call `Registry`, so tests use a fake and never multicast), `daemon` (the binary's command line, `pick_interface`, `net_info` and the `serve` loop), `clock` (phase B: the media clock, PTP time read from the box's dantesync, below). Phase A sends no PTP and no audio: the device is a follower only and never a grandmaster (design §5.5).
- **ARC (`arc.rs`, inferno's `arc_server.rs` and `proto_arc.rs`).** Every opcode inferno's server answers is answered byte for byte as inferno answers it with no flows and no subscriptions, and nothing else: a request Dante Controller gets refused it asks again at once (live, #72 2026-10-26: 0x2200 and 0x2204 about 2 250 times a second while the device refused both with 0xffff; the service stayed stopped until fixed). Op1 → reply (status OK unless named):

  | op1 | reply |
  |---|---|
  | 0x1000 | counts (TX rename flag; 0 TX and 0 RX flows, inferno says 32) |
  | 0x1002, 0x1003 | the device name; the names (current, factory, board, `:705`) |
  | 0x1100, 0x1102 | 110, 94 zero bytes |
  | 0x2000, 0x2010 | TX channels (default names), TX names now; pages of 32, `0x8112` while more follow |
  | 0x2013, 0x3001 | TX rename (`00 00`), RX rename (no body); all or nothing, 0xffff if any item is invalid (inferno renames the valid ones) |
  | 0x2200, 0x3200 | TX, RX flows: `10 00` + 32 zero bytes (16 slots, none used) for any first flow |
  | 0x2201, 0x2202 | create, delete a multicast TX flow: 0xffff, no body (inferno without flows) |
  | 0x2320 | status 0x0030, no body (inferno's "???") |
  | 0x3000 | RX channels, pages of 16, no subscription |
  | 0x3010 | subscribe or unsubscribe: no body; phase A subscribes nothing, one info line with the channel numbers |
  | 0x3014 | netaudio's unsubscribe (`0001 0000 <ch>`): no body |
  | 0x3300 | `38 00 38 fd 38 fe 38 ff` |

  0xffff only where inferno answers it: a page request without its first item (bytes 2–3 of the body zero, or under 4 bytes; channel and flow lists), a rename that renames nothing, 0x2201, 0x2202. **No reply** (`ArcOutcome::Unanswered`, as inferno's catch-all and its reads that fail before answering): any other opcode (0x2204 — not in inferno at 9767558 nor in netaudio, Dante Controller's body `00 01 00 01` is a page request — 0x1001 netaudio's device rename, 0x1101 its latency), op2 not 0, 0x2201 under 2 bytes, 0x2202 under 4, 0x3010 under 2 or with `min(count, len / 6)` 6-byte items running past the end, 0x3014 under 6. A datagram shorter than the header is dropped (`Ignored`); one whose length field disagrees with its size is dropped and counted (`ArcOutcome::Misframed { op1 }`, its header's opcode; the review of PR #78: a sender we misread never showed). Tests: `arc/tests.rs` pins each reply; `every_opcode_inferno_answers_is_answered_as_inferno_answers_it` walks inferno's 18 opcodes (0xffff only for 0x2201/0x2202).
- **The gap guard (`arc/gaps.rs`).** `arc::serve` counts every refused (0xffff), unanswered or misframed request per peer (its IP address, named by an id only: 1 for the first peer seen, ids for the server's life, at most 64, then 0) and opcode, at most 256 entries a window (the rest summed), and logs one warning a minute: `ARC requests refused or not answered in a minute (peer id, opcode)` with `requests=<n>` and `counts=peer 1 0x2204 unanswered 134999, …` (16 entries, then sums; the gap is `refused`, `unanswered` or `misframed`). The window opens at its first request; the server looks every `GAP_CHECK` (1 s). A log, never a limiter: no answer depends on it. A live run with Dante Controller reads it in the journal; a steady count is a gap to close. A refused rename's reason (no such channel, no name at its offset, an invalid or clashing name) is a debug line only, never a warning per request (Dante Controller asks again at once: the review of PR #78; `a_refused_rename_is_counted_never_a_warning_of_its_own` captures the log).
- **Info and heartbeat (`info.rs`, inferno's `info_mcast_server.rs`).** Dante Controller finds the device over mDNS and CMC, then asks UDP **8700** for its board info and goes on to ARC only once that is answered (live, #72 2026-10-26). The server listens at the device's address only (as inferno: no group joined) and sends everything multicast, from that socket (Linux routes a multicast from a bound source address out of that address's interface): replies to **224.0.0.231:8702**, a heartbeat every second to **224.0.0.233:8708** (the first at once), and the board and product info unasked at start. Every packet has a 32-byte header (start code 0xffff info / 0xfffe heartbeat, length, the device's own sequence from 1 over every packet, process id 0, the CMC device id, `Audinate`, an 8-byte opcode). Answered (byte 1 of a request is any; for 0x21, 0x13 and 0x77 the last byte too): `07 xx 00 61` board info → `07 2a 00 60`, 200 bytes; `07 xx 00 c1` product info → `07 2a 00 c0`, 336 bytes (the config's manufacturer and model, the workspace version at 0x1c); `07 xx 00 13` network info → `07 2a 00 11`, 64 bytes (link speed, MAC, address, netmask, gateway twice); `07 xx 00 77` → `07 2a 00 78`, `00 00 00 03 00 00 00 00`. No clock in phase A: clock stats (`07 xx 00 21`) get no reply and the heartbeat is the header alone, as inferno before its clock has an offset (no 0x8001 frequency, 0x8002 peaks or 0x8003 RX latency records). Anything else gets no reply and an info line with its opcode, the way to see what Dante Controller asks next; shorter than 32 bytes is dropped; start code and length are not checked (inferno). **The bound (`info/limit.rs`, ours, not inferno's; the review of PR #78):** each reply goes to a group every Dante device on the band's network hears, so a 32-byte unicast request from any sender would put up to 368 bytes onto all of them: at most `limit::PER_SPAN` (10) replies of a kind (board, product, network info, 0x77: the reply, not the request's whole opcode, so a varied byte 1 or last byte meets one bound) go out in any second (a sliding window: the times of the kind's last ten), the rest are dropped before they take a sequence number (`Multicaster::answer_within`), counted, and logged once a minute from the first drop, looked at every `limit::CHECK` (1 s): `info replies over the bound dropped in a minute (at most 10 a second of each kind)` with `dropped=<n>`, `counts=0x61 board info 990, 0x13 network info 5, 0x77 1`. Requests without a reply are not bounded. Not adapted yet: inferno's channel-change notification on 8702 after an RX rename (`07 2a 01 02`).
- **The daemon.** `iem-dante-dev --config <path> (--iface <name> | --ip <IPv4>)`, `--version` (`iem-dante-dev <workspace version> <GITHUB_SHA or local>`). It binds ARC, CMC and the info server on the one address, keeps mdns-sd to that interface's IPv4 (all interfaces disabled, then the address's enabled), announces, and after every rename the ARC server saved (the state file first, `arc::respond`; then its `Notify`) announces again: only the changed records go out. The interface's facts for the network info come from its files, read by the binary and parsed in `daemon.rs`: the MAC from `/sys/class/net/<iface>/address`, the link speed from `.../speed` (0 when unknown or missing, at most 10 000), the gateway from `/proc/net/route` (the interface's first default route, up and through a gateway, in its subnet; else 0.0.0.0). SIGTERM/SIGINT end serving; the mDNS daemon's shutdown then sends the goodbyes (confirmed within 3 s), exit 0. Exit 1 (address not there yet, MAC file unreadable, serving failed, goodbyes unconfirmed) is restarted by the unit, 2 (command line, config, state file, a state file folder it cannot write, an interface without a usable MAC) is not. Right after loading the device it creates and removes the state file's temporary file (`DeviceState::check_writable`, the `<name>.tmp` `save` writes), so a folder it cannot write is exit 2 at the start, not a refused first rename. Decisions live in `daemon.rs` (mutated; tests on loopback with a fake registry and receivers standing in for the groups); `src/bin/iem-dante-dev.rs` is Linux-only glue, excluded from mutation, with a stub `main` elsewhere. No CI job builds the crate on Windows or wasm.
- **Logs** name counts, ports, opcodes and channel numbers, never a device or channel name, an address or a MAC (our own lines). mdns-sd's own lines (through `log`) may name records: the box's journal is private, never pasted raw into a ticket.
- **The service.** `scripts/gen3/iem-dante.service`: `/opt/iemmixer/bin/iem-dante-dev --config /etc/iemmixer/dante-device.toml --iface ${IEM_DANTE_IFACE}` (from `/etc/iemmixer/iem-dante.env`), `User=` from the drop-in `/etc/systemd/system/iem-dante.service.d/10-user.conf` (the box's admin user, never root), `StateDirectory=iem-dante` (the private config's `state_file` lies in `/var/lib/iem-dante`), no capabilities (every port above 1024), `Restart=on-failure`, `RestartPreventExitStatus=2`, a stop bounded at 10 s with `SendSIGKILL=no` (I8: a request and a bounded wait, never force-ended).
- **The CI build.** The `dante-bin` job builds it in release for x86_64 Linux, checks it is an x86-64 ELF whose `--version` names this run's `GITHUB_SHA`, prints its sha256 and uploads `iem-dante-dev-<sha>` on pushes (dev and main). A new job: the required checks on `main` are regenerated from the job list (`.claude/rules/ci-rust-toolchain.md`).
- **Deploy** (dev time, from the dev box): `scripts/gen3/deploy.sh --host <user@host> --artifact <the downloaded iem-dante-dev> --sha256 <the job's sha256> --config <ops device config> --iface <the box's Dante interface>`. Refused while `EVENT-NOW` exists (`$IEMMIXER_EVENT_NOW`, else `~/.config/iemmixer/EVENT-NOW`), again right before the install; the artifact's sha256 checked; a `--host` that is not the `GEN3_HOST` of iempc's private env (`$PC_ENV`, else `~/.config/iemmixer/iem-pc.env`, read as iempc's `load_env` reads it) is one warning, an env without `GEN3_HOST` too (no env file: none; the warnings name no value); right after `id -un` (never root) `ssh <host> sudo -n -l systemctl stop iem-dante` must succeed, else refused before anything is copied (a device "ide event" could not stop is never installed; the review of PR #78); scp into `~/.cache/iem-dante-deploy` (overwritten, never deleted); then on the box `sudo -n install -D -m 0755|0644 <stage file> <target>` for `/opt/iemmixer/bin/iem-dante-dev`, the drop-in (before the unit, so a failure between them never leaves a unit without its `User=`), the unit, `/etc/iemmixer/dante-device.toml` and `/etc/iemmixer/iem-dante.env`, and `sudo -n systemctl daemon-reload`, `enable iem-dante`, `restart iem-dante`; then the flag once more: one that came during the install ("ide event" may have stopped the service before the restart started it again) runs `sudo -n systemctl stop iem-dante` and exits 1, nothing read back (a stop that fails says the device may still run); read back: the installed sha256, `--version`, `systemctl is-active` after `GEN3_SETTLE_S` (3 s). **The sudoers rule** (the box's admin user, `NOPASSWD`, since every call is `sudo -n`) must allow exactly: `install -D -m 0755|0644` of the five stage files to their targets, `systemctl daemon-reload`, `systemctl enable iem-dante`, `systemctl restart iem-dante` and `systemctl stop iem-dante` (the event's stop and deploy's after a late flag; `sudo -n -l` of an allowed `NOPASSWD` command asks no password and needs no rule of its own). Tests: `scripts/gen3/test_deploy.py` (a stand-in ssh/scp; `PC_ENV` points at a temporary file, so the dev box's own env is never read; the `integrity` job runs them).
- **The box's clock (phase B, plan `docs/superpowers/plans/2026-10-26-gen3-phase-b-audio-through.md` Task 2).** dantesync (MIT, the fleet's PTPv1 follower; the release camera-box's `DANTESYNC_VERSION_PIN` names) is the box's one PTP owner, a follower of the band's audio grandmaster: it holds UDP **319/320** (PTP event and general, joined to 224.0.1.129 on the allowed grandmaster's subnet), UDP **31900** (its time server: `DSYN`/`DSYX` queries) and TCP **8898** (its read-only HTTP status), and no 123 (NTP server mode off; its NTP client and its poll of the fleet's NTP master on 31900 go out from ephemeral ports). Our device never opens 319/320, never sends PTP and can never be a grandmaster (design §5.5): its media clock reads PTP time from 127.0.0.1:31900 (`clock`, `clock::dsyx`). `iem-dante-dev clock --seconds <n>` runs that poller alone (`clock::Poller`, the service's own step) and prints one JSON line a poll, numbers only (`daemon::ClockLines`: t_s, ready, this poll's k_ns, dk_ns since the line before, off_ns against the anchored k, re_anchors, re_anchor_ns, holdover, sample 0–5, dantesync's locked, mode, freq_ppb); it serves nothing. **Install** (dev time, from the dev box): `scripts/gen3/install-dantesync.sh --host <user@host> --version <vX.Y.Z> --sha256 <the release asset's sha256> --config <iemmixer-ops/site/gen3-dantesync.json>`. The pin and its sha256 are arguments (read from camera-box's `scripts/dantesync-version-gate.sh` and the release's `dantesync-linux-amd64.sha256`; kept beside in the private env as `GEN3_DANTESYNC_VERSION`/`GEN3_DANTESYNC_SHA256` for the record), never "latest" and never a source build: the dev box downloads `<tag>/dantesync-linux-amd64` and its `.sha256` (`$DANTESYNC_RELEASE_BASE`, a test seam) and both must equal `--sha256` before anything reaches the box (camera-box's fleet-upgrade order). The config must be a follower's (exit 2, values never printed): `ntp_server` (the fleet's NTP master), `ntp_server_mode.enabled` false, `http_status` enabled on 8898, `system.gm_allowlist` the audio grandmaster, `system.clock_discipline` absent or `ptp_phase_lock` (only it carries the date offset the media clock needs). Refused with nothing changed on the box: the `EVENT-NOW` flag (before the download and again right before the install); ptp4l, phc2sys or statime installed (a binary on the PATH or a loaded unit: one read-only survey); anything but dantesync on UDP 319/320 (`sudo -n ss -Hulnp`; dantesync's own sockets are an update); no python3 on the box; a staged binary whose `--version` is not the tag's. Then, as dantesync's `install.sh` does it, every step `sudo -n` from `~/.cache/dantesync-install`: `install -D -m 0755` the binary to `/usr/local/bin/dantesync`, `-m 0644` the config to `/etc/dantesync/config.json` and install.sh's unit (`User=root`, `Restart=always`, FIFO 50, no `--interface`: with an allowlist dantesync joins on the grandmaster's subnet) to `/etc/systemd/system/dantesync.service`, `systemctl daemon-reload`, `systemctl disable --now` each of systemd-timesyncd, chrony, ntp and time-sync-coordinator the box has, `timedatectl set-ntp false`, `systemctl enable dantesync`, `systemctl restart dantesync` (nothing failing is ignored, unlike install.sh). Read back: the installed sha256, `dantesync --version`, `systemctl is-active` after `GEN3_SETTLE_S` (3 s), then `scripts/gen3/dantesync_probe.py` fed to the box's `python3 -` (no file left there; within `GEN3_DANTESYNC_WAIT_S`, 300 s, polled once a second): a DSYX reply, locked, with the date-offset extension, and the HTTP status `date_authority` follower with `gm_source_ip` in the config's `gm_allowlist` (an address, a CIDR prefix, or a host name through `gm_allowlist_resolved`); one numbers-only JSON line (waited_s, dsyx, locked, mode, ext, freq_ppb, http, follower, gm_allowed), each failing reason on stderr. A read back that fails after the install leaves dantesync installed and running (no rollback); read again by hand: `ssh <host> python3 - --wait 600 < scripts/gen3/dantesync_probe.py`. **Its sudoers lines** (besides deploy.sh's, the box's admin user, `NOPASSWD`, exactly as the script runs them): `ss -Hulnp`; `install -D -m 0755 .cache/dantesync-install/dantesync /usr/local/bin/dantesync`; `install -D -m 0644` of `.cache/dantesync-install/config.json` to `/etc/dantesync/config.json` and of `.cache/dantesync-install/dantesync.service` to `/etc/systemd/system/dantesync.service`; `systemctl daemon-reload`; `systemctl disable --now systemd-timesyncd|chrony|ntp|time-sync-coordinator`; `timedatectl set-ntp false`; `systemctl enable dantesync`; `systemctl restart dantesync`. "ide event" never stops dantesync (receive-only, as the fleet's other followers). Tests: `scripts/gen3/test_install_dantesync.py` (the install against a stand-in ssh/scp and a `file://` release; the probe against stand-in time and status servers on loopback).
- **The event stop.** "ide event" (`iempc event`) also runs `ssh <GEN3_HOST> sudo -n systemctl stop iem-dante` beside the PC's switch, right after the flag, collected within `GEN3_STOP_S` (5 s) and never changing the event's exit code (`.claude/rules/guard.md`, dev-box bullet). Nothing of it can stop, delay or change the event path (the review of PR #78): `start_gen3_stop` and `end_gen3_stop` catch every exception (Popen's `ValueError` on a NUL byte the env file kept, its `OSError` with no `ssh` on PATH, a closed stderr or stdout), every Gen 3 line goes through `gen3_say` (a line stderr cannot take is lost, never raised) and the report through `gen3_emit` (a warning when stdout cannot take it). The ssh runs in a session of its own and writes into `gen3-stop.log` in iempc's state folder (appended under a `--- <time> gen3 stop started` line, emptied past 256 KiB at the next stop's start), never into pipes that close when iempc ends: a failed stop's warning quotes its own output from there, a stop left running names the log, and a log that cannot be opened is one warning while the stop still runs. `GEN3_HOST` is an optional key of the private `iem-pc.env`; absent is one info line. Nothing starts the device again when the event ends (deploy.sh, or `sudo systemctl start iem-dante` in dev time); a reboot of the box during an event starts it (the unit is enabled, the flag lives on the dev box).
- **P6.** The device's test name and its channel names live only in the ops repository's device config (`iemmixer-ops/site/gen3-device.toml`), the fleet's NTP master and the audio grandmaster only in its dantesync config (`iemmixer-ops/site/gen3-dantesync.json`), the box's address and user only in the private env and the deploy's arguments. This repository holds the synthetic `config/test-dante-device.toml` (`test-device`, `RX 1`…`RX 32`, `TX 1`…`TX 16`) and synthetic addresses in tests (`10.0.0.10`, locally administered MACs `02:00:00:00:00:0a` / `…:01`); a captured packet goes into a test only with its MAC replaced.
- **Dante rule.** Our device only: the tool never sends a command that changes another Dante device; reads of other devices (mDNS browsing, ARC reads) are allowed (CLAUDE.md, Dante).
