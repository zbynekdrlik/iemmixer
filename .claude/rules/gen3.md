# Gen 3: our own Dante device (#72; design `docs/superpowers/specs/2026-10-24-gen3-linux-dante-design.md`, plan `docs/superpowers/plans/2026-10-25-gen3-phase-a-dante-device.md`)

- **The crate.** `iem-dante` is GPL-3.0-or-later (parts adapted from teodly/inferno at `9767558`; each adapted file names its origin in its header) and never a dependency of `iem-engine` in phase A (`scripts/check_engine_deps.py` stays clean). Modules: `device` (the config and the persisted names, Dante's name rules), `wire` (the 10-byte request/response header), `arc` (UDP 4440, below; `arc::gaps` counts what it refuses or leaves unanswered), `cmc` (UDP 8800: the 0x1001 advertisement), `info` (UDP 8700: the info requests and the heartbeat, below), `announce` (the mDNS records and the `Announcer` behind a two-call `Registry`, so tests use a fake and never multicast), `daemon` (the binary's command line, `pick_interface`, `net_info` and the `serve` loop). Phase A sends no PTP and no audio: the device is a follower only and never a grandmaster (design §5.5).
- **ARC (`arc.rs`, inferno's `arc_server.rs` and `proto_arc.rs`).** Every opcode inferno's server answers is answered byte for byte as inferno answers it with no flows and no subscriptions, and nothing else: a request Dante Controller gets refused it asks again at once (live, #72 2026-10-26: 0x2200 and 0x2204 about 2 250 times a second while the device refused both with 0xffff; the service stayed stopped until fixed). Op1 → reply (status OK unless named):

  | op1 | reply |
  |---|---|
  | 0x1000 | counts (TX rename flag; 0 TX and 0 RX flows, inferno says 32) |
  | 0x1002, 0x1003 | the device name; the names (current, factory, board, `:705`) |
  | 0x1100, 0x1102 | 110, 94 zero bytes |
  | 0x2000, 0x2010 | TX channels (default names), TX names now; pages of 32, `0x8112` while more follow |
  | 0x2013, 0x3001 | TX rename (`00 00`), RX rename (no body); all or nothing, 0xffff if any item is invalid (inferno renames the valid ones) |
  | 0x2200, 0x3200 | TX, RX flows: `10 00` + 32 zero bytes (16 slots, none used) for any first flow |
  | 0x2201, 0x2202 | create, delete a multicast TX flow: 0xffff, no body (inferno without flows) |
  | 0x2320 | status 0x0030, no body (inferno's "???") |
  | 0x3000 | RX channels, pages of 16, no subscription |
  | 0x3010 | subscribe or unsubscribe: no body; phase A subscribes nothing, one info line with the channel numbers |
  | 0x3014 | netaudio's unsubscribe (`0001 0000 <ch>`): no body |
  | 0x3300 | `38 00 38 fd 38 fe 38 ff` |

  0xffff only where inferno answers it: a page request without its first item (bytes 2–3 of the body zero, or under 4 bytes; channel and flow lists), a rename that renames nothing, 0x2201, 0x2202. **No reply** (`ArcOutcome::Unanswered`, as inferno's catch-all and its reads that fail before answering): any other opcode (0x2204 — not in inferno at 9767558 nor in netaudio, Dante Controller's body `00 01 00 01` is a page request — 0x1001 netaudio's device rename, 0x1101 its latency), op2 not 0, 0x2201 under 2 bytes, 0x2202 under 4, 0x3010 under 2 or with `min(count, len / 6)` 6-byte items running past the end, 0x3014 under 6. A datagram that is no request is dropped (`Ignored`). Tests: `arc/tests.rs` pins each reply; `every_opcode_inferno_answers_is_answered_as_inferno_answers_it` walks inferno's 18 opcodes (0xffff only for 0x2201/0x2202).
- **The gap guard (`arc/gaps.rs`).** `arc::serve` counts every refused (0xffff) or unanswered request per peer (its IP address, named by an id only: 1 for the first peer seen, ids for the server's life, at most 64, then 0) and opcode, at most 256 entries a window (the rest summed), and logs one warning a minute: `ARC requests refused or not answered in a minute (peer id, opcode)` with `requests=<n>` and `counts=peer 1 0x2204 unanswered 134999, …` (16 entries, then sums). The window opens at its first request; the server looks every `GAP_CHECK` (1 s). A log, never a limiter: no answer depends on it. A live run with Dante Controller reads it in the journal; a steady count is a gap to close.
- **Info and heartbeat (`info.rs`, inferno's `info_mcast_server.rs`).** Dante Controller finds the device over mDNS and CMC, then asks UDP **8700** for its board info and goes on to ARC only once that is answered (live, #72 2026-10-26). The server listens at the device's address only (as inferno: no group joined) and sends everything multicast, from that socket (Linux routes a multicast from a bound source address out of that address's interface): replies to **224.0.0.231:8702**, a heartbeat every second to **224.0.0.233:8708** (the first at once), and the board and product info unasked at start. Every packet has a 32-byte header (start code 0xffff info / 0xfffe heartbeat, length, the device's own sequence from 1 over every packet, process id 0, the CMC device id, `Audinate`, an 8-byte opcode). Answered (byte 1 of a request is any; for 0x21, 0x13 and 0x77 the last byte too): `07 xx 00 61` board info → `07 2a 00 60`, 200 bytes; `07 xx 00 c1` product info → `07 2a 00 c0`, 336 bytes (the config's manufacturer and model, the workspace version at 0x1c); `07 xx 00 13` network info → `07 2a 00 11`, 64 bytes (link speed, MAC, address, netmask, gateway twice); `07 xx 00 77` → `07 2a 00 78`, `00 00 00 03 00 00 00 00`. No clock in phase A: clock stats (`07 xx 00 21`) get no reply and the heartbeat is the header alone, as inferno before its clock has an offset (no 0x8001 frequency, 0x8002 peaks or 0x8003 RX latency records). Anything else gets no reply and an info line with its opcode, the way to see what Dante Controller asks next; shorter than 32 bytes is dropped; start code and length are not checked (inferno). Not adapted yet: inferno's channel-change notification on 8702 after an RX rename (`07 2a 01 02`).
- **The daemon.** `iem-dante-dev --config <path> (--iface <name> | --ip <IPv4>)`, `--version` (`iem-dante-dev <workspace version> <GITHUB_SHA or local>`). It binds ARC, CMC and the info server on the one address, keeps mdns-sd to that interface's IPv4 (all interfaces disabled, then the address's enabled), announces, and after every rename the ARC server saved (the state file first, `arc::respond`; then its `Notify`) announces again: only the changed records go out. The interface's facts for the network info come from its files, read by the binary and parsed in `daemon.rs`: the MAC from `/sys/class/net/<iface>/address`, the link speed from `.../speed` (0 when unknown or missing, at most 10 000), the gateway from `/proc/net/route` (the interface's first default route, up and through a gateway, in its subnet; else 0.0.0.0). SIGTERM/SIGINT end serving; the mDNS daemon's shutdown then sends the goodbyes (confirmed within 3 s), exit 0. Exit 1 (address not there yet, MAC file unreadable, serving failed, goodbyes unconfirmed) is restarted by the unit, 2 (command line, config, state file, an interface without a usable MAC) is not. Decisions live in `daemon.rs` (mutated; tests on loopback with a fake registry and receivers standing in for the groups); `src/bin/iem-dante-dev.rs` is Linux-only glue, excluded from mutation, with a stub `main` elsewhere. No CI job builds the crate on Windows or wasm.
- **Logs** name counts, ports, opcodes and channel numbers, never a device or channel name, an address or a MAC (our own lines). mdns-sd's own lines (through `log`) may name records: the box's journal is private, never pasted raw into a ticket.
- **The service.** `scripts/gen3/iem-dante.service`: `/opt/iemmixer/bin/iem-dante-dev --config /etc/iemmixer/dante-device.toml --iface ${IEM_DANTE_IFACE}` (from `/etc/iemmixer/iem-dante.env`), `User=` from the drop-in `/etc/systemd/system/iem-dante.service.d/10-user.conf` (the box's admin user, never root), `StateDirectory=iem-dante` (the private config's `state_file` lies in `/var/lib/iem-dante`), no capabilities (every port above 1024), `Restart=on-failure`, `RestartPreventExitStatus=2`, a stop bounded at 10 s with `SendSIGKILL=no` (I8: a request and a bounded wait, never force-ended).
- **The CI build.** The `dante-bin` job builds it in release for x86_64 Linux, checks it is an x86-64 ELF whose `--version` names this run's `GITHUB_SHA`, prints its sha256 and uploads `iem-dante-dev-<sha>` on pushes (dev and main). A new job: the required checks on `main` are regenerated from the job list (`.claude/rules/ci-rust-toolchain.md`).
- **Deploy** (dev time, from the dev box): `scripts/gen3/deploy.sh --host <user@host> --artifact <the downloaded iem-dante-dev> --sha256 <the job's sha256> --config <ops device config> --iface <the box's Dante interface>`. Refused while `EVENT-NOW` exists (`$IEMMIXER_EVENT_NOW`, else `~/.config/iemmixer/EVENT-NOW`), again right before the install; the artifact's sha256 checked; scp into `~/.cache/iem-dante-deploy` (overwritten, never deleted); then on the box `sudo -n install -D -m 0755|0644 <stage file> <target>` for `/opt/iemmixer/bin/iem-dante-dev`, the unit, the drop-in, `/etc/iemmixer/dante-device.toml` and `/etc/iemmixer/iem-dante.env`, and `sudo -n systemctl daemon-reload`, `enable iem-dante`, `restart iem-dante` (the commands a limited sudoers rule must allow); read back: the installed sha256, `--version`, `systemctl is-active` after `GEN3_SETTLE_S` (3 s). Tests: `scripts/gen3/test_deploy.py` (a stand-in ssh/scp; the `integrity` job runs them).
- **The event stop.** "ide event" (`iempc event`) also runs `ssh <GEN3_HOST> sudo -n systemctl stop iem-dante` beside the PC's switch, collected within `GEN3_STOP_S` (5 s) and never changing the event's exit code (`.claude/rules/guard.md`, dev-box bullet). `GEN3_HOST` is an optional key of the private `iem-pc.env`; absent is one info line. Nothing starts the device again when the event ends (deploy.sh, or `sudo systemctl start iem-dante` in dev time); a reboot of the box during an event starts it (the unit is enabled, the flag lives on the dev box).
- **P6.** The device's test name and its channel names live only in the ops repository's device config (`iemmixer-ops/site/gen3-device.toml`), the box's address and user only in the private env and the deploy's arguments. This repository holds the synthetic `config/test-dante-device.toml` (`test-device`, `RX 1`…`RX 32`, `TX 1`…`TX 16`) and synthetic addresses in tests (`10.0.0.10`, locally administered MACs `02:00:00:00:00:0a` / `…:01`); a captured packet goes into a test only with its MAC replaced.
- **Dante rule.** Our device only: the tool never sends a command that changes another Dante device; reads of other devices (mDNS browsing, ARC reads) are allowed (CLAUDE.md, Dante).
