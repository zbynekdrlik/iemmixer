# Live E2E on the Gen 3 box: `iempc gen3-gate live` (S7, #10; #72 phase H)

The gate is `scripts/iem-pc/iempc_gen3_live.py`, its refusals and its run in `.claude/rules/gen3.md` (the box's live gate), its verdict `live_verdict.py`. The #10 comments of 2026-10-08 hold the lanes' decisions.

## Where they run

- Specs `e2e/tests/live/*.spec.ts`, config `e2e/playwright.live.config.ts`: one worker, no retries, trace, screenshot and video off (a trace would hold the tokens and the host). The mock config ignores `**/live/**`.
- Only from `iempc gen3-gate live` on the dev box, in one iempc process: the begin (the box's HIL job), then Playwright and the bursts in parallel, the end, the verdict, the status `live/gen3` on the box's build. Playwright runs Chromium on the dev box against the band's public URL through the tunnel (the members' real path); nothing of it runs on the box. The notes below call that dev-box process the runner.
- Public CI only lists them: the e2e job's `--list` step, with no `LIVE_*` and the mock PINs removed. Locally: `--list` of both configs. The pure support runs in the mock job (`tone.spec.ts`, `live-support.spec.ts`).

## Variables, tokens and P6

- `support/env.ts` reads every value on first use (`box()`, `live()`, `runMarker()`), so `--list` needs none; a refusal names the variable, never its value. A new `LIVE_*` goes there, with validation. `box()` holds what every spec against a server of ours reads (the origin, the build, the tokens, the member, the test input) and is what the fixtures (`expectBuild`, `openLive`, `openStart`, `apiGet`/`apiPost`, the relay, `liveSocket`, `LiveMixer`) read; `live()` adds the talkback input and the burst level (the live specs, `BurstWatch`). `originOf(name, schemes, env)` is the origin's check (`live-support.spec.ts` runs it).
  - `LIVE_BASE_URL` a bare `https://` origin (an `http://` one only in a process whose spec called `allowPlainHttp()` before the first read: the Gen 3 box's, #72; a live spec never does); `LIVE_SHA` the 40-hex build; `LIVE_TOKENS` the path of a JSON `{engineer, member}` of JWT-shaped tokens; `LIVE_MEMBER`, `LIVE_TEST_INPUT`, `LIVE_TALKBACK_INPUT` ids; `LIVE_BURST_DBFS` at most −20; `LIVE_RESULTS` the JSON report's path (config).
  - **`LIVE_MEMBER` plays in every band** (ops variable, roster mode #58): a person who plays only in the other band has no mixer page while that band plays (a vacant set's notice), so the limiter test and the member's tunnel test fail at `openLive` waiting for `global-volume-fader`, on any build. Pick a person who plays in both bands. The limiter test's EQ restore goes back through the protocol's f32 and can leave the band's frequency a few millionths of a hertz off (inaudible).
  - `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT` (digits) build the client-error marker.
- **No band PIN (decision 1):** the gate mints an engineer token and one member token on the box (`iem-soakclient token`, `iempc_gen3.mint_tokens`, expiry 3600 s), read back into a 0700 folder of iempc's state, removed on the box at once. Nothing logs in; `openLive(page, who)` stores the token as the UI does (`storeLogin`), from `/api/version`, a page with no manifest: the full Chromium (the push spec) fetches a manifest's icon for its install check once a page with one has loaded, and a navigation that cuts that download after its answer began logs "Error while trying to use the following icon from the Manifest" into the next page (live run 1; `live-support.spec.ts` holds an icon's answer to show it). The headless shell runs no install check.
- **A one-off real-browser check from the dev box** (#63 Step 7, 2026-10-22): mint a short engineer token on the box as the service user with `iem-soakclient token --jwt-secret-file <server secrets/jwt_secret> --sub engineer --engineer --seconds 900 --out <file>`, read it into an owner-only file, remove it on the box; store it as `storeLogin` does (`/api/version`, `localStorage.iem_token`) and drive the page with Playwright through `LIVE_BASE_URL`; delete the token file after. Never a PIN.
- **Import `test` from `./support/live`, never `support/session.ts`:** its `pins.ts` throws at import without PINs (the CI list step catches it).
- **No error carries a URL, a token, a push endpoint or a site value.** `navigate`, `apiGet`/`apiPost` (`apiAt`), the relay and `liveSocket` throw fixed words. Compare a value that may be secret or site data as a boolean (`expect(a === b, "…").toBe(true)`), never `toBe(value)`, and poll a boolean (`expect.poll` prints what it received); never `toHaveURL`; read a request's body with `bodyOf`, never `postDataJSON()` (its error holds the body). The live console guard redacts URLs (`support/console.ts`, `redacted`); a page outside the fixtures uses `guardConsole`.

## Relay and no reconnect

- Every page socket goes through the `relay` fixture (`relaySockets`): one real socket per path and test, opened only after `/api/version` names `LIVE_SHA` (`expectBuild`); a second attempt is refused and never reaches the server; a server close fails the test. A persistent context calls `relaySockets(page)` itself.
- Runner sockets (`BurstWatch`, the desk's `LiveMixer`) follow the same rule, through one handshake (`liveSocket`: the page's Origin and User-Agent, 15 s bound). `LiveMixer`'s URL follows the origin's scheme (`mixerSocketURL`: `wss:` on the public host, `ws:` on the Gen 3 box's `http:`).
- A request that writes server state (a push subscribe or revoke, a client error), or whose answer a test judges (`/api/tunnel`), comes after an `expectBuild`: nothing is written to a server of another build, and a failure names the hop.
- **"The server closed" means the far side: the server or the tunnel between** (live run 3, 2026-10-09). The relay, the watch and the desk's sockets name a far-side close with its code, its UTC time, the time open and since the last message (`socket.ts` `closeFacts`, never the far side's reason text); the watch adds its last status. Match the time against the server's journal (the runner's clock ran about 1 s ahead of the server's in run 3): a session the server ended logs its end (`WebSocket disconnected`, `Audio WebSocket disconnected`, `client silent: closing`; only a mixer socket that failed or was sent away before its first state logs no end), and a silence close reaches the runner as code 4002 when the path still carries it; a drop on the path reads 1006. In run 3 the runner lost two sockets at once (the watch and the page's mixer socket, about 0.5 s after a burst's `listening`) and later a third, and the server logged no end for any: the lost listen sessions' probe edges kept coming at the same microsecond as the live watches' for at least a minute and a half; the lost mixer session's survival is inferred only from its missing end. The path between dropped them; since then the server ends a session silent for 30 s (`server-engine.md`, not yet proven through the tunnel). A watch that finds no burst names its frame and status counts, its own frames since the last `listening` and where it stands (run 3's meters spec: no burst in 163 s with the watch open; a silent stream or a miscount, the next run's words decide). The harness still never opens a socket twice: a far-side close fails the test.
- **A runner socket lost mid-burst leaves the spec's changes in place** (no other socket may undo them). The relay's fixed failure code makes the browser step red. The change stays in the engine's state: nothing re-imports it.

## Bursts and the burst-only rule

- While Playwright runs the gate fires `iem-engine supervise test-signal mic1 -20 30 --listen` in bursts of 30 s every 60 s at −20 dBFS, the HIL ceiling (decision 4).
- The server tells only a `&hil=1` listen socket a burst's edges: `AudioStatus` `probe` (its first probe frame) and `listening` (the first own frame after). The probe gate is per socket, so the edges are per socket.
- **`BurstWatch` counts a burst only after 5 s of the slot's own frames before its `probe`.** A watch opened mid-burst gets `probe` with its first frame, and a probe stall over the gate's 100 ms hold gives `listening` and `probe` again: neither tells the time left, so the watch waits for the next burst. `inBurst()` ends at most 28 s after the `probe`.
- **`desk.ts` is the only way a live spec changes the engine.** A change happens only inside a burst (every mix TX is zero) and goes back before it ends, checked against `listening`: `desk.during` runs the steps inside one burst, `desk.change` refuses a change outside it or with under 2 s left and keeps its undo, `desk.track` keeps a page action's undo. The undos run newest first when the steps end, at once when the burst ends (a 50 ms guard), and at the fixture's teardown (a body's `finally` does not run after a timeout).
- **The server drops a closed socket's queued commands:** every socket waits for its own barrier (`applied()`) before it closes.
- Tunnel, push and client error change no engine state and need no burst.

## Measurements (row → spec)

- Numbers leave a test only as `live_number` annotations whose keys are `LIVE_NUMBER_KEYS`, the verdict's `NUMBER_KEYS` (`tone.spec.ts` compares them).
- **Listen (#25):** inside a burst the engineer clicks Listen; the first decoded audio within 3 s (`first_audio_ms`). The player's output through an `AnalyserNode`, `toneOf` over 1 s: 1 kHz ± 1 Hz at `LIVE_BURST_DBFS` ± 0.5 dB (`listen_hz`, `listen_dbfs`). Every probe frame CELT, 20 ms, stereo, and decodes (`opus_frames`). **Reading a window must not stall the page or the runner** (live run 1: window 1 clean, window 2 a gap): the page's frames come through the relay in this process, and the player keeps only 80 ms ahead, so `readTone` moves the 32768 samples as one base64 string (13–36 ms measured locally); returned as a number array they took 200–500 ms and the player ran dry (`tone.spec.ts` runs the three windows on the real `audio_player.js` behind `routeWebSocket`). The spec names the player's own underruns (`playerDropouts`, `getStreamStats().dropouts`) in a gap's message and requires none from the settling to the last window (an underrun is a decoded frame that found the schedule behind the clock, not the arrival-gap count): a gap with underruns is a late feed, one without is silence the player was handed.
- **Talkback (A4):** Chromium's fake microphone plays 1 kHz at half scale, the page encodes it onto `/ws/talkback`; the runner reads the `LIVE_TALKBACK_INPUT` meter (its trim off, inside the burst). Median meter against the encoder's level: −8.4 ± 0.3 dB (`talkback_db`). **Chromium's AGC ramps the capture for ~2.5 s** (`talkback-capture.spec.ts` checks it), so the window starts 2.7 s after the encoder's first frame. Talk is held at most 8 s; while held, never 5 silent meter frames in a row, counted from 300 ms after the input's meter first hears the talkback: the encoder starts beside the socket's open (#58), so its first frame can come a second before the server hears any.
- **Limiter (X14):** the burst's sine, its input dry and open, at the mix's level +12 dB and the mix EQ's first peak band at +12.04 dB (1 kHz): +4 dBFS into a limit of −6 dB. The counter grows ≥ 1.5 s within 5 s, and Reset in the page zeros it (`limiter_active_s`). A solo fails it early.
- **Meters (#25):** the runner's socket only: ≥ 27 `Meters` frames in 3 s, and the burst input's median peak within 0.5 dB of the burst level, the input dry and open (`meter_fps`, `burst_input_dbfs`).
- **Tunnel:** `/api/tunnel` reads Ok with ≥ 1 ready connection; the engineer's `tunnel-status` reads `Vonkajší prístup: OK` (class `ok`); a member's page shows no `tunnel-banner` and no indicator once a `TunnelStatus` frame came (the relay's `events`).
- **Push:** a persistent profile (`chromium.launchPersistentContext`, notifications granted) on the full Chromium, `channel: "chromium"`: the headless shell has no push service (subscribe fails "push service not available", measured 2026-10-09), so the dev box needs full Chromium, never `--only-shell`. Its own console guard allows nothing. A fresh profile's first `pushManager.subscribe()` takes 4–33 s (the push service's registration; seven of nine runs over 27 s, 2026-10-09), so the wait for the subscribe POST is 90 s (`SUBSCRIBE_MS`; 30 s failed live run 1). The subscribe answers 200 with an `https://` endpoint the browser holds; the logout's unsubscribe answers 200 for it, and `getSubscription()` is null. A `PushLedger` on the context keeps every posted endpoint until an unsubscribe of it answers 200; the fixture's teardown (it runs also after a timeout) unsubscribes in the browser, closes the profile (nothing more can be posted), then, after `expectBuild`, revokes the rest on the server. The gate's end compares the server's subscription counts (`push_before`/`push_after`) as the backstop.
- **Client error:** the start page posts `{panic_message: iemmixer-live-marker-<run id>-<attempt>}` to `/api/client-error`, which answers 204; the gate's end finds the marker in `iem-server.service`'s journal.

## The verdict (`live_verdict.py`, `live/gen3`)

- Pure, stdlib. The record contract is its module docstring: `begin.json`, `pc.json`, `bursts.jsonl`, `evidence.json`, `results.json` (the report).
- Cancelled, never red: a cancelled PC job, a failed one without a record, `left-dev`/`not-free`. A cancelled browser job alone is red, and so is a PC job that succeeded without a record.
- The checks, in order: begin ready; the pc job `browser-done` with ≥ 1 burst, each exit 0; every expected title passed; the client-log marker found; `push_after` ≤ `push_before`; the job end ok. Each job's result comes last in its check.
- **Titles are read with `live_verdict.py`'s `test(` rule (`PW_TEST`):** a spec's tests are called through `test(` with a literal title (a `test.extend` result is named `test` too), and no comment writes `test(`.
- The summary holds fixed codes, numbers and spec titles, never a test's error text.
