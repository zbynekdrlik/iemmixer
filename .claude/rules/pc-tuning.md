# PC tuning window (S1c, #15)

`scripts/pc-tuning/tuning_window.py` drives the PowerShell tuning/measure modules (`IemTuning.psm1`, `IemMeasure.psm1`) over ssh, on top of `spike_window.py`'s window, state, "ide event" guard and unwind. `latency_report.py` analyses the collected data. A window opens only through `spike_window.py new --signal`; every command checks the "ide event" flag and pre-empts like the spike window. Site values (driver/registry/task names, channel numbers, handover values, the tuning profile) come ONLY from the private `$SPIKE_ENV` (`~/.config/iemmixer/asio-spike.env`) and `$TUNING_PROFILE` (`~/.config/iemmixer/pc-tuning.json`) at run time; they and the runbooks live in the private ops repo, never here (P6). The profile's `nic.hwid` is the NIC's exact `MatchingDeviceId` and each `devices[].hwid` a full `PCI\VEN_xxxx&DEV_xxxx` id (the PowerShell side checks both before any write). Tests use synthetic values (inputs 101–124, synthetic GUIDs, layout housekeeping/card/nic/audio).

- **The guard era (#15, re-plan and decision of 2026-10-07).** Since S6 the guard's engine holds the card in dev, and it is the engine that must hold 32: the guard enters and exits the tuning modes, reads the drift and runs `apply-tier2` through its elevated tuning task, which loads `IemTuning.psm1` and `profile.json` only from the elevated tuning folder (`%ProgramData%\iemmixer\tuning`: Administrators and SYSTEM change it, the user reads). The trust model: only the admin ssh path from the dev box fills it — `iempc tuning-install` and the refresh after `iempc activate` (`scripts/iem-pc/iempc_tuning.py`, IemPc's `Install-IemTuning`: every file's sha256 and the profile checked by IemTuning's own loader before anything is written) — never the bundle's copy in the user's root, which any process of the user may change. `iempc trace` (`iempc_trace.py`) measures the live engine with IemMeasure from the same folder and parses with `latency_report` (unchanged); details in `guard.md`. The spike window (`tuning_window`) stays for spike-only work: a window takes the card from the guard's engine. **The lane findings of 2026-10-07 (#15):** (1) the bootstrap's `IemPc.psm1` is imported only from the admin-only `<elevated root>\bootstrap-stage` copy, checked before and after the copy (`elevated_ps.staged_import`, `guard.md`); (2) **TEMP rule:** every elevated session that imports IemTuning sets TEMP and TMP to the admin-only `<elevated root>\temp` first — its Add-Type has csc write and then load a DLL in TEMP, and the session user's TEMP is open to every process of the user: `sw.measure_import` (so `tuning_body`/`tps`/`tps_change`, the unwind's tuning-exit and `analysis_step`) and the trace's `measure_load` through `elevated_ps.temp_first` (`scripts/asio-spike/elevated_ps.py`: one line, composed on the dev box, the folder made and read back like IemPc's `Install-IemElevatedFolder`), `Install-IemTuning` and the guard's tuning task through IemPc's `Set-IemElevatedTemp`. Never put TEMP into the stop-only import (`trace_stop_import`, the trace's stop): it compiles nothing. The asio-spike job's analysis step reads the TEMP the compile used (`ANALYSIS_PROBE`'s `temp`). (3) `iempc trace` records its run in `<state>/trace.json` before the start and removes it after a confirmed stop; `iempc event` (before `iemmode event`, inside its budget), `iempc dev` and the next trace stop a recorded trace first (`stop_recorded`: IemMeasure 'stop-only' from the elevated tuning folder; a failure keeps the record and prints an owner alarm, the event path goes on). (4) Every window session imports SpikePc, GoldenPc, IemMeasure and IemTuning only from the admin-only stage, checked against the window's attested bundle record (`asio-spike.md`'s stage rule); the stop-only import stages IemMeasure alone. (5) The elevated session runs only admin-only copies of our programs: `tuning-install` and `activate` also put the bundle's `iemmode.exe` into `%ProgramData%\iemmixer\bin`, which every iemmode call runs while it reads back (`guard.md`, `iempc_bin.py`).

- **One window lock (decision A of the #32 review).** `sw.window_lock()` is an exclusive `fcntl.flock` on `<STATE>.lock`, reentrant per thread, waited for at most `LOCK_WAIT_S` (1200 s, longer than a whole unwind; then an owner alarm and a `StepError`). It serialises across processes (spike_window, tuning_window, `iempc event`'s `spike_window.py preempt`): every state write (`save_state` writes a temp file of its own — pid + thread — and replaces atomically, under the lock), every read-modify-write (`sw.update_state(fields, change)` on the state AS SAVED NOW — never save a state loaded before a PC call), every unwind (`unwind` holds it; `cmd_preempt`/`cmd_to_event`/`cmd_reboot_prepare` read the state under it) and every bring-back (post-boot's too). Whoever comes second re-reads the state and does nothing when the window is already closed with REAPER back — two bring-backs at once would trigger the meter bridge twice (a REAPER dialog during the event, #9). Never hold the lock over a long PC wait (a run, a measurement); only over state updates, unwinds and bring-backs. `window_lock(wait_s)` / `update_state(..., wait_s=)` take a shorter bound where a caller has one (`iempc event`'s close after a failed preempt waits at most the event budget minus `SWITCH_MIN_S`). Long read-only calls run outside the lock and the write re-takes it on the state as saved then (`reboot-prepare`, `handover-s1a`: F2 round 3 m3, m5).

- **PC changes in flight: intents and settling (F2 round 3 MAJOR, decision 1, and the review of lane G2).** The protocol lives in `scripts/asio-spike/pc_change.py`; spike_window re-exports it, and it reaches the state, the lock, `ps` and `alarm` through spike_window at call time (`_sw()`), so faking `sw.ps` fakes it too (spike_window run as a script registers itself under its own name: one module, one lock state; import spike_window before pc_change). The lock guards the state, never a PC call (holding it across the call would make "ide event" wait for a save and quit or an enter). Every step that changes what the event depends on goes through `pc_change(step, bound_s, call, fields=, after=, check=, late=)`: to-dev (`SAVE_QUIT_S` 120, `fields` card `switching`), set-buffer (`SET_BUFFER_S` 60, `pref_current`), the run start (`RUN_START_S` 60), enter/exit (`MODE_S` 240, `tuning_mode`), apply/undo (`APPLY_S` 600). `begin_change` (under the lock, after `open_state` and the step's `check`) records `in_flight = {step, started (wall clock), bound_s, prior}` and the step's fields BEFORE the ssh call and refuses while another LIVE intent exists (`intent_live`: within its bound; a stale one is overwritten with an owner alarm); `end_change` clears it after the call, on error too, and merges `after` only while the window is still open. A body the PC refused on the stop file (nothing ran) puts `prior` back instead. The bound is the ssh call's own timeout; a new changing step needs one. A preempt or to-event unwinds under the lock (`unwind_closing`: REAPER back at once, and a `settling = {step, until}` record saved with the close), then `close_out` without the lock: `settle` — only after a `REAPER_STEPS` step (to-dev, set-buffer, run) — checks every `POLL_S` that REAPER runs and is the one ASIO holder (`reaper_on_card`) and brings it back again under the lock with an owner alarm (a failed read or bring-back is an alarm and the watch goes on), until `SETTLE_S` (15 s) after the step's process cleared its intent, at the latest `SETTLE_S` after the remaining bound (taken between 0 and `bound_s`: a clock step moves nothing); after a journal step it reads no PC and only waits for the intent to clear. Then the `settling` record goes, a journal step that never came back gets its deferred exit (`exit_left_behind`: clears the intent first, then the exit, an alarm), the stop file goes (`clear_stop`, in `finally`), and the preempt fails (exit 1, iempc lets the guard bring REAPER back) when the watch ended without REAPER on the card. A preempt that finds the window closed waits (without the lock) while another process's `settling` record is live (`wait_for_settle`), and `iempc event` runs the spike preempt for a closed window whose settle is live, so the guard's bring-back never runs next to a settle's. A step whose window was closed meanwhile runs its late handler `late(state, ran)` first (the intent still recorded, so the settle keeps watching; a handler runs only while its intent is the recorded one, never after `exit_left_behind` took it over), then raises `EventNow`: to-dev reads REAPER on the card and alarms only when no settle covers it (an alarm during a settle would send the owner to run the event path next to the settle's bring-back; it never brings REAPER back itself), set-buffer reads the preference and alarms unless it is the original (never written, I2), enter/exit/apply/undo run the tuning exit (`late_journal`: after an enter that ran, otherwise while `tuning_mode`), apply/undo that ran also alarm; a refused step (`ran` False) gets the state as it was before it and does neither. The journal writers (`JOURNAL_STEPS`) never meet the preempt's own tuning-exit: two writers at once lose journal entries, so the unwind records `{"deferred": ...}` for a live journal intent and the late step (or `exit_left_behind`) exits. Every changing body starts with `step_guard` (`changing`, `tps_change`): it throws `STEP_REFUSED` on the PC while `queue\stop` exists, before the tuning modules' import; the dev box reads that as `EventNow` with the flag, else as a StepError naming the stale stop file. `reboot-prepare` and `handover-s1a` refuse while an intent is live. SIGTERM and SIGHUP end both scripts through `SystemExit` (`exit_on_signals`, set at their entry points, not in `main()`), so the clean-up runs. Setup, tuning-setup, wpt-install and inventory have no intent: they add files, tasks or tools and change nothing the event depends on. Settle bound: an in-flight apply can keep the preempt past `iempc`'s `SPIKE_SHARE_S`, which then refuses its iemmode call (REAPER is back by then; `spike_window.py status` shows the `settling` record). The one deliberate lock over a PC call is the overtaken trace start's stop (m4, bounded by `TRACE_STOP_CALL_S`): a preempt may wait for it before its bring-back.

- **StrictMode 5.1 array idiom (PowerShell).** Under `Set-StrictMode -Version Latest` on Windows PowerShell 5.1, a helper that returns 0 or 1 rows unrolls to `$null` / a scalar, so a later `.Count` or index throws. Wrap a row-returning helper's result with the repo's `,@()` / `@(...)` pattern (see `Test-SpikePc` / `Test-IemTuning`), and build an empty typed array as `[uint32[]]$ids = @()` — an `$ids = if (...) { [uint32[]]@() }` unrolls the empty array to `$null`, and `IemCpuSets.Set` then hits `ids.Length` on null → `NullReferenceException` on the mode-EXIT (CPU-set clear / REAPER-restore) path.

- **IemTuning/IemMeasure invariants (#32 A1–A14 and its review round).**
  - Registry undo writes back the journal's stored value KIND and data, never the item's declared type; a journal entry without a stored value is refused, not guessed.
  - Registry deletes go through `Remove-IemRegValue` (`RegistryKey.DeleteValue`, one literal name), never `Remove-ItemProperty -Name`, which treats the NDIS `*` keywords as wildcards.
  - Native programs go through `Invoke-IemNative` (stderr captured as output, only the exit code decides), never `& exe 2>&1` under `$ErrorActionPreference='Stop'`. `Invoke-IemXperf` verifies xperf's Microsoft signature and minimum version once per process.
  - Event-log queries go through `Get-IemWinEvent`: only "no events found" is empty, any other error throws; never `-ErrorAction SilentlyContinue`.
  - Boots are compared with `Test-IemSameBoot`: a random GUID token in the VOLATILE boot key (gone at every reboot; a non-volatile key is refused), equal tokens = one boot, the time is information only (review R1). The token is read and created under the `Global\iemmixer-boot-token` mutex (waited ≤ 30 s, an abandoned one is taken over), so two first callers after a boot never write two tokens (#32 MINOR-3). It needs no DACL of its own: when full access to an existing mutex is refused, the .NET Framework `Mutex` constructor opens it with `MUTEX_MODIFY_STATE | SYNCHRONIZE` (reference source `mutex.cs`, `CreateMutexHandle`), which every elevated caller and SYSTEM get from the creator's default DACL. Apply and enter need the boot (they throw on a boot-key problem); undo and the state never do (#32 MINOR-4): `Get-IemBootIdentityOrUnknown` gives an identity without a token plus `problem` — never this boot, so nothing reads as pending on it — undo records the revert's boot that way and returns a `problem` row (`cmd_undo` alarms on it), `Get-IemTuningState` returns `boot_problem` (reboot-prepare alarms on it, post-boot fails its checks: an empty pending list proves nothing without a token).
  - **One profile rule for processors, on both sides (#32 MINOR-6, MAJOR-2 and its review).** A processor number is an integer 0..63 (`ConvertTo-IemLpNumber` / `lp_number`); a list (`ConvertTo-IemLpList` / `lp_list`) refuses an entry that is none — null, float (2.0 too), bool, string, nested list — never dropped, rounded (`[int]1.6` = 2) or truncated (`int(1.6)` = 1). The layout (`Assert-IemLayout` / `check_layout`): an object; a role absent (none) or a list, never null or a scalar; one role per processor. A device's `lps` (`Get-IemDeviceLps` / `check_devices`): a non-empty list (missing/null/empty = "no processors"). `nic.rss` base and max (`Assert-IemNicRss` / `check_rss`): numbers, base <= max; where the range lies against the layout and the present processors only the PC checks. `load_profile` refuses every processor SHAPE the PC refuses, so the state step's device mask and RSS read never throw on a profile tuning-setup copied; relations (a card's `lps` against `layout.card`, a device on a card or audio processor, processors that are not present) and the profile's other fields are checked only on the PC (before any write, or by the state step itself). `scripts/pc-tuning/profile_cases.json` (tables `numbers`, `layouts`, `device_lps`) is the shared table both self-tests run — add a case there, never to one side only. Integers arrive as Int32 on Windows PowerShell 5.1 and Int64 on pwsh 7 (both accepted), a JSON float as Decimal/Double; Python needs `type(x) is int` (a bool is an int subclass). `Get-IemDeviceLps` is the ONE list the check and the affinity mask read; the placement reads `Get-IemLayoutLps housekeeping` and refuses a processor missing from the CPU Set map (it would join as ID 0).
  - **The RSS rule (#32 MINOR-5, spec §6.1/§6.4 R2).** `nic.rss.base` is a `layout.nic` processor; past `layout.nic` the range may reach only processors of NO role (the spec's NIC LP 4 with RSS 4–5, LP 5 its unplaced sibling), never a card, audio or housekeeping processor; each present.
  - **Self-test profiles go through `ConvertTo-Json` on 5.1:** a double `1.0` is written as `1` and reads back as an integer, so a non-integer case built with `New-TestProfile` uses `2.5` or a string; integral floats (`2.0`) live only in `profile_cases.json`, read straight with `ConvertFrom-Json`. The trace tests' run folders live under `$env:ProgramData` (removed in `finally`): the runner's temp path can hold an 8.3 name (`RUNNER~1`) that ETW might report in its long form.
  - Plan values are only ever written into the plan named `iemmixer` (it refuses `plan.source`, the built-in schemes and any foreign plan, checked before any write; the name is set with `/changename` after `/duplicatescheme`).
  - Mode order: enter pauses the governor first; exit reverts the plan and restores the governor last. The iemmixer power plan stays defined but inactive after exit; it is never journaled or deleted.
  - The card's IRQ affinity (R1) is applied only when the card's MSI is flagged (`MSISupported = 1`) AND granted (`Win32_PnPAllocatedResource`); otherwise the row is `skipped` and nothing is written.
  - The NIC driver key must match the profile's `nic.hwid` (exact `MatchingDeviceId`), looked up under `registry_root`, before any write.
  - The applied version is stamped per tier, only after a complete, clean apply (state reports `drift_tiers`); an `-Only` name that is not a group of the tier is an error.
  - The journal (schema 2; a schema-1 journal is converted only where exact, else refused naming the file) is written through to disk and swapped with `File.Replace`; a missing, empty or unreadable journal falls back to a complete `.tmp`, else it is refused.
  - The read-only fingerprint and inventory functions live in `IemMeasure.psm1`; `Export-IemNearGlitch` takes `-Name`; `Get-IemPollSample` is gone (the poll is `poll_body`, below).
  - Rows may carry `skipped` (apply) and `reactivated` (enter); `cmd_apply`/`cmd_enter`/`cmd_undo` fail only on `failed`.
  - `Exit-IemTuningMode` reports a schema-1 journal's global-section entry it cannot convert as a row with action `problem` and still completes the exit. `cmd_exit` and the unwind's tuning-exit step pass the rows to `sw.alarm_exit_problems`, which names each such row (key and error) in an owner alarm; the exit stays successful (`tuning_mode` cleared, REAPER still comes back).

- **Nothing is force-ended (I8) — the reboot stays graceful.** `cmd_reboot` sends `REBOOT_REQUEST`: `shutdown.exe /r /t 0 /d p:2:4` (immediate, planned: OS reconfiguration) WITHOUT `/f`. Microsoft's `shutdown` docs: "If the timeout period is greater than 0, the /f parameter is implied" — so ANY `/t` above 0 is a forced restart (the first version's `/t 60` was one, #32 B1). Program-spec invariant I8 (`guard.md`): nothing is ever force-killed — services stop gracefully, processes are never ended, reboots are graceful. The request starts the restart at once, so its answer may be lost: `sw.NoReply` (the ssh session ended after the command was sent, the call outlived its bound, no complete JSON reply) is reported as "the PC may be restarting; run post-boot" — but ssh's exit 255 with a pre-session line (`SSH_NOT_CONNECTED`, whole lines only, F2 round 3 m8: `ssh: connect to host <h> port <n>: …` (refused, timed out, no route, network unreachable), `ssh: Could not resolve hostname <h>: …`, `<dest>: Permission denied (<methods>)`, `Host key verification failed.`) is a plain `StepError`, nothing was sent (review round 3, m7); the same words anywhere else (the network dropping mid-call, a remote program's error) are `NoReply` — while an error REPLY (a plain `StepError`, `PC step failed: …`) means nothing restarted (review m9). Without the force an app may veto the restart; post-boot then reports "the PC did not reboot after the request" and the blocking app is resolved in the physical owner-at-PC window (Task 16), never with a force. `scripts/check_integrity.py` bans every force-end verb (FORCE_KILL) and every restart (F2 round 3 m9, decision 3) EVERYWHERE, comments included, across `crates/**`, `e2e/**`, `scripts/**`, `.github/**` (CODE_SUFFIXES). Reading a restart's arguments was given up (non-literal flags, `EWX_REBOOT | 0x4`, `InitiateShutdownW(.., 0x5, 0)`, `Command::new("shutdown")` with its flags in the next statement, a multi-line `-ArgumentList`, an argv with the flag on a continuation line all slipped through): `restart_lines` reports ANY restart mechanism (`RESTART_MECHANISMS`: `shutdown.exe` in any form, a `shutdown` command line with a switch other than `/a`, `shutdown $args`, `& shutdown`, `Start-Process`/`-FilePath shutdown`, `Command::new("shutdown")`, a Python/JS/.NET process API or an argv list starting with `"shutdown"` (`RESTART_ARGV` also across two lines), `Restart-`/`Stop-Computer`, `Win32Shutdown(Tracker)`, `.Reboot(`, WMI/wmic reboot, `InitiateShutdown*`, `InitiateSystemShutdown*`, `ExitWindows(Ex)`, `Nt/ZwShutdownSystem`, the `EWX_*` and `SHUTDOWN_*` flags) unless its line carries `RESTART_MARKER` (`iemmixer:graceful-restart`) AND every mechanism on it lies inside `RESTART_SAFE`: `& shutdown.exe /r /t 0 [/d p:x:y] [/c '<literal text>']`, the command ending right there (`;`, a comment or the line's end — never a quote, which may open one more argument or close a string another is joined to; review of lane G2, finding 4). `psshutdown(64)` and `Start-Process` with parameters before the program are mechanisms too. The one marked line is `tuning_window.REBOOT_REQUEST`; another graceful form needs its own safe form and test before its first caller. Protocol words (`"shutdown"` as a command name, `Cmd::Shutdown`, `graceful_shutdown`) are no mechanism. A test that checks the reboot request compares the program without spelling `shutdown.exe` (the scan reads test files too). So in any tuning/spike code or comment write "force-end" and "the restart request" in prose and never a kill verb or a restart spelled out. (`.md` rules like this one are not scanned.)

- **`reboot-prepare` prepares a reboot only over a cleanly preempted window (I1).** `sw.unwind(..., bring_back_reaper=False)` runs the safe unwind order (`stop-spike → trace-stop → tuning-exit → restore-buffer`) and stops at `bring-back`. A spike not confirmed gone after `stop-spike` (60 s) may still hold the driver, so `unwind` — with or without the bring-back — still runs trace-stop and tuning-exit (neither touches the driver) but alarms the owner and raises BEFORE `restore-buffer` and `bring-back` (#32 B10: the buffer is never written under a possibly open driver, which `set-buffer` also refuses); the card stays free and the window open, so no reboot is prepared over a held card. `unwind` only alarms and carries on past a failed trace-stop or tuning-exit (so REAPER still comes back on "ide event"), so `cmd_reboot_prepare` also REFUSES when any returned step failed (`unwind_failures`: an `error` entry, or `stop-spike` false; #32 B4) — a trace left running or a mode lever not reverted would carry into the reboot. The spike is never force-ended (I8); the owner waits for it or pre-empts in a dev window. It also refuses while a PC change is in flight (a live intent). Its read-only calls (the tuning state, which compiles IemTuning, and the PC time) run after the unwind, OUTSIDE the lock and `event="abandon"`, and the `rebooting` write is one `update_state(change=)` that refuses a window a preempt closed or whose card was taken meanwhile (F2 round 3, m3), and a step begun in that gap: a live intent, a touched buffer not verified as restored, a mode recorded as entered (review of lane G2, finding 3). It refuses without a boot token (owner alarm; post-boot could never confirm the reboot; finding 7) and records the tuning state's `boot_token` with the reboot: post-boot tells a reboot by that token against the one `Get-IemTuningState` reads after it (`boot_changed`: equal = the same boot, `Test-IemSameBoot`'s rule), never by `Get-IemBootTime` (a clock change moves it; decision 5); a token missing on either side is "whether the PC rebooted cannot be told (<why>)", never "did not reboot". `undo_plan` treats `rebooting` as card-away like `switching`/`free` (#32 B3): an "ide event" (preempt) or `to-event` on a prepared window runs stop-spike and bring-back, and the window closes only once REAPER is back. The prepare's verified buffer restore (`pref_restored`) is not written again in that state — after the reboot REAPER may already hold the driver — and the bring-back reads the value and refuses unless it is the original. After the reboot, `post-boot` always runs the bring-back (it starts REAPER through the start task when REAPER did not start by itself — still reported as a problem, a reboot must come back in event mode) and closes the window only when the bring-back's handover checks passed (#32 B13), then removes the spike's stop file reboot-prepare's unwind left (`sw.clear_stop`); a failed bring-back keeps the window open as `rebooting` so `to-event`/preempt brings REAPER back later. post-boot checks the "ide event" flag on every autostart poll and every second between polls (`nap_unless_event`, never a 10 s sleep): on it, the bring-back runs at once, the read-only checks are skipped and `EventNow` goes to main (review m10, round 3 m4); it says "REAPER brought back" only when the bring-back succeeded.

- **xperf `-a dpcisr` prints per-CPU usage as TABLES (#32 B8).** Per section: the whole-trace table (header `CPU n Usage, …`, a units row ending `Module`, rows = one `usec %` cell per CPU then the module name; `"Unknown"` keeps its quotes, as in its `Total = N for module "Unknown"` histogram), the module histograms, the 1-second interval table (a label column, spaces before the commas) and the distribution table (bare `CPU n` columns, three cells each). `latency_report.parse_dpcisr` maps columns to CPU numbers and rows to modules, passes over the two bucket tables, and RAISES `ValueError` when a histogram module has no usage row or when no DPC module is read at all (an empty or foreign text, an unknown section header — a traced Windows run always has DPCs; a trailing colon on `DPC Info:` is read, review M2) — the first parser expected a made-up `(… CPU n usage)` line, read no usage from a real 90 s trace and so the watched-CPU budget passed unchecked (fail-open). A module "runs on" a CPU when its usec there is > 0. Fixtures are hand-written in the real layout with synthetic module names only (`DPCISR_XPERF`; the real trace names a private driver, P6), and the parse errors carry counts and line numbers, never a module name (an error text is what gets pasted into a public ticket).

- **Trace stop: ownership, order, stop-only import (#32 MAJOR-1, MINOR-1, MINOR-2, F2 round 3 item 4).** Every stop — the unwind's `trace-stop` (preempt at "ide event", to-event, reboot-prepare), `tuning_window trace-stop`, a failed measure's `abandon_trace`, a cut, the final stop, an overtaken start — sends `sw.trace_stop_body(env, run_dir)`: IemMeasure imported with `-ArgumentList 'stop-only'` (IemTuning never loads: no Add-Type compile, no TEMP set up, no `PC_TUNING_ROOT`/`PC_XPERF` needed) and `Stop-IemTraceSessions -Dir <run folder> -TimeoutSeconds 20`. Never route a stop through `tuning_body`/`tps`. Ownership is a property of the session: the NT Kernel Logger is ours exactly when `logman query "NT Kernel Logger" -ets` names an output file under `-Dir` (any line holding `<Dir>\`, case-insensitive — the field labels are localized, never key on "Output Location"); IemMarkers is ours by name; whether IemMarkers runs proves NOTHING (xperf -on may start only the kernel logger, a partial stop may leave it alone). `-Dir` goes through `ConvertTo-TraceDir` on BOTH sides — `Start-IemTrace` (where xperf's `-f` comes from) and every stop: it must start with a drive, is folded by `GetFullPath` (doubled or forward separators, `.`/`..`; never rely on ETW folding a path, so the start must fold too) and must still be `X:\folder` afterwards (a root or relative path would make every trace ours). Never compare a raw caller path with logman's output. The kernel logger is stopped first, IemMarkers after it, each on its own; any error, logman output not read within 5 s of its exit (`Invoke-LogmanRun`), or a kernel logger that runs but is not ours (`kept`) fails the call, naming them and what did stop. Nothing running = success (idempotent). A session that ended between two logman calls is gone, never an error: logman exits `PLA_E_DCS_NOT_FOUND` (0x80300002, `$script:SessionNotFound`) on the kernel logger's detail query (it was listed a moment before — CI run 37464797322: a hosted runner's own kernel logger) or on a stop; the reply lists such a stop under `gone`. The session LIST (`query -ets`) is only a shortcut: when it fails (CI run 37465635726: 0x80071068, the WMI GUID not found, while another tool's session ended during the list) both sessions are queried and stopped on their own and the list's error goes to `notes`, never to the errors — each session's own query and stop decide. Every other logman failure stays an error. `Invoke-LogmanRun` returns the exit `code` for this; key on the code, never on logman's localized text. (`Stop-IemTrace`, with or without `-Merge`, is gone: it had no caller.) On the dev box `sw.check_trace_stop` accepts only a reply with `stopped` a list and `kept == []`; any other reply or error keeps `state["trace"]` recorded and alarms (trace-stop or the next preempt retries). The bound: four logman calls × (`TRACE_STOP_LOGMAN_S` 20 + 5 s read) + start ≤ `TRACE_STOP_CALL_S` 120 (a test pins it); a new logman call in the stop moves both.

- **measure / hwlat (#32 B5–B7, B11, C1, C2).**
  - **No kernel trace left behind (B5).** `state["trace"]` is recorded before `Start-IemTrace`; any error inside `_measure` (the start, the run, a cut, the stop or the analysis) runs `abandon_trace` — a quick stop (`trace_stop_body`, no merge; the raw files stay on the PC) that clears the state once confirmed; a stop that fails or is not confirmed keeps it recorded with an owner alarm, and the measure's own error is re-raised. `EventNow` is re-raised untouched and `abandon_trace` does nothing while the flag exists: the preempt's unwind (`trace-stop`) stops the trace, so nothing delays REAPER (review m5). `clear_trace()` reloads the state right before saving and changes only `trace` — a preempt in another process (`iempc.py event`) may have saved `closed`/`card`/`pref_restored` meanwhile; the measurement row is added the same way. `measure` and `hwlat` refuse while a trace is recorded; `tuning_window trace-stop` stops it with `event="finish"` like every window command (review m4). Every start goes through `start_trace`: a start the "ide event" overtook (its call ended in `EventNow`, or the flag is there right after) may have finished after a preempt's trace-stop found no session, so the measure stops it itself (quick, no merge) before `EventNow` goes on (review round 3, m5) — under the window lock, so never at the same time as the unwind's own trace-stop, whose logman stop would then fail (a false alarm, `trace` kept); `Stop-IemTraceSessions` is idempotent, whichever comes second stops nothing, and a confirmed stop clears `trace` if it is still that run's (F2 round 3, m4).
  - **Stop quick, merge and analyse abandonably (B6, review M1).** Every stop is the plain logman stop (`trace_stop_body`, never `-Merge`: a merging stop is one `xperf -stop … -d` call, so a preempt would wait for the merge) in its own short `event="finish"` call; `state["trace"]` is cleared right after the final one. The plain stop needs no xperf and no signature check (xperf itself was verified when the trace started) and serves ALL stops — the final one, every cut's and the unwind's (review round 3, m9). The merges (`merge()`: `Invoke-IemXperf -merge <base>kernel.etl <base>markers.etl <trace>.etl`, the files present, then a check that the merged `.etl` exists and is not empty (else a throw naming it), then `Remove-Item` of those raw files — only reached when the merge succeeded and wrote its trace, a failed or empty merge throws and keeps them; review m8, F2 round 3 m10) and the xperf analysis never compete with an event (decision B of the #32 review): `analysis()` yields one step at a time (per trace: merge, dpcisr, near-glitch for diag), each its own `event="abandon"` call, issued only while the flag is absent (`check_event`), and composed by `analysis_step(root, since, body)`: `analysis_guard` FIRST, then `sw.measure_import` (IemMeasure, which loads IemTuning: an Add-Type compile), then the step (F2 round 3, m6) — the PowerShell sets itself to Idle priority (the import and the xperf it starts inherit it) and throws `ide event: the analysis step did not start` when the spike's stop file was written after the analysis began (the final stop returns the PC's `Get-IemNow`; every preempt writes the stop file first), which the dev box turns into `EventNow`; a refused step compiles nothing. Residual after the flag: at most the one step already running goes on, at Idle, and ends by itself. The guard runs for real on Windows PowerShell 5.1 (m11): `tuning_window.py analysis-script --root <dir with bin> --since <iso> --sums <the bundle's SHA256SUMS>` prints `analysis_step` with `ANALYSIS_PROBE` as the body through `sw.ps_script`, and the asio-spike job's "Analysis guard runs as on the PC" step pipes it into `powershell -Command -` with no stop file, an older one (both start at Idle with IemMeasure and IemTuning loaded — the probe asks for an IemTuning function: IemMeasure keeps a failed IemTuning load to itself) and a newer one (refused with exactly `ANALYSIS_REFUSED` through ps_script's catch). "Before the import" means before the tuning modules' import: `ps_script` itself imports SpikePc and GoldenPc first, which compile nothing. Change `analysis_guard` or `analysis_step` only with that step green. Locally, pwsh 7 runs the same script with real `bin`/`queue` folders and `$env:SystemRoot` set (IemMeasure joins logman's path to it).
  - **Cuts (B7, review M1).** A cut stops the trace, sets its raw files aside as `cut-N.kernel.etl`/`cut-N.markers.etl` (`set_aside()`, same call), checks the flag and only then restarts with the SAME `trace_options` (`-CSwitch` for `--trace diag`) — no kernel trace ever starts once "ide event" came. `analysis()` merges and analyses every trace — the final one and each `cut-N.etl`, which holds the glitch that caused it — dpcisr always and, for diag, the near-glitch view (`Export-IemNearGlitch -Name 'cut-N.etl'` → `cut-N.near.txt`, the `Invoke-IemDpcIsr` naming); the summary lists `cuts` as `{cut, findings[, near_glitch]}`.
  - **Downloads and parses give way (review M3).** The analysis files are fetched with `sw.scp(..., event="abandon")` (the flag is polled every `POLL_S`; on it the local scp gets Ctrl-C — SIGINT, on which scp closes its ssh session and exits by itself; scp starts with SIGINT's default action (`preexec_fn=sigint_default`), since an ignored SIGINT would be inherited and the interrupt then lost (review round 3, m3) — the partial file is removed and `EventNow` raised; nothing is ended harder, and any copy past `SCP_BOUND_S` is interrupted the same way). `check_event()` runs before every copy and parse, and near dumps are parsed from their files in two streamed passes (`lr.near_glitch(path, check=check_event)`), never read whole.
  - **A light sentinel poll (B11).** The 10 s poll during a run (`poll_body`) goes through `sw.ps`, NEVER `tps`: importing IemMeasure/IemTuning runs `Add-Type` (a C# compile) in every new PowerShell on the PC being measured. It reads one raw WMI counter class (Get-IemCpuSample's fields), the plan from `powercfg /getactivescheme`, the governor named in the local profile and the callback thread's priority; the residual load is one ssh + PowerShell start with the SpikePc import per 10 s, like the status poll. Keep new per-poll work out of the tuning modules. A plan powercfg cannot give is an error, never a guess (review m11). The poll is PowerShell composed in Python, so the asio-spike CI job runs it for real: `tuning_window.py poll-script --root <dir with bin\SpikePc.psm1> --governor … --pid … --tid … --sums <the bundle's SHA256SUMS>` prints exactly what `sw.ps` sends (`sw.ps_script`), and the step pipes it into Windows PowerShell 5.1 with the bundle as `bin` and checks the sample's shape. Change the poll body only with that step green.
  - **Stress and failed runs (C1, C2).** `--stress` threads run on the profile's housekeeping CPUs minus any `--audio-cpus` unless `--stress-cpus` says otherwise; the spike and `check_request` refuse stress next to `--audio-cpus` without `--stress-cpus`, and ANY overlap of the two lists, with or without busy threads (review m12). A spike run whose outcome is `error` (a stress thread, the hwlat scanner or the power-throttling lever not set; every mode) fails the step in `cmd_run` — never a measurement; `hwlat_summary` also marks a row `failed` unless it ended `done`, `placed` (a list) and `time-critical`, and `cmd_hwlat` writes its rows after every CPU. `measure` accepts only `MEASURED` outcomes (`done`, or `stopped` by the stop file): `refused`, `fault-caught`, `rate-changed` and `stop-hung` fail the step with the outcome and exit code named, are recorded in `measurements` as a `failed` row with no summary, and are never analysed. `cmd_run` itself keeps returning them to its other callers (probe/reopen/fault modes, where e.g. `fault-caught` is the expected result). An unreadable dpcisr fails measure as a `StepError` naming the raw file (B8).

- **Tuning commands fail loud (I2, script-failure-policy).** A command that applies OR reverts profile items raises on any `Undo-IemTuning`/`Invoke-IemTuningApply` row with `action=="failed"` — `cmd_undo` mirrors `cmd_apply` here. `post_boot_verdict`'s `failed_items` cannot catch an un-reverted lever (a failed revert stays journaled but still matches its tuned value → counts `ok`), so a silent exit 0 would hide a global lever left applied. Never swallow a failed row.
