# PC tuning window (S1c, #15)

`scripts/pc-tuning/tuning_window.py` drives the PowerShell tuning/measure modules (`IemTuning.psm1`, `IemMeasure.psm1`) over ssh, on top of `spike_window.py`'s window, state, "ide event" guard and unwind. `latency_report.py` analyses the collected data. A window opens only through `spike_window.py new --signal`; every command checks the "ide event" flag and pre-empts like the spike window. Site values (driver/registry/task names, channel numbers, handover values, the tuning profile) come ONLY from the private `$SPIKE_ENV` (`~/.config/iemmixer/asio-spike.env`) and `$TUNING_PROFILE` (`~/.config/iemmixer/pc-tuning.json`) at run time; they and the runbooks live in the private ops repo, never here (P6). Tests use synthetic values (inputs 101–124, synthetic GUIDs, layout housekeeping/card/nic/audio).

- **Load-bearing import order.** `tuning_window`'s `from golden_window import StepError, ps_quote` resolves ONLY because `import spike_window` runs first and, as an import side effect, inserts `scripts/golden` on `sys.path`. Keep the `sys.path.insert(... "asio-spike")` + `import spike_window as sw` lines BEFORE the `from golden_window import ...` line (tuning_window.py top). Reordering them breaks the import on a clean interpreter.

- **`BUNDLE_FILES` ↔ everything derived from it.** When `spike_window.BUNDLE_FILES` changes (it grew 4 → 6 to add `IemTuning.psm1`/`IemMeasure.psm1`), EVERYTHING derived from the count must move in the SAME push: `verify_bundle` (exact `sorted(BUNDLE_FILES)` match), `preflight_problems`' file count, EVERY test fixture that simulates a healthy bundle (`PreflightTests.GOOD`, `DevTimeWindowTests` `files:`), AND the asio-spike CI `Bundle` `Copy-Item` list. A drift makes the dev-box `fetch-bundle` reject every artifact — and CI stays GREEN either way (the CI bundle step does not check `BUNDLE_FILES`), so the hazard is invisible in CI. Add the module to `BUNDLE_FILES`, the CI Copy-Item, and the fixtures together.

- **StrictMode 5.1 array idiom (PowerShell).** Under `Set-StrictMode -Version Latest` on Windows PowerShell 5.1, a helper that returns 0 or 1 rows unrolls to `$null` / a scalar, so a later `.Count` or index throws. Wrap a row-returning helper's result with the repo's `,@()` / `@(...)` pattern (see `Test-SpikePc` / `Test-IemTuning`), and build an empty typed array as `[uint32[]]$ids = @()` — an `$ids = if (...) { [uint32[]]@() }` unrolls the empty array to `$null`, and `IemCpuSets.Set` then hits `ids.Length` on null → `NullReferenceException` on the mode-EXIT (CPU-set clear / REAPER-restore) path.

- **IemTuning/IemMeasure invariants (#32 A1–A14).**
  - Registry undo writes back the journal's stored value KIND and data, never the item's declared type; a journal entry without a stored value is refused, not guessed.
  - Registry deletes go through `Remove-IemRegValue` (`RegistryKey.DeleteValue`, one literal name), never `Remove-ItemProperty -Name`, which treats the NDIS `*` keywords as wildcards.
  - Native programs go through `Invoke-IemNative` (stderr captured as output, only the exit code decides), never `& exe 2>&1` under `$ErrorActionPreference='Stop'`.
  - Event-log queries go through `Get-IemWinEvent`: only "no events found" is empty, any other error throws; never `-ErrorAction SilentlyContinue`.
  - Boot comparisons use `Test-IemSameBoot` (300 s tolerance against clock steps).
  - Mode order: enter pauses the governor first; exit reverts the plan and restores the governor last. The iemmixer power plan stays defined but inactive after exit; it is never journaled or deleted.
  - The card's IRQ affinity (R1) is applied only when the card already uses MSI (`MSISupported = 1`); otherwise the row is `skipped` and nothing is written.
  - The NIC driver key must match the profile's `nic.hwid` (`MatchingDeviceId` prefix), looked up under `registry_root`, before any write.
  - The profile version is stamped only after a complete, clean apply; an `-Only` name that is not a group of the tier is an error.
  - The journal is written through to disk and swapped with `File.Replace`; a missing, empty or unreadable journal falls back to a complete `.tmp`, else it is refused.
  - Rows may carry `skipped` (apply) and `reactivated` (enter); `cmd_apply`/`cmd_enter`/`cmd_undo` fail only on `failed`.

- **reject-case shadowing (tests)** — the spike's `--activity-channels` case is in `asio-spike.md` (it loads alongside this rule on `scripts/asio-spike/**`).

- **Nothing is force-ended (I8) — the reboot stays graceful.** `cmd_reboot` sends `REBOOT_REQUEST`: `shutdown.exe /r /t 0 /d p:2:4` (immediate, planned: OS reconfiguration) WITHOUT `/f`. Microsoft's `shutdown` docs: "If the timeout period is greater than 0, the /f parameter is implied" — so ANY `/t` above 0 is a forced restart (the first version's `/t 60` was one, #32 B1). Program-spec invariant I8 (`guard.md`): nothing is ever force-killed — services stop gracefully, processes are never ended, reboots are graceful. Without the force an app may veto the restart; post-boot then reports "the PC did not reboot after the request" and the blocking app is resolved in the physical owner-at-PC window (Task 16), never with a force. `scripts/check_integrity.py`'s FORCE_KILL scan bans a `shutdown` line carrying `/f`/`-f` anywhere or a `/t` above 0, `Restart-Computer`/`Stop-Computer -Force`, and every force-end verb EVERYWHERE, comments included, across `crates/**`, `e2e/**`, `scripts/**`, `.github/**` (CODE_SUFFIXES) — so in any tuning/spike code or comment write "force-end" in prose and never a kill verb, a force flag or a restart delay on a `shutdown` line. (`.md` rules like this one are not scanned.)

- **`reboot-prepare` prepares a reboot only over a cleanly preempted window (I1).** `sw.unwind(..., bring_back_reaper=False)` runs the safe unwind order (`stop-spike → trace-stop → tuning-exit → restore-buffer`) and stops at `bring-back`. A spike not confirmed gone after `stop-spike` (60 s) may still hold the driver, so `unwind` — with or without the bring-back — still runs trace-stop and tuning-exit (neither touches the driver) but alarms the owner and raises BEFORE `restore-buffer` and `bring-back` (#32 B10: the buffer is never written under a possibly open driver, which `set-buffer` also refuses); the card stays free and the window open, so no reboot is prepared over a held card. `unwind` only alarms and carries on past a failed trace-stop or tuning-exit (so REAPER still comes back on "ide event"), so `cmd_reboot_prepare` also REFUSES when any returned step failed (`unwind_failures`: an `error` entry, or `stop-spike` false; #32 B4) — a trace left running or a mode lever not reverted would carry into the reboot. The spike is never force-ended (I8); the owner waits for it or pre-empts in a dev window. `undo_plan` treats `rebooting` as card-away like `switching`/`free` (#32 B3): an "ide event" (preempt) or `to-event` on a prepared window runs stop-spike and bring-back, and the window closes only once REAPER is back. The prepare's verified buffer restore (`pref_restored`) is not written again in that state — after the reboot REAPER may already hold the driver — and the bring-back reads the value and refuses unless it is the original. After the reboot, `post-boot` always runs the bring-back (it starts REAPER through the start task when REAPER did not start by itself — still reported as a problem, a reboot must come back in event mode) and closes the window only when the bring-back's handover checks passed (#32 B13); a failed bring-back keeps the window open as `rebooting` so `to-event`/preempt brings REAPER back later.

- **xperf `-a dpcisr` prints per-CPU usage as TABLES (#32 B8).** Per section: the whole-trace table (header `CPU n Usage, …`, a units row ending `Module`, rows = one `usec %` cell per CPU then the module name; `"Unknown"` keeps its quotes, as in its `Total = N for module "Unknown"` histogram), the module histograms, the 1-second interval table (a label column, spaces before the commas) and the distribution table (bare `CPU n` columns, three cells each). `latency_report.parse_dpcisr` maps columns to CPU numbers and rows to modules, passes over the two bucket tables, and RAISES `ValueError` when a histogram module has no usage row — the first parser expected a made-up `(… CPU n usage)` line, read no usage from a real 90 s trace and so the watched-CPU budget passed unchecked (fail-open). A module "runs on" a CPU when its usec there is > 0. Fixtures are hand-written in the real layout with synthetic module names only (`DPCISR_XPERF`; the real trace names a private driver, P6).

- **measure never leaves a kernel trace behind (#32 B5).** `state["trace"]` is recorded before `Start-IemTrace`; any error inside `_measure` (the start, the run, a cut, the stop or the analysis) runs `abandon_trace` — a quick `Stop-IemTrace` WITHOUT `-Merge` (the raw files stay on the PC) that clears the state; a stop that fails keeps it recorded with an owner alarm, and the measure's own error is re-raised. `EventNow` is re-raised untouched: the preempt's unwind (`trace-stop`) stops the trace, so nothing delays REAPER. `measure` and `hwlat` refuse while a trace is recorded; `tuning_window trace-stop` stops it. At the end of the run the stop-and-merge is its OWN `event="finish"` call (it changes the PC, so it completes), `state["trace"]` is cleared right after, and the xperf analysis (dpcisr per trace and cut, the near-glitch dump) runs in a separate `event="abandon"` call (#32 B6) — an "ide event" never waits for the analysis. A circular trace's cut restarts with the SAME `trace_options` as the start (`-CSwitch` for `--trace diag`), and `analysis()` gives every trace — the final one and each `cut-N.etl`, which holds the glitch that caused it — its dpcisr and, for diag, its near-glitch view (`Export-IemNearGlitch -Name 'cut-N.etl'` → `cut-N.near.txt`, the `Invoke-IemDpcIsr` naming); the summary lists `cuts` as `{cut, findings[, near_glitch]}` (#32 B7).

- **Tuning commands fail loud (I2, script-failure-policy).** A command that applies OR reverts profile items raises on any `Undo-IemTuning`/`Invoke-IemTuningApply` row with `action=="failed"` — `cmd_undo` mirrors `cmd_apply` here. `post_boot_verdict`'s `failed_items` cannot catch an un-reverted lever (a failed revert stays journaled but still matches its tuned value → counts `ok`), so a silent exit 0 would hide a global lever left applied. Never swallow a failed row.
