# `iempc roster-install` (#58 plan Task 14, design §9)

`iempc roster-install --file <ops>/site/roster.toml [--dry-run]` is how a roster reaches the IEM PC. The server polls `roster.toml` beside its config every 2 s and applies a valid change live (`.claude/rules/server-engine.md`, roster reload), so the tool only checks, places and follows the file. The module docstring of `iempc_roster.py` lists the steps; what is not obvious from the code:

- **Dev time, locked, a PC command** (`Spec(pc=True, dev_time=True, locked=True)`): the EVENT-NOW flag refuses it (design §9), a flag that appears during a call runs the event path (exit 10), and the flag is read again right before the install call, since `guarded` only notices a flag that predates a call at its end.
- **The check runs the active bundle's own server, admin-only.** `iemmode status` names the active bundle (`iempc_soak.active_bundle`); its `iem-server.exe` is read once from `bundles\<sha>`, checked by this box's fetch record and run from the admin-only stage (`iempc_bin.staged_program`, the #15 rule: the elevated ssh session runs only admin-only copies), with `IEMMIXER_CONFIG` = `PC_SERVER_CONFIG` (an optional key of the private env, a full `X:\…\file` path; refused without it). So a bundle not fetched on this box refuses (`iempc fetch-bundle --sha <active>`), and a bundle from before Part B answers exit 2 (no `roster check`). The check's answer is judged in Python (`check_result`): exit, `ok`, `problems` and the file's sha256 must agree.
- **Two ssh calls, not one:** the check (a read, abandoned by a new flag) and the install (a change, finished first). Each checks the upload's sha256 first; the install copies it to `roster.toml.new`, checks it, `Move-Item -Force` onto `roster.toml` and checks that. Windows PowerShell 5.1's forced move deletes the target first: for an instant there is no `roster.toml`, which the server reads as "gone, the roster in use stays" and reads again at its next poll.
- **What `roster.status.json` can say** (`roster_watch::Status`, `outcome`): `applied: true` is in use (exit 0; `ok: false` with `problems` = what failed after it went into use, an archive move); `applied: false` is refused (exit 1), its problems ending with "in use instead: the roster applied last" while the server runs on its fallback. The server writes **no** status for a Deferred roster (engine not synced, a switch a restart cut short: it reads again every 2 s), for the roster already in use, or while no server runs (the guard in event): the wait (`WAIT_S` 20 s, a read every `POLL_S`) ends "not applied within 20 s" naming what the status held (exit 1). The install call returns the status as it stood before the move (`before`): the same refusal again is an earlier refusal of the same bytes and is waited out; the same applied status is the roster already in use (`unchanged: true`, nothing added or removed).
- **Not during a soak or a live run of this dev entry** (`iempc_live.refuse_while_running`, `RUNNING["roster-install"]`; a dry run is not refused): a reload announces the band, which closes every person's mixer socket with 4003, the soak client's and the live run's included.
- **P6:** the output is ids and counts only (`added`/`removed` filtered to id characters, anything else `?`; the server's problems already name ids only). The file itself holds names: it lives in the private ops repo and on the PC, never here.
- Tests: `test_iempc_roster.py` on `iempc_test_support.Base` (`FakePc.replies` answer the check, `FakePc.texts` the install (`roster.toml.new`) and the status reads (`roster.status.json`), in that dict order since the install script also names the status file) and `RosterInstallGuardTests` (`test_iempc_live.RunningGuardCases`).
