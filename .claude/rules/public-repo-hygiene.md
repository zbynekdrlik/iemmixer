# Public-repo hygiene (program spec P6)

- This repository is public. Site data never enters it: band member names, host names, IPs, Dante device names and channel numbers, real track names, PINs, keys, tokens, user paths, the REAPER project name. Real values live only in the private `zbynekdrlik/iemmixer-ops`.
- Placeholders: `member1`…`member9` (MEMBER_1…MEMBER_9; `member1` = ELEVATED_MEMBER), `engineer`, TRANSLATOR; hosts `mixer.example.org`, LAN `http://10.0.0.10`; synthetic Dante numbers (member N = 69+2N/70+2N, i.e. 71–88; any other output 89/90; engineer 91/92; HIL's spare outputs 94/95; inputs 101–124); input names from program spec §3.1 where the code does not key on a REAPER-era name.
- **Every clone installs the pre-push hook** (S0 plan, Task 1 Step 9): gitleaks + `scripts/denylist_scan.py` with the private denylist `~/.config/iemmixer/denylist.txt` and `scripts/allowed-identities.txt`. CI repeats all three in the `secrets` job (`DENYLIST` secret). The denylist's non-credential terms are also kept in the ops repo; its credential entries only on the box and in the secret.
- **Scanner output never shows a term, a matched line or an address** — only a location and the entry number: `tree <path>:<line>: denylist entry N` (`tree <path>:run <N>: …` for a text run of binary content; `tree <path>!/<member>:<line>|run <N>: …` for a member of a container — a gzip / bzip2 / xz stream's one member is `<path>!/`, nested members `a.zip!/b.zip!/c.txt`, a tar in a gzip `b.tar.gz!/!/dir/note.txt`), `<sha> <path>: denylist entry N` (`<sha> <path>[!/<member>]:<line>|run <N>: …` for a changed blob git's line diff cannot show — binary, UTF-16, UTF-32, a container), `<sha> author|committer email is not an allowed identity`, a git-lfs finding (`tree <path>[:<line>]: git-lfs pointer|filter, …` / `<sha> <path>: …`), or a container finding (`tree <path>[!/<member>]: cannot be scanned: <why>` / `<sha> …`); open the local denylist to see entry N. Every finding line starts with a fixed word (`tree` or a commit's short SHA), never a raw path (a `::`-prefixed path would read as a CI workflow command), and a path component — of a file or of a container member's name — holding a term — in any reading, see below — **any non-ASCII character or any control character** is shown `[redacted]`: no set of readings can be proven complete, and printed in a reading the scanner lacks, the ASCII tail of a term would reach the public log (#32 E3: a cp1250 path printed its term with only the accented letter replaced; #32 review m5: the same for double-encoded UTF-8; review of lane G3: a term glued to an escape sequence that ends in a letter, ESC [ 2 J, matched nothing and was printed). Commit mode decodes git's C-quoting (`core.quotePath`) of a `+++` path and forces `core.quotePath=true`, and terms + text are NFC-normalized, so a term cannot leak or hide behind an octal escape, a trailing tab, an added `++ ` line misread as a header, or a decomposed diacritic (see `scripts/denylist_scan.py` docstring). Commit mode also (#29) scans every added/modified path via `git diff-tree` (so an empty or binary file, whose path the unified diff omits, is still checked), splits content lines on `\n` only (not `str.splitlines()`, which also breaks on CR/VT/FF/NEL/U+2028 and would drop the `+` prefix on a line's tail), and `unquote_c` keeps a malformed C-escape literal rather than crashing or dropping the bytes that follow — three DETECTION bypasses distinct from the #27 output-leak class.
- **The scanner's modules (#32 F5):** `scripts/denylist_scan.py` (the CLI, the terms and their spellings, `Scanner`, tree / commit mode, output) imports `denylist_readings.py` (the readings of decoded text, `Views`, `SEP`), `denylist_content.py` (units, batches, segments, embedded UTF-16 strings) and `denylist_containers.py` (the members of containers); stdlib only, run from `scripts/` so the siblings import. The tests: `test_denylist_scan.py` (modes, git, output), `test_denylist_readings.py`, `test_denylist_content.py`, sharing `denylist_test_support.ScanTestCase` (not a test module). The sources keep every non-ASCII or invisible character as an escape (backslash, `u`, four hex digits); an agent's file-edit tools turn such a typed escape into the character itself (#32 F5: it put a literal Greek question mark into a test), so write or change those lines through a small script that builds the backslash, and check the diff for literal invisible characters.
- **Editing the scanner — parity/gotcha notes (#29):** all three line splits (`scan_tree` blob, `scan_commits` diff, `--hash`) must use `.split("\n")` on **bytes-decoded** text. `--hash` reads the blob committed in HEAD (or `<rev>:<path>`) with `cat-file`, never the working-tree file (#32 F5 m8: an uncommitted edit, eol conversion, an encoding or a smudge filter diverged the key; `Path.read_text()` also translates CR/CRLF), and numbers its units with the same functions as both modes. An empty or binary added file produces **no `+++` diff header** (git emits `Binary files … differ` or nothing), so its path is enumerated via `git diff-tree --name-only -z --root ...` and deduped against the `+++` paths in `seen`. `git diff-tree -m --first-parent` is a **no-op on git 2.43** (`--first-parent` after `-m` is ignored → all-parents; use `--diff-merges=first-parent` if you truly want first-parent only) — the scanner deliberately keeps `-m` (all-parents = safe over-scan, never misses a path any merge parent introduces). `git show`, by contrast, DOES honour `-m --first-parent` (a merge's diff against its first parent) — the scanner now says `--diff-merges=first-parent` outright.
- **Local git state must not reshape what the scanner reads (#32 review, F5 m7):** every git call goes through `git()`, which passes `--no-replace-objects` (and `GIT_NO_REPLACE_OBJECTS`) and an empty `GIT_GRAFT_FILE`: a replace ref swapped a term-bearing blob for a clean one in `cat-file` / `ls-tree` / `show`, and a grafts file cut earlier commits out of `rev-list` (`--no-replace-objects` alone does not stop grafts). Commit mode refuses a shallow repository with a usage error: a shallow clone, or a `.git/shallow` written by hand, cuts the history like a graft (review of lane G3); CI checks out the whole history (`fetch-depth: 0`). The one parsed diff (`scan_commit_diff`'s `git show`) pins `--src-prefix=a/ --dst-prefix=b/` (else `diff.noprefix` prints `+++ b/x` for the path `b/x`, read as `x` — wrong allow key and location; `mnemonicPrefix`, and `srcPrefix`/`dstPrefix` from git 2.45, change prefixes too), `--no-relative` (`diff.relative` from a subdirectory hides every change outside it), `--diff-merges=first-parent` (`log.diffMerges=combined` empties a merge's diff for a file only one parent changed), `--root` (`log.showRoot=false` prints no diff for a root commit) and `--no-show-signature`, besides `--no-color --no-ext-diff --text --no-textconv --no-renames` and `-c core.quotePath=true`. The two `git show -s` metadata calls go through `METADATA` (`--encoding=UTF-8 --no-show-signature`): `i18n.logOutputEncoding` re-encodes message and emails (UTF-16's NULs crashed the identity split, ISO-8859-2 hid a term) and `log.showSignature` prints "No signature" into the author field of a signed commit. Any NEW parsed `git show`/`diff`/`log` call needs the same pins; `diff-tree` / `ls-tree --full-tree` / `cat-file` are plumbing and read no such config.
- **What the scanner reads (#32):** `.gitattributes` never hide content — tree mode reads each blob's bytes via `cat-file` (no attributes), commit mode diffs with `git show --text --no-textconv` (a `binary` / `-diff` attribute or a textconv driver would otherwise hide added lines). git-lfs does hide it (the repository holds only a pointer), so a pointer blob and any non-comment `.gitattributes` line setting `filter=lfs` is a finding in both modes (#32 review m9). Content is read as numbered **units** in **batches** (`denylist_content.py`), shared by tree mode, commit mode and `--hash` so allow keys stay in parity: text lines; UTF-32 / UTF-16 text (`wide_codec`: a BOM — UTF-32's `FF FE 00 00` before UTF-16's `FF FE` — or the NUL pattern of Latin text) as its decoded lines **and then its byte runs** (a binary may only look like wide text: quiet 16-bit PCM, a blob starting `FF FE` — #32 review m3/m4); other NUL content (binary) as text runs — byte runs without control characters plus embedded UTF-16 strings (Windows wide strings in an `.etl` / `.lnk`), one unit per string: its other-byte-order reading one byte later spells the same letters and is dropped (F5 m11), and they are read lazily (the little-endian spans as integer pairs, each string decoded when used), so ~600 000 of them in 4 MiB cost 4 MiB — numbered on as `run N`. Whole lines are batched up to `CHUNK` (256 KiB), byte runs of binary content up to twice that; a line, run or wide string longer than `CHUNK` is read in **segments** (F5 m9): steps of up to `max(CHUNK, 6 × overlap)` and at least half that, each segment reaching back at least the overlap (4 KiB, or 12 × the longest term — the longest one-character spelling is `%F0%9F%98%80`) before its step, its edges right after a space, tab, comma or semicolon where the content has one (no reading turns those into a word character, so an edge never makes a false word boundary — one right after a reference's `;` can at most add a false positive) and never inside a UTF-8 character; every segment carries the unit's key `\0sha256:<hex>` of the whole unit, so its allow key is the same in all three modes, and a match found in two overlapping segments is reported once. Random bytes form short words by chance (the f64 goldens hold 28 % of all 3-letter words), so in a binary run — and in an embedded UTF-16 string, review of lane G3 — a term under `MIN_BINARY_TERM` (5) characters counts only inside a run of `LONG_TEXT_RUN` (32) bytes of valid UTF-8 (see Known limits). In commit mode a changed blob that is not plain text, or is a container, is scanned whole, and a finding is kept only when its unit is absent from the old blob (read a batch at a time, the old container expanded only when a member is wanted).
- **Containers (#32 F5 m6, `denylist_containers.py`):** a zip-based file (zip, docx, xlsx, odt, jar …, also a zip appended to other content), a gzip / bzip2 / xz stream (concatenated streams joined) and a POSIX / GNU tar archive are expanded: each member is decompressed and read like a blob at `<path>!/<member>`, depth first, its name scanned like a path. Limits per blob, every level together (review of lane G3: per container, nested containers multiplied them), each a finding `cannot be scanned: <why>`, never a silent skip: a member over `MEMBER_LIMIT` (32 MiB); more than `EXPANSION_LIMIT` (128 MiB), or — past `RATIO_FLOOR` (1 MiB) — more than `RATIO_LIMIT` (20) times the blob's size decompressed from it; more than `MEMBER_COUNT_LIMIT` (10 000) members in it; containers nested more than `DEPTH_LIMIT` (4) deep; an encrypted member (general purpose flag bit 0 or 6), a broken member, a broken archive or stream. Once a blob-wide limit is reached nothing more of the blob is read. A stored or deflated zip member is read from its own compressed bytes to their end — zipfile stops at the declared size, which a crafted zip sets to 0 — and a directory entry carrying data is read like a file; concatenated streams are joined across NUL padding (xz's own, zeros between gzip members); bytes after the last stream are read raw with the blob. 7z, RAR, zstd, lzip, LZ4, cabinet, `.Z` and `ar` archives, a PDF with any stream (whatever its filter name is spelled as — `/Fil#74er`) or with binary content, and a PNG with a `zTXt` or compressed `iTXt` chunk are findings too. Text is never read as a container: a blob that is valid UTF-8 without a NUL byte is text even when it starts like a bzip2 stream or a magic-only archive, and the other checks are strict — gzip's method byte, the tar header checksum, a PDF only at offset 0, a zip found from its end record only when zipfile opens it. A container finding is allowlisted by the key of the whole blob (`--hash <path> blob`), so any change to the blob needs a new review. One member is in memory at a time: it costs up to twice its size while it is decompressed (zlib joins its output), its size while it is scanned, plus the containers above it when nested (three 4 MiB zip members: 2.4 × one member while expanded, was 3.4). The CPU a container blob costs is bounded by its expansion: at most 20 times its size past 1 MiB, 128 MiB, 10 000 members.
- **Readings (`denylist_readings.py`) and spellings (#32):** text is decoded **losslessly** (UTF-8, `surrogateescape`; `line_key` hashes the exact bytes, valid UTF-8 lines keep their keys) and matched in every **reading** (`Views`): escapes decoded — HTML named character references first (`&dcaron;`, `&shy;`, `&nbsp;`, HTML5's legacy ones without `;`; a dict lookup, `html.unescape` for a legacy prefix; so a double-escaped `&amp;#271;` decodes too — F5 m5), then `\uXXXX`, `\u{X}`, `\UXXXXXXXX`, XML / HTML `&#N;` / `&#xN;`, C / Rust / Python byte escapes `\xNN` / octal / `\0` / letter escapes, percent-encoding (an escape right before a term is also a word boundary, #32 review M1); double-encoded UTF-8 read back (`unmojibake`, a `CodePage` per reading: cp1250, and Latin-1 with cp1252 in one table — they differ only in 0x80-0x9F — with a byte a code page leaves undefined read as the C1 control Windows shows for it, F5 m3); a compact reading (`compact`: Unicode's whole Default_Ignorable_Code_Point set removed — soft hyphen, zero-width characters, LRM / RLM, bidi controls, variation selectors, invisible operators, tag characters, F5 m5 — and compatibility letters such as fullwidth ones in NFKC, with U+037E and U+1FEF, the two characters besides the Kelvin sign whose NFC form is ASCII, F5 m10); undecodable bytes re-read as cp1250, Latin-1, ISO-8859-2 and cp852 (only those bytes — re-reading valid UTF-8 is mojibake that splits words). git stores a non-UTF-8 commit message or name with those bytes converted as Latin-1 (`verify_utf8`), so commit metadata is also read back as cp1250, ISO-8859-2 and cp852 (F5 m4). Each entry is matched as written and in its **ASCII spelling** (`ascii_spelling`: NFKD, combining marks dropped, the letters NFKD keeps whole spelled out — ł l, đ d, ø o, ß ss, æ ae, œ oe, ı i, þ th — F5 MAJOR: a name loses its diacritics in a path, an e-mail address, an identifier or a host name), as a second ASCII term of the same entry. Between the words of a multi-word entry any run of whitespace (a no-break space, a tab, a line break) and batch separators match (F5 m1), so a term wrapped onto the next line of a batch, or of a commit message, is found — on the line it starts on, keyed by that line in every mode. Identity emails are read NUL-separated (`%ae%x00%ce%x00`), compared exactly (case aside, no `strip()`), and an email holding a line separator is never allowed (#32 E4: `splitlines()` let U+2028 push the committer email out of the check).
- **Editing the scanner — cost and false positives (#32):** the units of a batch are joined by `SEP` (U+E000, a non-word character): no reading may create or remove it (escape decoders, named references and `unmojibake` never produce it — a decoded U+E000 becomes U+FFFD), because a match maps to the unit it starts in by the SEPs before it; only the gap of a multi-word term crosses one. An ASCII term is matched only in the raw, escape-decoded, `unmojibake` and `compact` readings behind a case-fold `in` pre-filter on its longest word (`fold` covers re.IGNORECASE's extra matches İ ı ſ and the Kelvin sign, checked against every code point) — a re-reading or NFC can only remove an ASCII term's match; the NFC and re-read readings are built only for a term with a non-ASCII character whose longest ASCII word occurs. The stated budget (`test_a_large_binary_blob_stays_within_the_cpu_and_memory_budget`, #32 review m7): a 4 MiB blob of random bytes against 40 terms in under 1.0 s CPU per MiB and a peak under two copies of the blob plus 24 MiB (measured at F5: 0.36–0.45 s/MiB and 17 MiB; it was 65 s / ~1 GB for 20 MiB before m7). The same peak bound holds for one 4 MiB line and one 4 MiB binary run (`test_one_long_line_stays_within_the_memory_budget`, `…_binary_run_…`: 8 MiB measured, 60 MiB before F5 m9). A change to matching, decoding or unit extraction can also add false positives that only the PRIVATE denylist reveals (the public tests use synthetic terms): before handing off, run `python3 scripts/denylist_scan.py --denylist ~/.config/iemmixer/denylist.txt --allow scripts/denylist-allow.txt --identities scripts/allowed-identities.txt --tree HEAD --commits HEAD` — CI scans the full history the same way — and keep it clean (~40–50 s CPU, ~55 MiB for tree + history in 2026-10). A synthetic test term is always an invented word (`zyxname`, `ďqxwzy`), never an ordinary word or a real name — either could equal a private entry, and a pushed test line can never be taken back.
- **Known limits of the scanner (#32 F5, accepted and documented, not fixed):** (1) F5 m2: in binary content a term under 5 characters counts only inside a run of 32 bytes of valid UTF-8, so a short term — a 4-digit PIN — in legacy-encoded text (cp1250, Latin-1) inside a binary file, or in a short run, is not found. (2) An ASCII entry is not matched in a spelling with added diacritics (`zyxname` in `zýxname`); the ASCII spelling is made only from an entry written with them — so list a name with its diacritics. (3) The words of a multi-word entry joined by nothing, `_`, `-` or `.` (an identifier, a host, an e-mail address) are not matched — list those spellings too. (4) A multi-word entry split across two batches (every ~256 KiB of text, or two segments), across two hunks of a commit, or where commit mode sees only the added half of a wrapped line. (5) A spelling longer than the segment overlap (thousands of escapes or invisible characters between letters) that crosses a segment edge; and at a forced edge (no space, tab, comma or semicolon in the window: base64, a minified blob) a term may be reported at the edge where the whole word does not hold it — a false positive, never a miss. (6) A stored (uncompressed) zip member and a tar member are also read in the container's own bytes, so one hit there can be reported twice (two allow keys). (7) Compression inside other formats is read only as raw bytes: image pixels, audio, a PNG's `iCCP` profile, compressed ID3 frames, a bare zlib stream, an archive appended to anything but a zip. (8) A term glued to letters or digits (`QxwzyVlq`, `getQxwzy`, `qxwzy2`) is not matched — the word-boundary rule; list such spellings. (9) A standalone `.lzma`, brotli or bare zlib stream is read only as raw bytes and not reported; so are a zip appended to another zip (only the last one's members are read) and the members of a bzip2 or LZMA zip member past its declared size (zipfile reads those). (10) A blob that is valid UTF-8 without a NUL byte is never a container: an all-text PDF without streams is read as text (an encrypted string in hex is not decoded), and a compressed stream encoded as printable text would be read as text.
- **Allowlist** `scripts/denylist-allow.txt`: sha256 keys of single lines that are ordinary text equal to a denylisted term: `python3 scripts/denylist_scan.py --hash <path> <N>` — N is the finding's line number or its `run N` (both are accepted, from 1), read from the blob committed in HEAD; for a finding only history holds, `--hash <rev>:<path> <N>` reads that blob; for a container member, `--hash <path>!/<member> <N>`; for a `cannot be scanned` finding, `--hash <path> blob` keys the whole blob — with a neutral reason ("reviewed ordinary prose, not site data") that never names or hints at the term. Prefer rewording the line. Never allowlist a real private value; never blanket-allow a term.
- **Importing more predecessor code** (S1b/S4/S5): `git -C ~/devel/reaperiem archive <pinned SHA> -- <paths>` into a temp dir, `python3 scripts/scrub_import.py --map ~/.config/iemmixer/scrub-map.tsv --root <dir> --report <tmp>`, rewrite Dante channel literals to the synthetic map and run the Dante gate (S0 plan, Task 2 Step 8), then scan the staged tree (`git write-tree` → `--tree`) before committing; add the paths to `docs/provenance/import-manifest.txt`.
