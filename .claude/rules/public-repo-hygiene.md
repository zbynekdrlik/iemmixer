# Public-repo hygiene (program spec P6)

- This repository is public. Site data never enters it: band member names, host names, IPs, Dante device names and channel numbers, real track names, PINs, keys, tokens, user paths, the REAPER project name. Real values live only in the private `zbynekdrlik/iemmixer-ops`.
- Placeholders: `member1`…`member9` (MEMBER_1…MEMBER_9; `member1` = ELEVATED_MEMBER), `engineer`, TRANSLATOR; hosts `mixer.example.org`, LAN `http://10.0.0.10`; synthetic Dante numbers (member N = 69+2N/70+2N, i.e. 71–88; any other output 89/90; engineer 91/92; HIL's spare outputs 94/95; inputs 101–124); input names from program spec §3.1 where the code does not key on a REAPER-era name.
- **Every clone installs the pre-push hook** (S0 plan, Task 1 Step 9): gitleaks + `scripts/denylist_scan.py` with the private denylist `~/.config/iemmixer/denylist.txt` and `scripts/allowed-identities.txt`. CI repeats all three in the `secrets` job (`DENYLIST` secret). The denylist's non-credential terms are also kept in the ops repo; its credential entries only on the box and in the secret.
- **Scanner output never shows a term, a matched line or an address** — only a location and the entry number: `tree <path>:<line>: denylist entry N` (`tree <path>:run <N>: …` for a text run of binary content), `<sha> <path>: denylist entry N` (`<sha> <path>:<line>|run <N>: …` for a changed blob git's line diff cannot show — binary, UTF-16, UTF-32), `<sha> author|committer email is not an allowed identity`, or a git-lfs finding (`tree <path>[:<line>]: git-lfs pointer|filter, …` / `<sha> <path>: …`); open the local denylist to see entry N. Every finding line starts with a fixed word (`tree` or a commit's short SHA), never a raw path (a `::`-prefixed path would read as a CI workflow command), and a path component holding a term — in any reading, see below — or **any non-ASCII character** is shown `[redacted]`: no set of readings can be proven complete, and printed in a reading the scanner lacks, the ASCII tail of a term would reach the public log (#32 E3: a cp1250 path printed its term with only the accented letter replaced; #32 review m5: the same for double-encoded UTF-8). Commit mode decodes git's C-quoting (`core.quotePath`) of a `+++` path and forces `core.quotePath=true`, and terms + text are NFC-normalized, so a term cannot leak or hide behind an octal escape, a trailing tab, an added `++ ` line misread as a header, or a decomposed diacritic (see `scripts/denylist_scan.py` docstring). Commit mode also (#29) scans every added/modified path via `git diff-tree` (so an empty or binary file, whose path the unified diff omits, is still checked), splits content lines on `\n` only (not `str.splitlines()`, which also breaks on CR/VT/FF/NEL/U+2028 and would drop the `+` prefix on a line's tail), and `unquote_c` keeps a malformed C-escape literal rather than crashing or dropping the bytes that follow — three DETECTION bypasses distinct from the #27 output-leak class.
- **Editing the scanner — parity/gotcha notes (#29):** all three line splits (`scan_tree` blob, `scan_commits` diff, `--hash`) must use `.split("\n")` on **bytes-decoded** text — `--hash` reads `read_bytes()` NOT `read_text()`, because `Path.read_text()` universal-newline-translates CR/CRLF to `\n` and silently diverges the allow key from the byte-level tree/commit key (a CR/CRLF line then can't be allowlisted). An empty or binary added file produces **no `+++` diff header** (git emits `Binary files … differ` or nothing), so its path is enumerated via `git diff-tree --name-only -z --root ...` and deduped against the `+++` paths in `seen`. `git diff-tree -m --first-parent` is a **no-op on git 2.43** (`--first-parent` after `-m` is ignored → all-parents; use `--diff-merges=first-parent` if you truly want first-parent only) — the scanner deliberately keeps `-m` (all-parents = safe over-scan, never misses a path any merge parent introduces). `git show`, by contrast, DOES honour `-m --first-parent` (a merge's diff against its first parent) — the scanner now says `--diff-merges=first-parent` outright.
- **A developer's local git config must not reshape what commit mode parses (#32 review):** the one parsed diff (`scan_commit_diff`'s `git show`) pins `--src-prefix=a/ --dst-prefix=b/` (else `diff.noprefix` prints `+++ b/x` for the path `b/x`, read as `x` — wrong allow key and location; `mnemonicPrefix`, and `srcPrefix`/`dstPrefix` from git 2.45, change prefixes too), `--no-relative` (`diff.relative` from a subdirectory hides every change outside it), `--diff-merges=first-parent` (`log.diffMerges=combined` empties a merge's diff for a file only one parent changed), `--root` (`log.showRoot=false` prints no diff for a root commit) and `--no-show-signature`, besides `--no-color --no-ext-diff --text --no-textconv --no-renames` and `-c core.quotePath=true`. The two `git show -s` metadata calls go through `METADATA` (`--encoding=UTF-8 --no-show-signature`): `i18n.logOutputEncoding` re-encodes message and emails (UTF-16's NULs crashed the identity split, ISO-8859-2 hid a term) and `log.showSignature` prints "No signature" into the author field of a signed commit. Any NEW parsed `git show`/`diff`/`log` call needs the same pins; `diff-tree` / `ls-tree --full-tree` / `cat-file` are plumbing and read no such config.
- **What the scanner reads (#32):** `.gitattributes` never hide content — tree mode reads each blob's bytes via `cat-file` (no attributes), commit mode diffs with `git show --text --no-textconv` (a `binary` / `-diff` attribute or a textconv driver would otherwise hide added lines). git-lfs does hide it (the repository holds only a pointer), so a pointer blob and any non-comment `.gitattributes` line setting `filter=lfs` is a finding in both modes (#32 review m9). Content is read as numbered **units** in **batches** of about `CHUNK` (256 KiB), shared by tree mode, commit mode and `--hash` so allow keys stay in parity: text lines; UTF-32 / UTF-16 text (`wide_codec`: a BOM — UTF-32's `FF FE 00 00` before UTF-16's `FF FE` — or the NUL pattern of Latin text) as its decoded lines **and then its byte runs** (a binary may only look like wide text: quiet 16-bit PCM, a blob starting `FF FE` — #32 review m3/m4); other NUL content (binary) as text runs — byte runs without control characters plus embedded UTF-16 strings (Windows wide strings in an `.etl` / `.lnk`) — numbered on as `run N`. Random bytes form short words by chance (the f64 goldens hold 28 % of all 3-letter words), so in a binary run a term under `MIN_BINARY_TERM` (5) characters counts only inside a run of `LONG_TEXT_RUN` (32) bytes of valid UTF-8; a shorter term in a short binary run is a known, accepted gap. In commit mode a changed blob that is not plain text is scanned whole, and a finding is kept only when its unit is absent from the old blob (read a batch at a time). Text is decoded **losslessly** (UTF-8, `surrogateescape`; `line_key` hashes the exact bytes, valid UTF-8 lines keep their keys) and matched in every **reading** (`Views`): escapes decoded (`\uXXXX`, `\u{X}`, `\UXXXXXXXX`, XML / HTML `&#N;` / `&#xN;`, C / Rust / Python byte escapes `\xNN` / octal / `\0` / letter escapes, percent-encoding — an escape right before a term is also a word boundary, #32 review M1); double-encoded UTF-8 read back (`unmojibake`: UTF-8 once decoded as cp1250 / Latin-1 and encoded again); a compact reading (`compact`: soft hyphen and zero-width characters removed, compatibility letters such as fullwidth ones in NFKC — #32 review m6); undecodable bytes re-read as cp1250, Latin-1, ISO-8859-2 and cp852 (only those bytes — re-reading valid UTF-8 is mojibake that splits words). git stores a non-UTF-8 commit message or name with those bytes converted as Latin-1 (`verify_utf8`), so commit metadata is also read back as cp1250. Identity emails are read NUL-separated (`%ae%x00%ce%x00`), compared exactly (case aside, no `strip()`), and an email holding a line separator is never allowed (#32 E4: `splitlines()` let U+2028 push the committer email out of the check).
- **Editing the scanner — cost and false positives (#32):** the units of a batch are joined by `SEP` (U+E000, a non-word character): no reading may create or remove it (escape decoders and `unmojibake` turn a decoded U+E000 into U+FFFD), because a match maps to its unit by the SEPs before it. An ASCII term is matched only in the raw, escape-decoded, `unmojibake` and `compact` readings behind a case-fold `in` pre-filter (`fold` covers re.IGNORECASE's extra matches İ ı ſ and the Kelvin sign, checked against every code point) — a re-reading or NFC can only remove an ASCII term's match; the NFC and re-read readings are built only for a term with a non-ASCII character whose longest ASCII word occurs. The stated budget (`test_a_large_binary_blob_stays_within_the_cpu_and_memory_budget`, #32 review m7): a 4 MiB blob of random bytes against 40 terms in under 1.0 s CPU per MiB and a peak under two copies of the blob plus 24 MiB (measured 0.41 s/MiB and 19 MiB; a 20 MiB blob 4.7 s / 41 MiB — it was 65 s / ~1 GB). A change to matching, decoding or unit extraction can also add false positives that only the PRIVATE denylist reveals (the public tests use synthetic terms): before handing off, run `python3 scripts/denylist_scan.py --denylist ~/.config/iemmixer/denylist.txt --allow scripts/denylist-allow.txt --identities scripts/allowed-identities.txt --tree HEAD --commits HEAD` — CI scans the full history the same way — and keep it clean (~22 s CPU for tree + history in 2026-09). A synthetic test term is always an invented word (`zyxname`, `ďqxwzy`), never an ordinary word or a real name — either could equal a private entry, and a pushed test line can never be taken back.
- **Allowlist** `scripts/denylist-allow.txt`: sha256 keys of single lines that are ordinary text equal to a denylisted term: `python3 scripts/denylist_scan.py --hash <path> <N>` — N is the finding's line number or its `run N` (both are accepted); for a finding only history holds, `--hash <rev>:<path> <N>` reads that blob — with a neutral reason ("reviewed ordinary prose, not site data") that never names or hints at the term. Prefer rewording the line. Never allowlist a real private value; never blanket-allow a term.
- **Importing more predecessor code** (S1b/S4/S5): `git -C ~/devel/reaperiem archive <pinned SHA> -- <paths>` into a temp dir, `python3 scripts/scrub_import.py --map ~/.config/iemmixer/scrub-map.tsv --root <dir> --report <tmp>`, rewrite Dante channel literals to the synthetic map and run the Dante gate (S0 plan, Task 2 Step 8), then scan the staged tree (`git write-tree` → `--tree`) before committing; add the paths to `docs/provenance/import-manifest.txt`.
- Commits use the GitHub noreply identity only (`scripts/allowed-identities.txt`). Merge with plain `gh pr merge --merge`: the account keeps its email private, so GitHub authors the merge with the noreply address. `--author-email` with a noreply address is rejected by the API ("Invalid email address") — never pass it.
