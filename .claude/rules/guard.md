# Guard, iemmode, PC install (S6, #9)

Design note `docs/superpowers/specs/2026-09-27-s6-asio-guard-hil-design.md`, plan `docs/superpowers/plans/2026-09-27-s6-asio-guard-hil.md`.

- **Preference window (I2).** The driver reads its preferred buffer only at open. `iem_win::prefwin::enter` refuses unless the store holds the recorded original and writes 32 with the original's kind; `AsioStream` calls `leave` right after `createBuffers` on every open, success or failure; both read back. At every other moment the registry holds REAPER's value. The guard's `PrefCheck` precedes `ReaperStart` in every plan and restores with `prefwin::restore(.., 3)`; after three failed restores at an event it follows `[guard] on_pref_fail` (`start_reaper_with_alarm`, recorded on #9). The elevated logon task (`iemmixer-logon`) restores it too (G1).
- **Stops are requests plus a bounded wait, then an alarm (I8).** `iem-engine interlock` stops at its `--stop-file` (`<root>\guard\interlock.stop`, seen within 0.1 s, exit 6), never Ctrl-Break (its default handler would end it with the card open). Engine `Shutdown` (supervisor pipe), server and runner Ctrl-Break delivered to their own console (`iem_win::console::ctrl_break`: under a process-wide lock detach, attach to the child's console, ignore Ctrl events, send `CTRL_BREAK_EVENT` to its group, detach, restore), tray `Quit`, REAPER 40026 then 40004, the predecessor app through its tray Exit command. The integrity scan refuses force-end verbs everywhere, comments included (Rust/tokio/Python/.NET kill methods, also named in `ForEach-Object`; job-close kills; WMI/CIM Terminate by `-MethodName` or `-Name`; wmic terminate/delete; tskill, pskill; `CREATE_BREAKAWAY_FROM_JOB` outside `crates/iem-win/`); write "force-end" in prose.
- **Planner invariants** (`plan::plan`, pure, mutated): on dev/live entry the app stops before REAPER saves (a phone cannot dirty the project between save and quit); the interlock runs whenever REAPER or the app runs, from any mode; `PrefCheck` before REAPER; the S1c fingerprint last (alarm only); a REAPER without the card or an app not serving is restarted. **Error policy** (`plan::on_error`): a failed engine release at "ide event" never tears down a healthy iemmixer (keep serving, alarm, the owner's prepared ❓); a dead or parked engine stops the plan (no REAPER while the card may be held, no app without REAPER).
- **Reboot = event** (`state::reset_to_event`): a boot later than the state file, or REAPER/the app running without an engine, drops a pending switch and sets `event`. Every waiting step takes the `Cancel` token and returns `Preempted` within 1 s; only mutating steps (a save, a quit, a registry write) finish first.
- **Predecessor exit** (`handover::app_exit`, `app_binary`): the exe SHA-256 equals `[guard] app_exe_sha256` at the precheck, before REAPER is touched; the process handle is opened before the tray command is posted, then exit code 0 within 30 s, ports 80/443 free, no newer temp file; the log line only corroborates. Anything else aborts the switch and restarts REAPER.
- **Site values** live only in the ops `site.toml` (`[card]`, `[guard]`), `~/.config/iemmixer/iem-pc.env` and the ops runbook: driver name and module, preference key, task paths other than `\iemmixer\…`, the predecessor's process names, exit command id and exe hash, hosts, channels. Tests use `Test Card`, `testcard.dll`, RX 101–132, TX 71–93, HIL's spare TX 94/95, exit id 4242.
- **Dev box (`scripts/iem-pc/iempc.py`).** "ide event" → `iempc event`: it writes `~/.config/iemmixer/EVENT-NOW` first, pre-empts an open S1a/S1c window (`spike_window.py preempt`), runs `iemmode event`, and `iemmode event --direct` when the guard is unreachable (exit 4). This is the one switch-over rule from S6 Task 16 Step 3 (guard installed) on; before that the interim switch (`CLAUDE.md`). Every other PC command refuses while the flag exists; every wait sees a new flag within 2 s. HIL is dispatched from the dev box (`iempc dispatch-hil`), never from public CI.
- **PC tasks (`IemPc.psm1`, Windows PowerShell 5.1).** `Register-IemTasks` registers the guard, StartApp, probe, tuning, exclude and logon tasks under `\iemmixer\` via `Schedule.Service` (Interactive, `PT0S`, IgnoreNew, no idle/battery stop, restart 3 × PT1M, priority 4, never ended hard) with `D:(A;;GRGX;;;<user SID>)(A;;FA;;;BA)(A;;FA;;;SY)` and `TASK_DONT_ADD_PRINCIPAL_ACE` (0x10: without it the service adds its own ACE for the user and the read-back refuses); the read-back accepts the generic or file form of those rights and nothing else. `iemmixer-StartREAPER` predates S6: it keeps its definition and only gains the descriptor; without it nothing is registered.
- **The elevated root** (`%ProgramData%\iemmixer`, resolved by `Register-IemTasks` from the known folder and written into each Highest task's command line (the entry script's path and `-TuningDir`); the elevated process never reads an environment variable for a path). Every folder (`tasks`, `tasks\out`, `tuning`) is owned by Administrators with a protected DACL (Administrators and SYSTEM full, the user read and execute), created with its security in one step; an existing folder owned by anyone else, or any junction or link, is refused. Our files are written fresh and owned by Administrators; everything reads back (`Test-IemElevatedItem`). `iem-task.ps1` pins `PSModulePath` to `$PSHOME\Modules` and Program Files first. The tuning task imports S1c's `IemTuning.psm1` only when the tuning folder, its parent, the module and `profile.json` pass that read-back; until they exist it answers `absent`. The guard writes `<root>\guard\tasks\<kind>.request.json` (`tuning`: `{id, verb}` of enter/exit/state/apply-tier2; `exclude`: `{id, sha, keep}`), read elevated only if no path part is a junction or link (at most 64 KiB, never echoed); the task writes `<elevated root>\tasks\out\<kind>.result.json` (`{kind, id, ok, at, result, error}`), which the user may only read: an elevated process never writes into the user's root. The guard (`effects::tuning`, `win::tasks::elevated`) writes the requests, waits for the answer with its id, and takes the elevated root from `pc.toml` `elevated_root` (default `C:\ProgramData\iemmixer`, what `Register-IemTasks` resolved), never from an environment variable; `exclude`'s `keep` is the other pin. S1c's record for the drift check is `<elevated root>\tuning\expect.json`.
- **PowerShell rules.** 5.1 syntax only (no `?:`, `??`, `&&`, `||`), ASCII files, `Set-StrictMode -Version Latest` (read parsed JSON through `Get-IemProp`), `"${name}:"` or `-f` where a colon follows a variable, one native command per CI step. `Test-IemPc.ps1` (the `windows` job) parses every script in the folder and runs the functions against real backends on the runner: a `\iemmixer-test\` task folder, a temp root, an HKCU test key, a disabled test firewall rule, a test service; Defender and the runner with `-WhatIf`; hil-v1.ps1 end to end against a fake `iemmode`.
- **Bundles (P5/G8).** The `bundle` job builds the release binaries (the server with `standalone,tls,audio` and the real UI), zips them with `hil-v1.ps1`, `IemPc.psm1`, `LICENSE-iem-engine`, `manifest.json` and `SHA256SUMS` (one level `tuning/<name>` allowed), runs the fresh guard's `install <zip> --verify-only` and refuses a tampered copy; it uploads only on a push to dev/main; `attest` attests the zip by digest. `iempc fetch-bundle` needs a green push run with both jobs and `gh attestation verify`. `bundle.rs` is the reference for `SHA256SUMS` names; `iempc.py` and `Test-IemBundleSums` are stricter (only `[A-Za-z0-9_.-]`, one level).
- **HIL v1 (`hil-v1.ps1`).** Runs from the verified `bundles\<sha>\` (it refuses elsewhere): job-begin → activate → checks → job-end → report → `result.json`. A refusal once the guard left dev is `cancelled` (no report); exit 1 only for `failure`. The `summary` is public (the ops report job posts it as `hil/iem-pc`, P6): check names, counts and a fixed cancel phrase by reason code (`left-dev`, `not-free`), never free text; the guard's text goes to `why`, details to `checks`, both private. The engine checks read the guard's `Reply.engine` (`iem_guard::EngineStatus`: `build`, `frames`, `callbacks`, `missed`, `resets`, `parked`, `faulted`, `pipe_private`, `spawns`, `last_exit`, `hil`; f64 peaks, so the reply types are `PartialEq` only) from `iemmode status`; the panic check drives `iemmode inject-fault` (`Request::InjectFault`) and wants exit 70, one respawn and the new engine streaming at 32. The guard fills `Reply.engine` from its supervisor connection (`Pc::engine_seen`: the hello's commit as `build`, the newest `Status`, the control pipe's DACL read once per engine process with `iem_win::token::sddl_is_private`), its own engine starts (`spawns`) and the watch's last exit code; `None` while no engine of ours runs and until the connection holds the hello and a `Status` (`effects::engine::seen_status`: an engine coming up is absent, never zeroed). So HIL v1 never reads a status once after a fixed sleep: `Wait-HilEngine` polls `iemmode status` (500 ms, at most `-EngineWait`, 30 s) until `Test-IemHilEngineUp` holds (frames 32 and callbacks above a mark; the bundle's build after activate, before engine-build and card; one more reset after force-reopen; callbacks above the respawned engine's first status after the fault), then the check judges the last status. A HIL job (`GuardState.job`, persisted, so a hand-over to a new guard exe or a restart keeps it; cleared whenever the mode leaves dev) starts every engine with `site::HIL_FLAGS` (`--test-signal --fault-injection`; never in live, refused in `pc.toml` `engine_args`); inside a job `activate` and `install-site` restart only the engine and the server (`daemon::restart_in_job`: a dev entry would stop the runner that runs the job), and `force-reopen` is the engine's supervisor `force_reopen`; `rehearse-teardown` is refused inside a job like `runner-stop` (its dev re-entry cancels the jobs and stops the runner). The job's 300 s of band quiet is `WinPc::quiet`, one `Quiet` per guard fed by every supervisor connection: a new connection keeps it when the last meter frame came at most `QUIET_GAP` (60 s) before (`Quiet::resume`), else it starts again, and `quiet_for` reads it only once this connection heard the stage (`Quiet::heard`); a hand-over to a new guard exe starts it again. The supervisor connect opens `\\.\pipe\<engine_pipe>` with interprocess's named-pipe connect and `ConnectWaitMode::Timeout(200 ms)`: its local-socket connect ignores `ConnectOptions::wait_mode` on Windows (2.4.4) and waits for a free instance forever; `seen` makes one attempt per look, `supervisor()` repeats them until the step's limit. `[guard] hil_tx` are HIL's spare card outputs, never a channel a band member hears (owner, #9 2026-09-28): `iem-engine check-site` (so install-site) refuses a mix's TX, a channel outside `[engine] channels`, a repeat or more than 8 (`Topology::hil_outputs`, `SiteError::HilTx`), and the engine refuses a `card_tx` that names a mix's TX. The test-signal check reads `Reply.engine.hil` (each spare output's peak since the engine's previous `Status`): it polls `iemmode status` while the TTL runs and wants every spare output at the asked level within 0.5 dB, then `Wait-HilSilence` (at most `-EngineWait`) for a status with all of them silent (`Test-IemHilSignal`, `Test-IemHilSilent`). Inputs are refused before any call: `-TestDbfs` above −20 dBFS, `-TestTtl` outside (0, 60] s (the guard's `HIL_MAX_TTL_S`). Not in HIL v1: the pipes' first-instance flag, the tunnel peer, the reopen's duration, the fault callback's time (plan Task 10 Step 6).
