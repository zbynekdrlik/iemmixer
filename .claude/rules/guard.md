# Guard, iemmode, PC install (S6, #9)

Design note `docs/superpowers/specs/2026-09-27-s6-asio-guard-hil-design.md`, plan `docs/superpowers/plans/2026-09-27-s6-asio-guard-hil.md`.

- **The owner's signal is the only gate (#38, owner decision 2026-10-06: "pre teba je podstatné či je alebo nie je event a o tom rozhodujem ja! NIE TY!!!").** "Ide event" / "event skončil" (the EVENT-NOW flag, the guard's `event` mode) alone stop or postpone work on the PC. No step measures silence, activity or the band playing: other devices on the Dante network feed the card's inputs, so a level says nothing about the band (2026-10-06: the HIL job on the new `main` was refused, "the band was quiet for 73 s"). A dev/live entry is the precheck, the stops and the start (`plan::every_entry_is_the_precheck_the_stops_and_the_start`; `plan(to, facts)`: the mode a switch starts from changes no step); a HIL job begins in dev while no other job runs (a switch refuses it at the pipe); the guard reads no meters (the engine's `topology`/`meters` frames parse as `Msg::Other`). Gone with it: the Interlock step, its 15-min retry, `iemmode dev --force`, `Pc::reaper_meters`/`engine_interlock`/`engine_stage_peaks`/`band_quiet_for`, `WinPc`'s `Quiet`, the guard site's `[activity] inputs`, `iem-engine interlock`. An older guard's `alarms.json`/`guard-state.json` still load: `plan::known_step`/`known_steps` read the gone `interlock` step as none, an old `interlock_retry` is ignored, an older iemmode's `force` too. Never add a level gate back without the owner's word.
- **Preference window (I2; #9 2026-09-28).** The preference holds 32 while the engine holds the card, REAPER's original at every other moment (a write while the driver is open most likely makes it ask for a reset: the first run on the PC faulted on its reopen budget). `iem_win::prefwin::Window` (`Original`/`Held`): `enter` Original → Held needs the recorded original in the store and writes 32 with its kind (a failed write still leaves it Held); Held → Held (a reopen) only reads 32 back and writes nothing; anything else refuses without a write (`NotOriginal`, `NotHeld`). `leave` Held → Original writes the original (a failure stays Held); Original touches nothing. Both read back. `AsioStream` leaves only where the card is released and no open follows (`.claude/rules/asio-spike.md`); a parked stream keeps 32. A hard kill, a power loss or an OS restart while the engine holds the card leaves 32: the guard's `PrefCheck` precedes `ReaperStart` in every plan (every event plan has it) and every engine start: `EngineStart` in every dev/live entry, the crash watch's `respawn` and `restart_in_job` (#9 2026-09-28, `a_respawn_restores_the_preference_right_before_the_engine_starts`, `a_job_restart_restores_the_preference_right_before_the_engine_starts`; a failed check starts nothing: respawn alarms like a failed start, the job restart unwinds). It is `prefwin::check(.., pc::PREF_ATTEMPTS, holders)` — an engine's 32 is a restore, never a refusal (`restore_takes_back_the_frames_of_an_engine_that_ended_holding_the_card`) — and **never writes while a process holds the driver module** (#9 2026-09-28: the holder's driver would most likely ask it for a reset, a REAPER at an event would drop out). The holders are read only when the value is not the original (`pc::card_holders`: anything counts, our engine too; unreadable → a running REAPER is assumed to hold it, as `facts_from` does). The result is `pc::PrefSeen`: `Original(writes)` or `Held(PrefHeld)`; in the event plan `Held` is no failure (alarm once per value, `PrefCheck` step, no owner question; `GuardState.pref_held` persists it, `iemmode status` names it, a reset keeps it, a check that finds or restores the original drops it; the dev entry's check after `ReaperSaveQuit` restores it), before an engine start it fails the step. After three failed restores at an event it follows `[guard] on_pref_fail` (`start_reaper_with_alarm`, recorded on #9). The elevated logon task (`iemmixer-logon`, G1) restores it by the same rule (#9 2026-09-28): `Restore-IemPref -Module` decides with the pure `Get-IemPrefAction` (`none` at the original, holders not read; `restore` while nothing holds the module; `held` while anything does, never written; an unreadable list (`$null`) assumes a running REAPER holds it) and reads the holders with `Get-IemModuleHolders` only when the value is not the original. A `held` run succeeds and its `logon.result.json` names it (`result.pref`: `action`, `before`, `holders` as `image:pid`); the guard takes each run once (`GuardState.logon_seen` = its `at`) at its start (before the event plan) and in the hourly look (`effects::tuning::logon_result`, REAPER known by `pc.toml`'s image, any case, ".exe" or not): `held` → `pref_held` with `PrefCheck`'s text, one alarm `logon task: …`; a run at the original drops `pref_held`; a failed run is logged. Before cutover the guard does not start at boot, so a REAPER autostarted by the predecessor could open the card at 32 before the logon task restores it (§10 test #2 on #35, 2026-10-06: a parked engine keeps 32, REAPER started first, the logon task found it `held`); the boot task (below) narrows that race to a boot whose task did not run in time (or a Fast Startup start), and the logon task and the guard stay the second and third line (a REAPER that won anyway is left at 32 until it quits, named, one alarm).
- **The boot task (`iemmixer-boot-pref`, #35).** At the system's start it reads the preference and writes the original back only when the value is not the original (a parked engine, a power loss or a hard kill left 32; a normal boot writes nothing and reads no holders) and no process holds the driver module: Task Scheduler's boot trigger, the desktop user's account by S4U (no stored password; the user's HKCU is loaded), Highest. Probed on the PC (#35, 2026-10-06): such a task started 4 s after the boot, the PC logged on by itself 2.6 s later, REAPER (the predecessor's autostart) started ~12 s after the task; the PowerShell write landed 3.6 s before REAPER; the native write is expected within a few seconds of the task's start, not yet measured with tasklist in the chain (test #2 measures it: the log header's time against REAPER's start; tasklist walks every process's modules). Its I2 basis is a holder check like the logon task's and the guard's, never the timing (review of PR #40, 2026-10-07: timing alone let a task started late write under REAPER without a word): right before the add, `tasklist.exe /m "<module>" /fo csv /nh` (`-Module`, the `[card]` module) writes the holders into `<elevated root>\tasks\out\boot-pref.holders`, and `findstr.exe /b /l \^"` looks for a line starting with a quote, a holder's CSV row (locale-independent: the words of tasklist's localized "no tasks" line are never read). A quote line → nothing written, `add=held`, exit 0 (REAPER runs at 32 until it quits; the logon task finds it `held` and the guard names it, one alarm). The add runs only on proof that the list was read: `findstr.exe /v /b /l \^"` must find a line that does not start with a quote (the "no tasks" line). findstr exits 1 both for "no match" and for a file named on its command line that it cannot open (2 only for bad usage; the lane's review), so exit codes alone cannot tell "no holder" from "unreadable". Without that proof, or when tasklist or its redirection fails (`&&`/`||` take a failed redirection as a failed command) → nothing written, `add=unread`, exit 2. The test runs the registered action with a module no process loads (written), `kernel32.dll` (held), a folder at the list's path (unread) and a list this user may write but not read (unread, tasklist having written it). The read-back still refuses a trigger delay, and the logon task stays the second line. It runs at no other moment: the boot trigger is its only trigger (no logon trigger, no repetition, no delay, enabled), no restart on failure, no late start (`StartWhenAvailable` off), no start on demand (`AllowDemandStart` off: the user, who may run our other tasks, cannot start it while REAPER plays); `Register-IemTasks`' read-back refuses any of these (`Test-IemTaskReport -Boot`; every task of ours: no late start, repetition, trigger delay or disabled trigger). The action is native, never PowerShell (~8 s to start at boot): `Get-IemBootPrefCommand` builds `cmd.exe /d /q /e:on /v:on /s /c "…"`: `reg.exe query` of the value into `<elevated root>\tasks\out\boot-pref.before`, `findstr.exe /i /l /x` of the original's line as reg.exe prints it (`    <name>    REG_DWORD    0x<hex>` or `REG_SZ    <raw>`), only when it differs the holder check above and, with no holder, `reg.exe add "HKCU\<key>" /v "<name>" /t REG_DWORD|REG_SZ /d <original> /f`, then a header `boot-pref <date> <time> add=none|held|unread|0|1` (cmd's local clock, a diagnostic only: a `DATE`/`TIME` the user sets would show instead; `Get-IemBootstrapState`'s last run and last result are authoritative) and `reg.exe query` appended to `<elevated root>\tasks\out\boot-pref.log`; cmd's exit code is 1 when the add failed, 2 when the holders could not be read, else 0 (a findstr that cannot compare the value falls through to the holder check, as before it). The holder search's quote is `\^"`: the caret makes cmd take the quote as text (cmd's quote state stays; the findstr command holds no `!`, so delayed expansion never reads the caret again), the backslash is findstr's escape of a quote; the branches are `&&`/`||` only (every path through the holder block ends in a successful `set`, so the outer `|| set "iemadd=unread"` fires only when tasklist or its redirection failed). It runs elevated with the user's environment, so the line holds no `%` (cmd, and Task Scheduler, expand `%name%` before cmd parses the line; `!name!` under `/v:on` is expanded after it, so a value the user set is text, never a command), `/d` skips cmd's AutoRun, `/e:on` keeps the extensions whatever the user's HKCU says, every program by its full path, no pipe and no `FOR /F` (each starts another cmd through `COMSPEC`); a key, value name, module or path holding `" % ! ^ & | < >` or a control character, a value name holding a backslash (findstr's literal), and a module that is not a bare `.dll` name, is refused before anything is read or registered; all three files live in the admin-only out folder (an elevated process never writes into the user's root). The key must be under HKCU (`Software\…`, `HKCU:\…`, `Registry::HKEY_CURRENT_USER\…`). `Register-IemTasks` reads the value in its own session's HKCU (`Get-IemPrefKind`: run it as the desktop user, as `iempc bootstrap` does) and writes that kind (DWord → REG_DWORD, String → REG_SZ, as `Restore-IemPref` keeps the kind); a key or value it cannot read is refused (a typo would make `reg add` create one). The original is fixed in the command line at registration, as the logon task's is: a changed site original needs `Register-IemTasks` again. **Fast Startup**: a shutdown with it on hibernates the system session, and the next start fires no boot trigger; then the logon task is again the first (a restart, as test #2, is a full boot). It is on only when `HiberbootEnabled` is 1 (`HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Power`) AND the hibernation file is present: without the file the shutdown is full whatever `HiberbootEnabled` says (the venue PC, review of PR #40: `HiberbootEnabled` 1, hibernation off in `powercfg /a`, the boot task runs). The file is the state, not the registry's setting (`HibernateEnabled`): `Test-IemHiberFilePresent` lists the system volume's root for `hiberfil.sys` (`[IO.Directory]::GetFiles`, FindFirstFile: the kernel holds the file open, so it is found, never opened; `powercfg /h off` deletes it). No `Add-Type` there (the lane's review): Windows PowerShell 5.1 compiles in the user's temp folder, which a process of the user could change under the elevated bootstrap session. `Get-IemFastStartup` (pure) judges: on, off, or unknown (`$null`) when a fact cannot be read and none is off, and only on names a problem. `Get-IemBootstrapState.fast_startup` holds `hiberboot_enabled`, `hiberfile_present`, `active`, `problem` and `error` (`Get-IemFastStartupState`); `Register-IemTasks` writes the problem as a warning and on the boot task's row (`warnings`, every row has it; `Get-IemBootTaskWarnings`), and names a Fast Startup it could not judge (the read error), never a refusal. Its `-FastStartup` takes a judged Fast Startup in place of the PC's facts (the test registers once with it on). `Get-IemBootstrapState` names the task's last result and last run (`tasks[].last_run`, UTC; 0x41303 "has not yet run" before the first boot) and the log's last block (`boot_pref.log`); its output holds site values (the user, the preference key): it stays on the dev box (P6). Registered on the PC in dev time from a fetched bundle: `iempc bootstrap --sha <bundle> Register-IemTasks -Root … -AppExe … -PrefKey … -PrefName … -PrefOriginal … -Module …` (values from the private env/site); then test #2 again: park → graceful restart → REAPER at the original, no `logon task: …` alarm, and `boot_pref.log` showing this boot's block with `add=0`, its header time before REAPER's start.
- **Stops are requests plus a bounded wait, then an alarm (I8).** Engine `Shutdown` (supervisor pipe), server and runner Ctrl-Break delivered to their own console (`iem_win::console::ctrl_break`: under a process-wide lock detach, attach to the child's console, ignore Ctrl events, send `CTRL_BREAK_EVENT` to its group, detach, restore), tray `Quit`, REAPER 40026 then 40004, the predecessor app through its tray Exit command. The integrity scan refuses force-end verbs everywhere, comments included (Rust/tokio/Python/.NET kill methods, also named in `ForEach-Object`; job-close kills; WMI/CIM Terminate by `-MethodName` or `-Name`; wmic terminate/delete; tskill, pskill; `CREATE_BREAKAWAY_FROM_JOB` outside `crates/iem-win/`); write "force-end" in prose.
- **Children and the guard's job** (`iem_win::spawn`, `decide::placement` mutated; #9 2026-09-28: the PC's task job allows no breakaway, EngineStart failed with "Access is denied. (os error 5)"). Every long-lived child (engine, server, tray, runner, a direct REAPER or app start, a hand-over's new guard) goes through `spawn_detached`, which reads the immediate job (`job_limits`: `IsProcessInJob`, then `QueryInformationJobObject(JobObjectExtendedLimitInformation)`; a nested job's parents are not read) and places the child, never by trial: no job or silent breakaway → no flag; breakaway allowed → the flag; neither, and the job does not end its processes when it closes → inside the job (`Pc::job` logs the reading at the guard's start, `iemmode status` names it: `pc::JOB_NOTE`); neither, and it does → refused (`PermissionDenied` with the reason = the step's error, the error policy unwinds). That limit is `spawn::JOB_ENDS_ON_CLOSE` (winnt.h 0x2000): its Win32 name matches the integrity scan's force-end verbs, so code never spells it. Helpers (`helper_flags`) stay in the job. On the hosted runner cargo's own job refuses the start, so `tests/spawn_job.rs` nests its process in a job without limits to run the in-job start (the nesting lasts for the process: one test per binary).
- **Engine exits** (`crash::after_exit`, mutated): 0 stays down; 2 (site/usage) and 3 (card) stay down with an alarm; any other (1 I/O, 70 RT fault, none) respawns after the backoff (1, 2, 4, 8, then 10 s) and counts toward the crash loop (3 in 10 min: dev or a trial back to REAPER, prod live the previous pin). 75 (`crash::STATE_BUSY`, the engine's `EngineError::StateBusy`: another process still held its state directory after its 3 s wait, most likely an engine that just ended; #32 minor-4) is no crash: respawn after `BUSY_RETRY` (2 s), no backoff, no loop; `CrashLoop::busy` counts them in a row and the guard alarms once at the third. The streak is bounded (#32 F3-r4 3): up to `crash::BUSY_LIMIT` (10, about 50 s) in a row (`crash::busy_retry`, `after_exit`'s `busy_streak`), then each further 75 counts as abnormal, so the backoff and the crash loop's fallback (REAPER, or the previous pin in prod) run when something the guard does not watch holds the directory. A plan's engine that ends with 75 before it is ready (EngineStart, then EngineArm's wait for its pipe) is started again inside the step, held, once, after `BUSY_RETRY`, with `PrefCheck` right before (`daemon::engine_ready`, `crash::ready_restart`, `Pc::engine_exit`: a look at the watched child; `WinPc`'s connect wait ends at once when its engine child has ended, `procs::Kids::ended`); a second busy end or any other end fails the step (#32 F3-r4 4). A session ending stays down whatever the code.
- **Planner invariants** (`plan::plan`, pure, mutated): on dev/live entry the app stops before REAPER saves (a phone cannot dirty the project between save and quit); no step reads the stage (#38, above); `PrefCheck` before REAPER in every event plan, after `HolderGone` (the check never writes under a holder, so it must not meet one the plan could have waited for; #9 2026-09-28), and exactly once, right before `EngineStart`, in every dev/live entry (after REAPER quit and our engine stopped: never while REAPER may hold the card, whose driver would see the write; #9 2026-09-28, `every_entry_restores_the_preference_right_before_the_engine_starts`); the S1c fingerprint last (alarm only); a REAPER without the card or an app not serving is restarted. **Error policy** (`plan::on_error`): every dev/live entry failure unwinds, its `PrefCheck` included; `on_pref_fail` is the event plan's rule only; a failed engine release at "ide event" never tears down a healthy iemmixer (keep serving, alarm, the owner's prepared ❓); a dead or parked engine stops the plan (no REAPER while the card may be held, no app without REAPER).
- **Where alarms go** (`pc::precheck`, mutated; owner decision, #9 2026-09-28): the guard's alarms (`send_notices` → `iem-server notify --to alarm`) go to the engineer's PWA notification subscriptions, the audience the predecessor's alerts reached (`server-engine.md`); there is no separate alarm list or alarm link. ≥ 1 subscription (`iem-server notify --count alarm`) is required for `live` and trials only ("no PWA notification subscription: …" refuses them). The predecessor's subscriptions arrive with `iem-migrate band`, a later step of the dev entry than the precheck, and a new one only through iem-server, which runs only in dev and live (in event the predecessor holds the band's address). So a dev entry without one (or with an unreadable list) goes on and names it: in its report (`--dry-run`: `precheck ok; <note>`) and in `iemmode status` (`Guard.subscriptions_note`, until the next precheck or an alarm notice reaches a phone, e.g. `iemmode alarm-test`); the alarms stay in the guard's alarm file, which the agent reads. Another precheck refusal still refuses a dev entry. HIL v1's `alarm-push` check is `iemmode alarm-test` reaching ≥ 1 device. `send_notices` sends each open alarm once; a new guard (hand-over, restart) reads the alarm file and tries again what reached no device, never an acknowledged alarm (#9 2026-09-28: a hand-over sent six acknowledged alarms from the morning; `an_acknowledged_alarm_is_never_sent`).
- **LAN 443: identity, not validity** (`tls::check`, mutated; #9 2026-09-28: curl's schannel refused LAN 443 with `SEC_E_CERT_EXPIRED`, and the predecessor serves the same expired certificate). IdentityCheck's LAN 443 runs the guard's own rustls client (ring, as iem-server; never native-tls): SNI = `[guard] public_host`, any chain and validity, the handshake's signatures verified with the served leaf's key (`SignaturesOnly`), the leaf byte-equal to the first certificate of the server's `cert.pem` (`effects::web::server_cert`: the server config's `tls_cert` next to it) before anything is sent, then an HTTP/1.0 `/api/version` naming the bundle. A certificate outside its validity is `Guard.lan_note` ("the LAN certificate expired on <date>; the predecessor serves the same one": the report once, `iemmode status` until the next identity check), never a failure or an alarm; the public host stays curl's validated check. The check runs on a thread bounded by `Lan::limit` (a timed-out socket is never reused); "ide event" returns within a `Cancel::SLICE`. Its tests (`tls/tests.rs`) build Ed25519 certificates with ring at run time (no key material in the repository) and serve them from a rustls server on loopback, TLS 1.3 and 1.2.
- **Reboot = event** (`state::reset_to_event`): a boot later than the state file, or REAPER/the app running without an engine, drops a pending switch and sets `event`. Every waiting step takes the `Cancel` token and returns `Preempted` within 1 s; only mutating steps (a save, a quit, a registry write) finish first.
- **Guard pipe writes** (`pipe::bounded`): every reply and subscriber update goes out bounded by `pipe::SEND_TIMEOUT` (2 s, inside `LAST_REPLY`): the Unix send timeout set at accept, on Windows `iem_win::pipe::write_within` (`pipe/win.rs` `Bounded`, excluded from mutation), never `&Stream`, whose Windows writes wait without a bound and mark the stream for interprocess's flush on drop (limbo): one linger thread per process whose `FlushFileBuffers` waits for each client to read everything, so one tray or HIL client that stops reading would keep every later close open (the engine's pipes met it, CI run 36373563262). A client that takes nothing is dropped; a dropped connection closes at once and its client still reads the reply, then the end (`pipe::tests` `a_client_that_does_not_read_holds_up_no_close`, Windows; `a_subscriber_that_does_not_read_is_dropped_within_a_bound`). The supervisor connection's sends to the engine go through the same `pipe::Bounded` with `win::engine::SEND` (1 s): a hung engine fails the send instead of holding the daemon thread (the "ide event" `EngineStop` then goes to `on_error`: `EngineHealth`, `KeepServing` or `StopAskOwner`), and the connection counts as closed, so the next step connects again (`win::engine::tests::a_send_to_an_engine_that_does_not_read_fails_within_a_bound`). `iemmode` and the tray keep interprocess's writes: the guard reads everything they send.
- **The guard pipe's frame is 256 KiB (S7, #10; `proto::MAX_FRAME`).** A reply carries every kept alarm (`Alarms::KEEP` 50 × `ALARM_CHARS` 600 characters), the `DETAIL_CHARS` (8000) detail and, since S7, the engine's two histograms (up to 1001 buckets each at the 1 ms cap, ~28 KB each). Non-ASCII text alone already passed 64 KiB, and a reply over the cap is never written: `iemmode status` and the reply of `iemmode event` would fail. `proto::tests::the_largest_reply_fits_a_frame` writes and reads back the largest (four-byte characters, the longest step name, every step, 8 spare outputs, both histograms as long as the parse reads them, the engine's counters at their largest, an unwound `last_switch` of `2 × Step::ALL` steps): ~218 KB, above 64 KiB, ~44 KB left for later fields. **Control characters:** JSON escapes a C0 control character to six bytes, so `daemon::cut` (the one place alarm texts and reply details are cut, by characters) makes every one but `\n` and `\t` a space (S7 Task 3 review: text of them reached ≈ 291 KB); the test writes the reply a second time with C0 text through `cut`. The four-byte character stays the longest a text character can be. Not taken: a separate request for the histograms (one more request type for one reader, the soak; the reply already carries the engine). **Version skew:** an `iemmode` or tray older than the cap refuses a frame over 64 KiB (`FrameError::TooLarge`; the tray then shows no guard and retries every 2 s). `activate` copies the bins before the hand-over, so a bundle's own `iemmode` and guard never mix. The dev box's admin-only `iemmode` can lag a build another path activated (`hil-v1.ps1`): `iempc_bin.pick` runs it only while the guard last seen runs the recorded build (the guard's `guard_build`, below; #15, the last lane, item 4), else `PC_BIN`'s, which `activate` copied with the guard's bins, until the next `iempc activate`. Only a build change this box neither dispatched nor activated can make the older copy run, for the one call whose reply names the new build; such an older `iemmode` fails only on a reply over 64 KiB (at 32 samples a histogram has at most 668 buckets, so it takes many long alarms).
- **Switch record (S7, #10; `switch_log.rs`, pure, mutated).** Every switch that ends leaves `GuardState.last_switch` (`LastSwitch`: `from`, `to`, `ended_in`, `outcome` (`done`/`kept_serving`/`needs_owner`; a newer guard's reads as `unknown`), `started`/`ended` in epoch seconds, `steps: [{step, ms}]`, `silence_ms`), saved with the state. A reset leaves it as it is, but the start's checks that follow a reset (`daemon::start`) are a switch of their own (event → event), so after a reboot the record is theirs. A step's time runs from the end of the step before (the switch's start for the first) to its own end (`daemon::switch` laps every step, failed ones too, and the `EngineHealth` read `failure` inserts after a failed `EngineStop`; the rehearsal's teardown, no switch, is not timed), so the steps add up to the switch and the state save between two steps counts toward the second. The in-ear silence (`switch_log::silence_ms`) runs from the first of `EngineStop` (the engine's fade-out) or `ReaperSaveQuit` through `ReaperHandover` (to event) or `EngineArm` (to dev or live), both included; none when either end is missing (nothing went quiet, or the plan stopped before the other side played). An unwound dev or live entry and its unwind leave one record (S7 part 3, #10 2026-10-07): `back_to_event` notes the failed or pre-empted entry's target and `Switching.started` (`Guard.unwinding`), the unwind's `begin` resumes the clock (`Laps::resume`) instead of starting it, and `finish` builds the record with `unwound` (the entry's target) and the entry's `started` (`LastSwitch::unwinding`), then clears it; `from`, `to` and `ended_in` stay the unwind's (`to` event). Its steps are the entry's, the failed or pre-empted step included, then the unwind's, on one clock, so the window runs from the entry's `ReaperSaveQuit` (or `EngineStop`) through the unwind's `ReaperHandover`; an entry that armed the engine before it failed counts the time the engine played as well (an upper bound). Every other switch (the watch's crash fallback, the start's checks, the switch after an unwind) has `unwound` none; an older guard's record without the key reads as none. `Laps` is not persisted: a restarted guard re-plans to event and times that switch. `Reply.last_switch` (absent before the first switch and from an older guard) is in every reply, the daemon's and the view's, so `iemmode status` prints it; `iempc switch-test` (S7 part 3) reads it. Both reads go through `switch_log::lenient`: a record this guard cannot read (another shape, a step it does not have) is none, never an unreadable state or reply.
- **`iempc switch-test` (S7 part 3, #10; `iempc_switch.py`, iempc.py keeps the call site only).** Dev time, locked, a PC command.
