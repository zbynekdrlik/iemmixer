# Guard, iemmode, PC install (S6, #9)

Design note `docs/superpowers/specs/2026-09-27-s6-asio-guard-hil-design.md`, plan `docs/superpowers/plans/2026-09-27-s6-asio-guard-hil.md`.

- **Preference window (I2; #9 2026-09-28).** The preference holds 32 while the engine holds the card, REAPER's original at every other moment (a write while the driver is open most likely makes it ask for a reset: the first run on the PC faulted on its reopen budget). `iem_win::prefwin::Window` (`Original`/`Held`): `enter` Original → Held needs the recorded original in the store and writes 32 with its kind (a failed write still leaves it Held); Held → Held (a reopen) only reads 32 back and writes nothing; anything else refuses without a write (`NotOriginal`, `NotHeld`). `leave` Held → Original writes the original (a failure stays Held); Original touches nothing. Both read back. `AsioStream` leaves only where the card is released and no open follows (`.claude/rules/asio-spike.md`); a parked stream keeps 32. A hard kill, a power loss or an OS restart while the engine holds the card leaves 32: the guard's `PrefCheck` precedes `ReaperStart` in every plan (every event plan has it) and every engine start: `EngineStart` in every dev/live entry, the crash watch's `respawn` and `restart_in_job` (#9 2026-09-28, `a_respawn_restores_the_preference_right_before_the_engine_starts`, `a_job_restart_restores_the_preference_right_before_the_engine_starts`; a failed check starts nothing: respawn alarms like a failed start, the job restart unwinds). It is `prefwin::check(.., pc::PREF_ATTEMPTS, holders)` — an engine's 32 is a restore, never a refusal (`restore_takes_back_the_frames_of_an_engine_that_ended_holding_the_card`) — and **never writes while a process holds the driver module** (#9 2026-09-28: the holder's driver would most likely ask it for a reset, a REAPER at an event would drop out). The holders are read only when the value is not the original (`pc::card_holders`: anything counts, our engine too; unreadable → a running REAPER is assumed to hold it, as `facts_from` does). The result is `pc::PrefSeen`: `Original(writes)` or `Held(PrefHeld)`; in the event plan `Held` is no failure (alarm once per value, `PrefCheck` step, no owner question; `GuardState.pref_held` persists it, `iemmode status` names it, a reset keeps it, a check that finds or restores the original drops it; the dev entry's check after `ReaperSaveQuit` restores it), before an engine start it fails the step. After three failed restores at an event it follows `[guard] on_pref_fail` (`start_reaper_with_alarm`, recorded on #9). The elevated logon task (`iemmixer-logon`, G1) restores it by the same rule (#9 2026-09-28): `Restore-IemPref -Module` decides with the pure `Get-IemPrefAction` (`none` at the original, holders not read; `restore` while nothing holds the module; `held` while anything does, never written; an unreadable list (`$null`) assumes a running REAPER holds it) and reads the holders with `Get-IemModuleHolders` only when the value is not the original. A `held` run succeeds and its `logon.result.json` names it (`result.pref`: `action`, `before`, `holders` as `image:pid`); the guard takes each run once (`GuardState.logon_seen` = its `at`) at its start (before the event plan) and in the hourly look (`effects::tuning::logon_result`, REAPER known by `pc.toml`'s image, any case, ".exe" or not): `held` → `pref_held` with `PrefCheck`'s text, one alarm `logon task: …`; a run at the original drops `pref_held`; a failed run is logged. Residual risk (design §11): before cutover the guard does not start at boot, so a REAPER autostarted by the predecessor can open the card at 32 before the logon task restores it; the logon task and the guard then leave it at 32 until REAPER quits (named, one alarm).
- **Stops are requests plus a bounded wait, then an alarm (I8).** `iem-engine interlock` stops at its `--stop-file` (`<root>\guard\interlock.stop`, seen within 0.1 s, exit 6), never Ctrl-Break (its default handler would end it with the card open). Engine `Shutdown` (supervisor pipe), server and runner Ctrl-Break delivered to their own console (`iem_win::console::ctrl_break`: under a process-wide lock detach, attach to the child's console, ignore Ctrl events, send `CTRL_BREAK_EVENT` to its group, detach, restore), tray `Quit`, REAPER 40026 then 40004, the predecessor app through its tray Exit command. The integrity scan refuses force-end verbs everywhere, comments included (Rust/tokio/Python/.NET kill methods, also named in `ForEach-Object`; job-close kills; WMI/CIM Terminate by `-MethodName` or `-Name`; wmic terminate/delete; tskill, pskill; `CREATE_BREAKAWAY_FROM_JOB` outside `crates/iem-win/`); write "force-end" in prose.
- **Children and the guard's job** (`iem_win::spawn`, `decide::placement` mutated; #9 2026-09-28: the PC's task job allows no breakaway, EngineStart failed with "Access is denied. (os error 5)"). Every long-lived child (engine, server, tray, runner, the interlock, a direct REAPER or app start, a hand-over's new guard) goes through `spawn_detached`, which reads the immediate job (`job_limits`: `IsProcessInJob`, then `QueryInformationJobObject(JobObjectExtendedLimitInformation)`; a nested job's parents are not read) and places the child, never by trial: no job or silent breakaway → no flag; breakaway allowed → the flag; neither, and the job does not end its processes when it closes → inside the job (`Pc::job` logs the reading at the guard's start, `iemmode status` names it: `pc::JOB_NOTE`); neither, and it does → refused (`PermissionDenied` with the reason = the step's error, the error policy unwinds). That limit is `spawn::JOB_ENDS_ON_CLOSE` (winnt.h 0x2000): its Win32 name matches the integrity scan's force-end verbs, so code never spells it. Helpers (`helper_flags`) stay in the job. On the hosted runner cargo's own job refuses the start, so `tests/spawn_job.rs` nests its process in a job without limits to run the in-job start (the nesting lasts for the process: one test per binary).
- **Planner invariants** (`plan::plan`, pure, mutated): on dev/live entry the app stops before REAPER saves (a phone cannot dirty the project between save and quit); the interlock runs whenever REAPER or the app runs, from any mode; `PrefCheck` before REAPER in every event plan, after `HolderGone` (the check never writes under a holder, so it must not meet one the plan could have waited for; #9 2026-09-28), and exactly once, right before `EngineStart`, in every dev/live entry (after REAPER quit and our engine stopped: never while REAPER may hold the card, whose driver would see the write; #9 2026-09-28, `every_entry_restores_the_preference_right_before_the_engine_starts`); the S1c fingerprint last (alarm only); a REAPER without the card or an app not serving is restarted. **Error policy** (`plan::on_error`): every dev/live entry failure unwinds, its `PrefCheck` included; `on_pref_fail` is the event plan's rule only; a failed engine release at "ide event" never tears down a healthy iemmixer (keep serving, alarm, the owner's prepared ❓); a dead or parked engine stops the plan (no REAPER while the card may be held, no app without REAPER).
- **Alarm recipients** (`pc::precheck`, mutated; #9 2026-09-28): ≥ 1 alarm recipient (`iem-server notify --count alarm`) is required for `live` and trials only. The alarm link (`/alarms`) is served by iem-server, which runs only in dev and live (in event the predecessor holds the band's address), so the owner can open it only after the first dev entry. A dev entry without one (or with unreadable recipients) goes on and names it: in its report (`--dry-run`: `precheck ok; <note>`) and in `iemmode status` (`Guard.recipients_note`, until the next precheck or an alarm notice reaches a phone, e.g. `iemmode alarm-test`); the alarms stay in the guard's alarm file, which the agent reads. Another precheck refusal still refuses a dev entry.
- **LAN 443: identity, not validity** (`tls::check`, mutated; #9 2026-09-28: curl's schannel refused LAN 443 with `SEC_E_CERT_EXPIRED`, and the predecessor serves the same expired certificate). IdentityCheck's LAN 443 runs the guard's own rustls client (ring, as iem-server; never native-tls): SNI = `[guard] public_host`, any chain and validity, the handshake's signatures verified with the served leaf's key (`SignaturesOnly`), the leaf byte-equal to the first certificate of the server's `cert.pem` (`effects::web::server_cert`: the server config's `tls_cert` next to it) before anything is sent, then an HTTP/1.0 `/api/version` naming the bundle. A certificate outside its validity is `Guard.lan_note` ("the LAN certificate expired on <date>; the predecessor serves the same one": the report once, `iemmode status` until the next identity check), never a failure or an alarm; the public host stays curl's validated check. The check runs on a thread bounded by `Lan::limit` (a timed-out socket is never reused); "ide event" returns within a `Cancel::SLICE`. Its tests (`tls/tests.rs`) build Ed25519 certificates with ring at run time (no key material in the repository) and serve them from a rustls server on loopback, TLS 1.3 and 1.2.
- **Reboot = event** (`state::reset_to_event`): a boot later than the state file, or REAPER/the app running without an engine, drops a pending switch and sets `event`. Every waiting step takes the `Cancel` token and returns `Preempted` within 1 s; only mutating steps (a save, a quit, a registry write) finish first.
- **Guard pipe writes** (`pipe::bounded`): every reply and subscriber update goes out bounded by `pipe::SEND_TIMEOUT` (2 s, inside `LAST_REPLY`): the Unix send timeout set at accept, on Windows `iem_win::pipe::write_within` (`pipe/win.rs` `Bounded`, excluded from mutation), never `&Stream`, whose Windows writes wait without a bound and mark the stream for interprocess's flush on drop (limbo): one linger thread per process whose `FlushFileBuffers` waits for each client to read everything, so one tray or HIL client that stops reading would keep every later close open (the engine's pipes met it, CI run 36373563262). A client that takes nothing is dropped; a dropped connection closes at once and its client still reads the reply, then the end (`pipe::tests` `a_client_that_does_not_read_holds_up_no_close`, Windows; `a_subscriber_that_does_not_read_is_dropped_within_a_bound`). The supervisor connection's sends to the engine go through the same `pipe::Bounded` with `win::engine::SEND` (1 s): a hung engine fails the send instead of holding the daemon thread (the "ide event" `EngineStop` then goes to `on_error`: `EngineHealth`, `KeepServing` or `StopAskOwner`), and the connection counts as closed, so the next step connects again (`win::engine::tests::a_send_to_an_engine_that_does_not_read_fails_within_a_bound`). `iemmode` and the tray keep interprocess's writes: the guard reads everything they send.
- **REAPER's dialogs** (`handover::dialogs`, mutated; #9 2026-09-28): `iem_win::window::dialog_titles(pid)` gives the titles of REAPER's visible top-level `#32770` windows. Only a title starting with `EVALUATION_NOTICE` (`About REAPER`, REAPER's own text) is its evaluation-license notice, shown at every start of an unlicensed REAPER, which runs normally with it (audio, web control, 40026/40004): the handover names it (`NOTICE_REPORT`, `reaper_notice: "evaluation"`, in the switch report and in `iemmode status` until the guard quits REAPER or a check cannot read it), never alarms on it and never closes it. Every other visible REAPER dialog blocks as before: the handover alarm, and `save_quit` stops during or after 40026 (no 40004); the titles go to the PC log only. An ssh shell (session 0) sees no windows, so only a guard in the console session sees the notice. `GetWindowTextW` sends no message to another process's window but `WM_GETTEXT` to our own: the Windows test creates and reads its dialogs on one thread, and no other test reads its own pid's dialogs.
- **Predecessor exit** (`handover::app_exit`, `app_binary`): the exe SHA-256 equals `[guard] app_exe_sha256` at the precheck, before REAPER is touched; the process handle is opened before the tray command is posted, then exit code 0 within 30 s, ports 80/443 free, no newer temp file; the log line only corroborates. Anything else aborts the switch and restarts REAPER.
- **Site values** live only in the ops `site.toml` (`[card]`, `[guard]`), `~/.config/iemmixer/iem-pc.env` and the ops runbook: driver name and module, preference key, task paths other than `\iemmixer\…`, the predecessor's process names, exit command id and exe hash, hosts, channels. Tests use `Test Card`, `testcard.dll`, RX 101–132, TX 71–93, HIL's spare TX 94/95, exit id 4242.
- **Dev box (`scripts/iem-pc/iempc.py`).** "ide event" → `iempc event`: it writes `~/.config/iemmixer/EVENT-NOW` first, pre-empts an open S1a/S1c window (`spike_window.py preempt`), runs `iemmode event`, and `iemmode event --direct` when the guard is unreachable (exit 4). This is the one switch-over rule from S6 Task 16 Step 3 (guard installed) on; before that the interim switch (`CLAUDE.md`). Every other PC command refuses while the flag exists; every wait sees a new flag within 2 s. HIL is dispatched from the dev box (`iempc dispatch-hil`), never from public CI.
- **PC tasks (`IemPc.psm1`, Windows PowerShell 5.1).** `Register-IemTasks` (`-Module` = the `[card]` driver module, mandatory since #9 2026-09-28: the logon task's command line carries it) registers the guard, StartApp, probe, tuning, exclude and logon tasks under `\iemmixer\` via `Schedule.Service` (Interactive, `PT0S`, IgnoreNew, no idle/battery stop, restart 3 × PT1M, priority 4, never ended hard) with `D:(A;;GRGX;;;<user SID>)(A;;FA;;;BA)(A;;FA;;;SY)` and `TASK_DONT_ADD_PRINCIPAL_ACE` (0x10: without it the service adds its own ACE for the user and the read-back refuses), then sets it again on every task with `IRegisteredTask.SetSecurityDescriptor(sddl, 0x10)`: an update (`TASK_UPDATE`) keeps a task's old descriptor. The read-back (`Test-IemTaskSddl`) wants exactly those three explicit ACEs, in the generic or file form of their rights; ACEs inherited from the task folder (`ID`, the real Task Scheduler prints `D:AI…(A;ID;0x1f019f;;;BA)(A;ID;0x1f019f;;;SY)(A;ID;FA;;;BA)`) pass only for Administrators and SYSTEM, any other inherited ACE, a deny or an object ACE refuses. Test such SDDL with the synthetic user SID, never `LA` (`RawSecurityDescriptor` resolves it to the machine's administrator). `iemmixer-StartREAPER` predates S6: it is never registered again, it only gains the descriptor; without it nothing is registered. The root's and the elevated folders' DACLs are protected, so their read-back stays exact (an inherited rule is a difference). Setting the root's DACL does not fix what already exists below it (CI run 36366619573: an existing file failed its read-back afterwards, the log does not show its rules; by design Windows' propagation keeps an item's own rules and passes nothing into a protected item), so `Set-IemRootAcl` reads every item below back (`Test-IemRootTree`: nothing of its own, exactly the root's rules inherited), resets each one that differs with an empty unprotected DACL `D:` (`Reset-IemInheritedItem`, icacls /reset for one item), parents first, and returns `reset` and `differed` (what each held before its reset); `Get-IemBootstrapState`'s `root.acl_ok` covers the same tree. Setting a folder's DACL makes Windows propagate to what lies below, and whether that goes through a junction is not relied on: `Set-IemRootAcl` walks the tree for a junction or link (`-LinksOnly`, no DACL read) and refuses one before it writes anything, and `Reset-IemInheritedItem` (`-Root`, `-Rel`) checks every path part from the root down right before its write (by path, so only the moment of use is left open). A self-test of "refuses X and changes nothing" sets X up where a write would otherwise happen (a loosened root, a folder with a rule of its own), else it holds trivially.
- **The elevated root** (`%ProgramData%\iemmixer`, resolved by `Register-IemTasks` from the known folder and written into each Highest task's command line (the entry script's path and `-TuningDir`); the elevated process never reads an environment variable for a path). Every folder (`tasks`, `tasks\out`, `tuning`) is owned by Administrators with a protected DACL (Administrators and SYSTEM full, the user read and execute), created with its security in one step; an existing folder owned by anyone else, or any junction or link, is refused. Our files are written fresh and owned by Administrators; everything reads back (`Test-IemElevatedItem`). `iem-task.ps1` pins `PSModulePath` to `$PSHOME\Modules` and Program Files first. The tuning task imports S1c's `IemTuning.psm1` only when the tuning folder, its parent, the module and `profile.json` pass that read-back; until they exist it answers `absent`. The guard writes `<root>\guard\tasks\<kind>.request.json` (`tuning`: `{id, verb}` of enter/exit/state/apply-tier2; `exclude`: `{id, sha, keep}`), read elevated only if no path part is a junction or link (at most 64 KiB, never echoed); the task writes `<elevated root>\tasks\out\<kind>.result.json` (`{kind, id, ok, at, result, error}`), which the user may only read: an elevated process never writes into the user's root. The guard (`effects::tuning`, `win::tasks::elevated`) writes the requests, waits for the answer with its id, and takes the elevated root from `pc.toml` `elevated_root` (default `C:\ProgramData\iemmixer`, what `Register-IemTasks` resolved), never from an environment variable; `exclude`'s `keep` is the other pin. S1c's record for the drift check is `<elevated root>\tuning\expect.json`.
- **PowerShell rules.** 5.1 syntax only (no `?:`, `??`, `&&`, `||`), ASCII files, `Set-StrictMode -Version Latest` (read parsed JSON through `Get-IemProp`), `"${name}:"` or `-f` where a colon follows a variable, one native command per CI step. `Test-IemPc.ps1` (the `windows` job) parses every script in the folder and runs the functions against real backends on the runner: a `\iemmixer-test\` task folder, a temp root, an HKCU test key, a disabled test firewall rule, a test service; Defender and the runner with `-WhatIf`; hil-v1.ps1 end to end against a fake `iemmode`.
- **Activate per mode** (`plan::activation`, mutated; #9 2026-09-28): `dev` as before (inside a HIL job `restart_in_job` first); `event` only while no engine, server, tray or runner runs (the process list) and no switch, HIL job or interlock retry waits (a hand-over's new guard starts in event and drops a retry, `state::reset_to_event`), and then it only copies the bins, pins, asks the exclude task and hands over: no call to REAPER or the app (the daemon test asserts the calls are exactly `Facts`, `SetBundle`, `Exclude`), and the new guard's start runs the event plan's checks as after any restart; `live` refused (`live --build`). It is how a guard fix reaches a guard in event, whose own code runs the dev entry's precheck: `iempc install`, `iempc activate` (in event), then `iempc dev`. Every reply carries `guard_build` (`proto::GUARD_BUILD`, a const from CI's `GITHUB_SHA`, "local" otherwise; absent from an older guard), from the daemon and from the view; `iempc activate` polls `iemmode status` until it names the SHA (`HANDOVER_S` 90 s, a failed read is read again, a new flag ends the wait and runs the event path). A guard built before the rule refuses `activate` in event: then `iempc activate --offline` quits it gracefully (`iemmode quit`, its processes read until none runs, `QUIT_S` 60 s, never forced) and runs the bundle's own `bundles\<sha>\iemmixer-guard.exe activate <sha>` (sha256 checked against the fetch record) = `daemon::activate_offline`: the guard's mutex for the whole run (held by a guard: refused before anything is read), the saved mode must be event, then the same rule on the saved state and the process list, then `activate_bundle` (bins, pin, exclusions through the same elevated task, saved; logs into guard.log), one JSON line, no guard started. The first `iemmode status` then starts the guard's task (the new exe) and the `guard_build` wait runs; a refused offline step starts the guard again.
- **Bundles (P5/G8).** The `bundle` job builds the release binaries (the server with `standalone,tls,audio` and the real UI), zips them with `hil-v1.ps1`, `IemPc.psm1`, `LICENSE-iem-engine`, `manifest.json` and `SHA256SUMS` (one level `tuning/<name>` allowed), runs the fresh guard's `install <zip> --verify-only` and refuses a tampered copy; it uploads only on a push to dev/main; `attest` attests the zip by digest. `iempc fetch-bundle` needs a green push run with both jobs and `gh attestation verify`. `bundle.rs` is the reference for `SHA256SUMS` names; `iempc.py` and `Test-IemBundleSums` are stricter (only `[A-Za-z0-9_.-]`, one level).
- **HIL v1 (`hil-v1.ps1`).** Runs from the verified `bundles\<sha>\` (it refuses elsewhere): job-begin → activate → checks → job-end → report → `result.json`. A refusal once the guard left dev is `cancelled` (no report); exit 1 only for `failure`. The `summary` is public (the ops report job posts it as `hil/iem-pc`, P6): check names, counts and a fixed cancel phrase by reason code (`left-dev`, `not-free`), never free text; the guard's text goes to `why`, details to `checks`, both private. The engine checks read the guard's `Reply.engine` (`iem_guard::EngineStatus`: `build`, `frames`, `callbacks`, `missed`, `resets`, `parked`, `faulted`, `pipe_private`, `spawns`, `last_exit`, `hil`; f64 peaks, so the reply types are `PartialEq` only) from `iemmode status`; the panic check drives `iemmode inject-fault` (`Request::InjectFault`) and wants exit 70, one respawn and the new engine streaming at 32. The guard fills `Reply.engine` from its supervisor connection (`Pc::engine_seen`: the hello's commit as `build`, the newest `Status`, the control pipe's DACL read once per engine process with `iem_win::token::sddl_is_private`), its own engine starts (`spawns`) and the watch's last exit code; `None` while no engine of ours runs and until the connection holds the hello and a `Status` (`effects::engine::seen_status`: an engine coming up is absent, never zeroed). So HIL v1 never reads a status once after a fixed sleep: `Wait-HilEngine` polls `iemmode status` (500 ms, at most `-EngineWait`, 30 s) until `Test-IemHilEngineUp` holds (frames 32 and callbacks above a mark; the bundle's build after activate, before engine-build and card; one more reset after force-reopen; callbacks above the respawned engine's first status after the fault), then the check judges the last status. A HIL job (`GuardState.job`, persisted, so a hand-over to a new guard exe or a restart keeps it; cleared whenever the mode leaves dev) starts every engine with `site::HIL_FLAGS` (`--test-signal --fault-injection`; never in live, refused in `pc.toml` `engine_args`); inside a job `activate` and `install-site` restart only the engine and the server (`daemon::restart_in_job`: a dev entry would stop the runner that runs the job), and `force-reopen` is the engine's supervisor `force_reopen`; `rehearse-teardown` is refused inside a job like `runner-stop` (its dev re-entry cancels the jobs and stops the runner). The job's 300 s of band quiet is `WinPc::quiet`, one `Quiet` per guard fed by every supervisor connection: a new connection keeps it when the last meter frame came at most `QUIET_GAP` (60 s) before (`Quiet::resume`), else it starts again, and `quiet_for` reads it only once this connection heard the stage (`Quiet::heard`); a hand-over to a new guard exe starts it again. The supervisor connect opens `\\.\pipe\<engine_pipe>` with interprocess's named-pipe connect and `ConnectWaitMode::Timeout(200 ms)`: its local-socket connect ignores `ConnectOptions::wait_mode` on Windows (2.4.4) and waits for a free instance forever; `seen` makes one attempt per look, `supervisor()` repeats them until the step's limit. `[guard] hil_tx` are HIL's spare card outputs, never a channel a band member hears (owner, #9 2026-09-28): `iem-engine check-site` (so install-site) refuses a mix's TX, channel 0, a repeat or more than 8 (`Topology::hil_outputs`, `SiteError::HilTx`); `[engine] channels` is no bound (not the card's output count), the card's own count is checked when the engine opens the stream (exit 3); the engine refuses a `card_tx` that names a mix's TX and keeps every mix's TX and both listen taps silent while the signal runs. The test-signal check reads `Reply.engine.hil` (each spare output's peak since the engine's previous `Status`, about once a second): `Wait-HilSilence` polls `iemmode status` every 500 ms from the signal's start until the TTL ran out and then, at most `-EngineWait` more, until a status shows all of them silent after one that carried the signal (`Test-IemHilSilent`, `Test-IemHilHeard`; a silent status before that may cover the time before the signal). Every status read before that silent one counts, since a short TTL's signal may show only in a `Status` after it: every spare output at the asked level within 0.5 dB, the last status silent (`Test-IemHilSignal`). The fake's `heard_from` proves it (Test-IemPc). Inputs are refused before any call: `-TestDbfs` above −20 dBFS, `-TestTtl` outside (0, 60] s (the guard's `HIL_MAX_TTL_S`). Not in HIL v1: the pipes' first-instance flag, the tunnel peer, the reopen's duration, the fault callback's time (plan Task 10 Step 6).
