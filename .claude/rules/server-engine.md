# Server ↔ engine (S5): ids, domains, echoes

- **The server is the engine's one controller** (`engine/client.rs`, role `control`). It connects to the control pipe (Unix socket path / Windows pipe name `engine_pipe`, override `IEMMIXER_ENGINE_PIPE`) and the media pipe `<pipe>.media` with plain tokio sockets — never with `interprocess`'s tokio feature: it would unify into the engine's dependency closure (`scripts/check_engine_deps.py`).
- **Ids, not indices:** UI protocol v2 (`iem_core::ws`, `UI_PROTO = 2`) keys every channel by the engine id (inputs and heard mixes share one namespace); `State{mix, group}` names the page's mix and the stems group. The site's `[[members]]` / `[[inputs]]` tables only add names, categories and owners; an id the topology lacks is left out, never guessed (`site_view.rs`).
- **Domains (`view.rs`):** fader −60 dB = off (`DB_OFF` −150 in the engine); UI pan 0…1 ↔ engine −1…1 (`ui_pan` / `engine_pan`), converted only there. EQ values are the engine's (freq_hz, gain_db, bw_oct); no normalised values anywhere.
- **Read-modify-write waits for the mirror:** an edit that builds on the current value (EQ band, preset ramp step) uses `request_applied` — `request` returns at the reply, before the delta reached the mirror.
- **Echoes:** a change carries its WS session as `origin`; that session gets no updates for it (it applied the change optimistically) except the channel mutes a solo change shows (`mixer_ws::own_echo`), because the mask is the server's view. A change with `origin: None` (preset ramp, Mute All, restore) reaches every session.
- **Solo** is the engine's transient mask, shown as each channel's mute (`muted = level.muted || masked`). A mute click on a masked channel changes the level's own mute but stays silent until the solo ends (UI `MuteClick::Masked`). 10 s after a member's last socket closed, the server clears that mix's solo.
- **Talk lock (X6):** `TalkStart` → `TalkAcquired{talk_id}`; `/ws/talkback` binds only with the held id within 1 s; released on `TalkStop`, the holder's mixer socket closing, or 2 s without frames.
- **History ids (F14):** an entry's timestamp (seconds) is its id for restore, pin and delete. `BandStore::add_snapshot` stores an entry whose second is taken under the next free one and returns it; `POST /api/snapshots/<member>` answers that id, never the clock's second.
- **Tests run the real engine:** `engine/testkit.rs` (`EngineHarness`, `#[cfg(test)] #[cfg(unix)]`) runs `iem_engine::engine::run` on NullRt with the test site; `engine_live_tests.rs` drives it through `AppState`, `routes_live_tests.rs` through the HTTP routes (`routes::api_tests::{router, call, token}`), and modules test their own private handlers in a `#[cfg(unix)] mod live` inside `tests` (`mixer_ws::handle`, `listen_ws::start`/`stop`). Engine tests are Unix-only: the `windows` job compiles every test (clippy `--all-targets`), so they and their imports stay behind `cfg(unix)`. `iem-engine` is a dev-dependency only — the server binary never links the GPL engine.
- **Band activity (§4.2, S6):** only the stage inputs count — `[activity] inputs`, or every `mics` input when the list is empty; the program input carries signal while the band is silent (S1a). `console::ActivityWatch` resolves the watched indices (`activity::watched_inputs`) whenever the site view changes (a new topology) and logs listed ids the topology lacks; `meters::max_watched_peak` feeds `BandActivity`.
- **Graceful stop (S6):** the binary installs SIGTERM/SIGINT (Windows: Ctrl-Break/Ctrl-C, which the guard delivers to the server's own console) before it binds, then `start_server_until(…, stop)`: the HTTP listener and, with `tls`, the HTTPS one (its `axum_server::Handle` gets `graceful_shutdown(Some(STOP_DRAIN))` in the same stop future) close at once, open requests on either get `STOP_DRAIN` (5 s), and the HTTPS task is awaited (bounded) before it returns; exit 0. Only then the runtime's `shutdown_timeout(1 s)` ends the engine client, the backup daemon and the tunnel watchdog — a server task still serving at that point would be cut, so every listener takes the stop. `start_server` (the tray) runs until the process ends. Test: `tests/graceful_stop.rs` (Unix; the signal is sent with the `kill` utility — a request, never a force-end; the HTTPS cases make a self-signed certificate with `openssl` next to the site file: `tls_cert`/`tls_key` resolve against the server's config directory, the site's folder, where `iem-migrate band` writes them on the PC). The Windows Ctrl-Break test of the server joins the `windows` job once `iem-win` exists (plan Task 12).
- **Alarm link (S6 bootstrap):** `iem-server alarm-link [--ttl-h 24]` (1–168 h) writes `alarm_link.json` next to the site file — the base64url SHA-256 of one 128-bit token and its expiry, never the token — and prints `<base>/alarms?t=<token>`, the base being `https://<https_domain>` or else an `https://` `lan_url` (`alarm_link::link_base`; an http-only site is refused: Web Push needs a secure context); a new link replaces the old. `POST /api/alarms/subscribe {token, subscription}` is public (the token is the credential, body ≤ 4 KiB): an incomplete or non-`https://` subscription is 400 and leaves the token; a wrong, expired or used token is 403 (constant-time hash compare); the link file is removed **before** the subscription is appended to `alarm_subscriptions.json` (atomic write, dedup by endpoint), so a token opens once even for concurrent posts (`removal_verdict`: a file already gone is a used link, 403), and a failed store after that is 500 with a used link (ask for a new one); an unreadable recipient file is an error, never overwritten. The UI page `/alarms` (route before `/:member`) asks for the notification permission inside the click, subscribes through the service worker's `PushManager` and posts; E2E `alarm-link.spec.ts` stubs `PushManager.prototype.subscribe` (incognito has no Push API). On an iPhone or iPad browser tab (`ios_tab`: not `navigator.standalone`) the page shows a hint instead of the button — iOS gives Web Push only to Home Screen apps, and a link from a message opens in Safari — so confirm the owner's phone before sending the link.
- **Two push audiences, never mixed (P9, design note §5.4):** the engineer's devices (`push_subscriptions.json`) get SOS and the band-activity notice (`console::activity_changed` → `notify::push_engineers`); the alarm recipients (`alarm_subscriptions.json`, the owner's phone) get only technical alarms: the guard's through `iem-server notify --to alarm <title> <body>`, and the running server's refused scheduled backup (`backup_daemon::settle` → `notify::push_alarm`, once per distinct error until a capture succeeds; an alarm that reached nobody is tried again at the next refusal). `--to band-activity` reaches the engineer's devices only; no other audience exists (the old `notify <title> <body>` is a usage error, exit 2). Exit 0 when a device took it, 3 when none did (no recipient of that audience, or every push failed — the guard sees an alarm that reached nobody), 1 on an error; `iem-server notify --count alarm` prints the number of alarm recipients (the guard's precheck needs ≥ 1 for `live` and trials; a `dev` entry only names a missing one, `guard.md`) and only reads. `notify::load_alarm_recipients` treats an unreadable or unparsable file as an error, never as none.
- **Notify mode reads, never prunes:** `notify::run_cli` reads one audience's store and sends; an expired endpoint is only logged (the running server's `push_engineers` prunes the engineer store). On a host where the server never ran it writes twice: `secrets::load_or_create` creates `secrets/` with `jwt_secret` and `vapid_private`, and `PushStore::load` (for `--to band-activity`) does its one-time v2 migration (`[]` + marker) — the same writes the server does at its first start.
