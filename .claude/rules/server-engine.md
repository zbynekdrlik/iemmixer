# Server ↔ engine (S5): ids, domains, echoes

- **The server is the engine's one controller** (`engine/client.rs`, role `control`). It connects to the control pipe (Unix socket path / Windows pipe name `engine_pipe`, override `IEMMIXER_ENGINE_PIPE`) and the media pipe `<pipe>.media` with plain tokio sockets — never with `interprocess`'s tokio feature: it would unify into the engine's dependency closure (`scripts/check_engine_deps.py`).
- **Ids, not indices:** UI protocol v3 (`iem_core::ws`, `UI_PROTO = 3`, `MIN_CLIENT_PROTO = 3`; v3 added `LineupChanged` and the close 4003, #58, so a v2 page reloads once at the deploy, never at a switch: #61 review M4; every client that opens `/ws/<page>` sends `proto=3`: the UI, the E2E sockets, the live desk and `iem-soakclient`) keys every channel by the engine id (inputs and heard mixes share one namespace); `State{mix, group}` names the page's mix and the stems group. The site's `[[members]]` / `[[inputs]]` tables only add names, categories and owners; an id the topology lacks is left out, never guessed (`site_view.rs`).
- **Domains (`view.rs`):** fader −60 dB = off (`DB_OFF` −150 in the engine); UI pan 0…1 ↔ engine −1…1 (`ui_pan` / `engine_pan`), converted only there. EQ values are the engine's (freq_hz, gain_db, bw_oct); no normalised values anywhere.
- **Read-modify-write waits for the mirror:** an edit that builds on the current value (EQ band, preset ramp step) uses `request_applied` — `request` returns at the reply, before the delta reached the mirror.
- **Echoes:** a change carries its WS session as `origin`; that session gets no updates for it (it applied the change optimistically) except the channel mutes a solo change shows, on the channels its viewer sees (`mixer_ws::own_echo_seen`), because the mask is the server's view. A change with `origin: None` (preset ramp, Mute All, restore) reaches every session.
- **Solo** is the engine's transient mask, shown as each channel's mute (`muted = level.muted || masked`). A mute click on a masked channel changes the level's own mute but stays silent until the solo ends (UI `MuteClick::Masked`). 10 s after a member's last socket closed, the server clears that mix's solo.
- **Talk lock (X6):** `TalkStart` → `TalkAcquired{talk_id}`; `/ws/talkback` binds only with the held id within 1 s; released on `TalkStop`, the holder's mixer socket closing, or 2 s without frames.
- **A pipe read is never a `select!` branch made fresh each turn** (live run 2026-10-14, a held Talk): `wire::read_frame`/`read_media_frame` read a header and a body in several awaits, so a `select!` whose other branch wins drops the bytes read so far and the next read starts inside a frame (server.log: `media pipe closed error=frame of 31707 bytes exceeds the limit`, a sample count the message called bytes, now `media frame of N samples exceeds the limit`, then a 0.5 s reconnect: talkback and listen gone). `MediaLink::run` keeps one read loop and one talkback write loop for the connection's life and selects over the two whole loops (`talkback_writes_never_cut_a_media_read_short`); a new pipe reader does the same, or reads in a task of its own. Each talkback write is bounded by `TALK_WRITE_WITHIN` (1 s, the engine's send timeout): listen frames no longer end a stuck write, so the limit ends the connection and the reconnect brings talkback back (`a_talkback_write_the_engine_never_takes_ends_the_connection`).
- **A silent client is gone (#10, live run 3; `ws_alive.rs`):** the mixer and listen sessions ping their client every `PING_EVERY` (10 s, `Keepalive`) and end once nothing came from it (a command, a pong) for `SILENT_FOR` (30 s): a warn line `WebSocket client silent: closing` / `Audio WebSocket client silent: closing` with `silent_s` (the listen one also `target`, `hil`), then a Close with `CLOSE_SILENT` (4002, bounded by `CLOSE_WITHIN`, 1 s; the page reconnects on it as on any close and reloads only on 4001). Every send of these sessions is bounded by `SEND_WITHIN` (30 s, `ws_alive::send`): a client that reads nothing would otherwise hold its session inside a send, where no ping is looked at (`WebSocket send stalled: closing`). Browsers, Node's `ws` and tungstenite answer pings by themselves. Why: in run 3 the runner lost sockets on the public path and the server logged no end of their sessions; the lost listen sessions streamed on (their probe edges logged for at least a minute and a half), holding a listen tap, and a lost mixer session keeps its mix's solo from clearing. The page's watchdog (30 s) and the soak client's idle bound are the same rule from the client's side. Talkback sockets are not pinged (their 2 s frame rule ends them). **Not yet proven through the tunnel:** it works only if the Cloudflare edge and cloudflared carry the server's pings to the far end and its pongs back; the next live run confirms it when every far-side close the runner reports is followed, 30–40 s later (silence is looked at on the ping ticks), by a `client silent: closing` line for that session in `server.log`. **Open decision (main/owner):** a phone that stops answering pings (a suspended browser) now has its mixer session ended within 30–40 s, and its mix's solo clears 10 s after the last socket of that mix, as for any close.
- **History ids (F14):** an entry's timestamp (seconds) is its id for restore, pin and delete. `BandStore::add_snapshot` stores an entry whose second is taken under the next free one and returns it; `POST /api/snapshots/<member>` answers that id, never the clock's second.
- **Listen probe (S7, #10; the owner's rule of #9 2026-09-28):** the engine's media streams 2 and 3 (`ENGINEER_PROBE`, `MEMBER_PROBE`: the HIL sine while a `HilTestSignal` with `listen` runs, `.claude/rules/engine.md`) reach only a `/ws/audio` session opened with `&hil=1` (`WsQuery.hil`, `listen_ws::asks_for_probe`; the engineer-only check comes first, as for every `/ws/audio` socket). `engine::media::route` sends them to a probe channel per slot (`MediaLink::subscribe_probe`); each of the four streams has an Opus encoder of its own (`Encoders`, indexed `slot + 2·probe`), and probe frames never count in the listen diagnostics (`Stats`, `frames_forwarded`). `listen_ws::feeds(.., hil)` subscribes the probe for a hil session only: any other session, whatever mix it hears, holds no probe receiver. A hil session's `Feeds::next` takes probe frames first and sends them in place of the slot's own (silent) frames, which `listen_ws::probe_gate::ProbeGate` (`src/listen_ws/probe_gate.rs`, pure) drops until no probe frame came for `PROBE_HOLD` (100 ms); the socket gets `AudioStatus` `probe` before a burst's first frame and `listening` before the first slot frame after it (the UI ignores `probe`). Probe frames reset the session's 5 s no-source timer. Tests: `listen_ws::probe_gate::tests`, `engine::media::tests::{route_maps_0_1_to_the_listen_slots_2_3_to_the_probe_and_nothing_else, probe_frames_reach_only_the_probe_channel_of_their_slot, each_stream_has_an_opus_encoder_of_its_own}`, `listen_ws::tests::{the_query_reads_hil, only_hil_1_asks_for_the_probe, a_socket_without_hil_holds_no_probe_feed, a_hil_feed_sends_the_probe_in_place_of_the_slots_frames_and_names_its_edges}`, and the NullRt `listen_ws::tests::live::a_listener_without_hil_gets_only_silence_while_a_probe_runs_and_a_hil_listener_gets_the_tone` (the burst through `EngineHarness::supervise`, a supervisor connection of its own).
- **Tests run the real engine:** `engine/testkit.rs` (`EngineHarness`, `#[cfg(test)] #[cfg(unix)]`) runs `iem_engine::engine::run` on NullRt with the test site; `engine_live_tests.rs` drives it through `AppState`, `routes_live_tests.rs` through the HTTP routes (`routes::api_tests::{router, call, token}`), and modules test their own private handlers in a `#[cfg(unix)] mod live` inside `tests` (`mixer_ws::handle`, `listen_ws::start`/`stop`). Engine tests are Unix-only: the `windows` job compiles every test (clippy `--all-targets`), so they and their imports stay behind `cfg(unix)`. `iem-engine` is a dev-dependency only — the server binary never links the GPL engine.

Never add a level-based notice or banner back without the owner's word.
- **Graceful stop (S6):** the binary installs SIGTERM/SIGINT (Windows: Ctrl-Break/Ctrl-C, which the guard delivers to the server's own console) before it binds, then `start_server_until(…, stop)`: the HTTP listener and, with `tls`, the HTTPS one (its `axum_server::Handle` gets `graceful_shutdown(Some(STOP_DRAIN))` in the same stop future) close at once, open requests on either get `STOP_DRAIN` (5 s), and the HTTPS task is awaited (bounded) before it returns; exit 0. Only then the runtime's `shutdown_timeout(1 s)` ends the engine client, the backup daemon and the tunnel watchdog — a server task still serving at that point would be cut, so every listener takes the stop. `start_server` (the tray) runs until the process ends. Test: `tests/graceful_stop.rs` (Unix; the signal is sent with the `kill` utility — a request, never a force-end; the HTTPS cases make a self-signed certificate with `openssl` next to the site file: `tls_cert`/`tls_key` resolve against the server's config directory, the site's folder, where `iem-migrate band` writes them on the PC). The Windows Ctrl-Break test of the server joins the `windows` job once `iem-win` exists (plan Task 12).
- **One push audience: the engineer's devices (owner decision, #9 2026-09-28; design note §5.4).** The mixer app (the PWA) on the engineer page subscribes them (`/api/push/subscribe`, engineer only, `push_subscriptions.json`), and `iem-migrate band` carries the predecessor's over with its VAPID keys: the audience the predecessor's alerts reached ("I added the PWA, allowed notifications and everything worked"). No separate alarm list and no alarm link exist (removed on that decision; never bring them back). The devices get SOS and the technical alarms (no band-activity notice, #38): the guard's through `iem-server notify --to alarm <title> <body>`, and the running server's refused scheduled backup (`backup_daemon::settle` → `notify::push_alarm` → `push_engineers`, which returns how many devices took it; once per distinct error until a capture succeeds, an alarm that reached nobody is tried again at the next refusal). `alarm` is the only `--to` (`band-activity`, `alarm-link` and the old `notify <title> <body>` are usage errors, exit 2). Exit 0 when a device took it, 3 when none did (no subscription, or every push failed — the guard sees an alarm that reached nobody), 1 on an error; `iem-server notify --count alarm` prints the number of those subscriptions (the guard's precheck needs ≥ 1 for `live` and trials; a `dev` entry only names a missing one, `guard.md`). Every `ALARM` payload (`notify::alarm_payload`) carries a tag from its text (`iem-alarm-<16 hex>`), which `sw.js` uses: the same notice again replaces itself, a different one shows on its own (`pwa.spec.ts` runs the served worker's push handler). A phone whose last-opened page was the predecessor's app has the predecessor's worker, which shows these pushes as "IEM Mixer — New alert" (its fallback); opening the engineer page while iemmixer serves installs ours again. The predecessor's worker is never changed (predecessor boundary).
- **Notify mode only reads:** `notify::run_cli` and `count_cli` read the store with `PushStore::read`, what `PushStore::load` would find without its one-time cleanup write: no `push_subs_v2_migrated` marker = none (the server's first start empties such a list), no file = none, an unreadable or unparsable list is an error, never none. An expired endpoint is only logged (the running server's `push_engineers` prunes the store). A notice never creates the runtime secrets: no subscription → 0 before any secret is read; a subscription without `secrets/vapid_private` is an error (`secrets::load_vapid`), so a later `iem-migrate band` still takes the predecessor's keys.
- **Roster mode (#58; `iem_core::roster`, `roster_state.rs`, `lineup_store.rs`, `people_archive.rs`):** `AppState.roster` (`None` = legacy mode: the site's `[[members]]`, every behaviour as before) is a std `RwLock` read through `state.roster()`; the active lineup is always `RosterState::lineup()` (main stands in for an unknown id), in the view, `band()`, captures and restores alike. `SiteView::build_with` makes the active lineup's people on their sets (plus the site's engineer entry) the members; a lineup input takes its name and owner, any other keeps the site's label and only an `engineer` owner; a roster set nobody wears in the active lineup is `vacant`, no page. `site()` is cached by (topology hash, roster SHA-256, active lineup); `AppState::band_of(lineup)` keeps one `BandStore` per lineup for the server's life (`lineups/<id>/`, legacy: the config dir) so a lineup's writers share one lock, and `band()` is the active one's: take it per use, never across a switch. Lineup files are written synced, then renamed, the rename tried again (5 × 200 ms) only on a transient Windows error (access denied, sharing or lock violation), never a silent fallback. **Migration** (`migrate_legacy`, call it at every start): "migrated" is `lineups/active.json`; a roster with `migration_problems` (its problems, a `takes_over` naming a person) or a `lineups/` without `active.json` migrates nothing; members' and the engineer's files are copied into `lineups.migrating/<main>/` with the work left after the commit in `migration.json`, the directory renamed as the commit, then the legacy copies deleted and former members archived from `lineups/migration.json`, which every later call finishes and removes. `takes_over` is read only there. **Backups** in roster mode carry `lineup` (whose live state) and `lineups` (the inactive ones' stored states), both skipped when empty; a backup whose live state is another lineup's (no `lineup` = main's) answers 409 `LINEUP_MISMATCH` on preview and restore; the preview names the lineups a restore replaces (`RestorePreview.lineups`), and the restore writes their states and their people's pins/hides into `lineups/<id>/customizations/`, a failure answering 500 `RESTORE_INCOMPLETE`. P6: roster problems name a value that is no valid id by field and position, parse errors drop every quoted or backticked span. Tests share `roster_state::tests::test_roster(active)` over `config/test-roster.toml`.
- **Roster reload and the band switch (#58; `roster_watch.rs`, `lineup_switch.rs`, `lineup_routes.rs`):** `roster.toml` is read at start and checked against the site's own `[engine]` table (`Config::engine`, `roster::engine_facts`; `iem-server roster check` reads the same plus `lineups/active.json` and `switch.json`); problems refuse the start unless `lineups/applied-roster.toml` (the roster the states follow, recorded at every settle and reload) can stand in: the server then starts with it (`roster_watch::Loaded::fallback`, `AppState::fallback`), the engineer's devices get one alarm (`fallback_alarm`), and every refused status names `roster.toml`'s problems and "in use instead: the roster applied last" until a roster file is in use again (so does a missing `roster.toml`). It is polled every 2 s (`roster_watch::poll`: (length, mtime), then SHA-256); `roster.status.json` says what became of each file (ids only); a running legacy server adopts its first roster (the migration runs live). **Every reload waits for a synced engine** (`Applied::Deferred`, read again at the next poll; nothing is read or written while it is not synced, nor while a switch a restart cut short is unfinished); only an engine refusal or the roster's own problems refuse it. A roster that comes into use without the engine (the start, an adoption) is `AppState::unsettled` until `roster_watch::settle` has put it in (the start runs it after the replay of an unfinished switch, an adoption spawns it; both are woken by the engine's state arriving, `EngineClient::wait_synced`): while it is `refusing` no page change, switch or restore runs; three refused tries free the pages with one alarm but keep the base, so the next roster change still moves people. **Every state says what it follows:** a lineup's stored state carries the SHA-256 of the roster it follows and its record of silenced sets in the same `state.json` (`MixerBackup::follows`, `silenced`), the running state both in `lineups/running.json` (`LineupStore::running`, written right after each import's answer, also by a switch, a replay and a restore). Before a transition's import `running.json` also gets `pending` (`Running::pending`: the roster followed once the import is in, its silenced sets, `roster_watch::state_digest` of the state sent; when it cannot be written nothing is imported and the transition answers `Deferred` (`NOT_RECORDED`): a settle counts that try as refused (`roster_watch::waits`), a reload that keeps meeting it alarms the engineer's devices once at `MAX_SETTLES` in a row (`AppState::unrecorded`, reset by a reload that applies); a failed import puts the record before back); every read resolves it against the engine's state (`roster_watch::running_of(store, held)`: taken when the engine holds the state sent) and saves the resolved record at once, and `transition` reads it first, right after it sees a synced engine (before the stored states, whose failure would otherwise leave it unresolved), so a start after an import whose answer was lost with the server moves nobody twice. Every roster that comes into use (load, fall-back, reload, adoption) is kept as `lineups/rosters.kept/<sha256>.toml` (`LineupStore::keep_roster`: written once, never rewritten or deleted by the server; the dot keeps the folder's name from being a lineup id, so no lineup and no walk over the lineups' folders takes it for a lineup). A reload and a settle share `transition`: a state's people move from the roster its marker names, looked up among the kept ones (`Follows::learn`; the roster before, the unsettled base, a backup's stored state on an older roster; a state without a marker follows the base, the roster applied last at a start, also after a switch a restart cut short; one on the new roster already, or on a roster not kept, moves nobody), so a transition cut short (a stop, a crash) never moves anyone twice; the rules hold on every set either roster lists, the roster before (or the unsettled base) and the new one, never on one only a roster learned from a marker lists: those only move people (a set the new one drops is silent). The stored states are worked out first; when the running state changes the pages are frozen (`AppState::freeze`) before any file is written, the running state read again and imported. The running state's import is sent as the engine will hold it: shaped by the topology with the engine's own `reconcile`, which lives in `iem_engine_proto::shape` for both (a moved mix keeps the slots of the set it came from; never copy it). An import whose answer is lost (no engine, no answer in time) is waited out, still frozen and nothing put back (`roster_watch::landed`: until the engine answers a `Ping`, then its state is compared with the one sent; an engine away `AppState::absent_alarm` (60 s, tests shorten it) is told to the engineer's devices once, and the wait goes on): taken, the transition goes on; not taken (or refused), the stored states go back. The pages stay frozen until the new roster is in use. The rules (`roster_watch::fit_recorded`): heard mixes muted on a set no leader wears; a set nobody wears muted and recorded, unmuted once worn again; a set its wearer muted is never recorded, so never unmuted. A switch's target and a backup restore's import take the rules too; a lineup without a stored state starts from the running state and its record. The engine keeps solos across an import: a switch, a replay, a fall-back, a reload and a settle end (`SetSolo` with no sources) the solo of each set whose wearer changes, still frozen (every solo when who wore the sets is not known; none for a state on the new roster already); a replay that only clears the intent ends those between the intent's two lineups. A reload, a settle, a switch, a restore and a backup capture never run beside each other: all take `AppState.switching` (a switch or restore `try_lock`s and answers busy, also while settling; a reload, a settle and a capture wait). The switch and the restore run on a task of their own (a dropped request never stops one half-way). `AppState::freeze` sets `frozen` under the change gate's write side, then sends a `Ping` barrier (`request_applied`: the mirror holds every change queued before); `AppState::apply` checks `may_change` and queues under its read side: never hold that std gate across an `.await`. Every unfreeze goes through `AppState::thaw`, which announces the band that plays (a person's page heard nothing of the engine while frozen), or, after a try that changed nothing for the pages (a failed freeze barrier, a transition that imported nothing), `AppState::thaw_unchanged`, which announces only when a person's page dropped an engine event while frozen (`mixer_ws::closing` marks it through `AppState::frozen_for_page`, under the change gate's read side; the thaw clears it under the write side), so a reload retried every 2 s does not close every person's socket every 2 s (#58 fifth review). A switch whose old state cannot go back in either answers 202 `SWITCH_PENDING`, keeps the intent and `frozen`, and `replay_when_synced` finishes it (pages and the engineer's devices told as for any switch); after `MAX_REPLAYS` tries the band before plays again (`fall_back`), after as many more the pages are freed with the engine's state and the intent cleared (`GAVE_UP`; `GAVE_UP_KEPT` says so when the clear failed and the next start tries again); the engineer's devices hear the outcome once it is known (`Replayed`). The retry interval of the replay, the settle and `landed` is `AppState::retry` (2 s; tests shorten it). Every page change goes through `AppState::may_change` (refused while `frozen` or settling, and from a page the active lineup no longer gives as it is): WS commands and pins/hides, the pins/hides PUT, Mute All, each ramp step; a new mix-changing path must call it too (through `AppState::apply` when it reaches the engine), and never while it holds `engine.mirror()` (`may_change` reads the mirror again: a second std `RwLock` read on one thread blocks behind a waiting writer, a deadlock). A person's page gets no engine `Changed`/`Reset` while frozen or once its band no longer plays (`mixer_ws::closing`), and the echo of a session's own solo is its viewer's (`own_echo_seen`). Who sees and moves heard mixes is `view::heard` (`Viewer::leads` reads `SiteView.leaders`, never a flag stored in the session, so it follows a switch at once); the preset ramp and `updates_for` use the page's own member (`Viewer::of_page`). A switch ends with `AppState::announce_lineup` (`lineup_tx`): every mixer page first hears `ServerMsg::LineupChanged` (the band in use, `mixer_ws::lineup_msg`, whatever the announcement carried), then people's mixer sockets close with `mixer_ws::CLOSE_LINEUP` (4003), and the engineer's page and a page without a person get their state and pins/hides again (`mixer_ws::on_lineup`). A stored `state.json`'s pins/hides are a copy for backups only: the lineup's `customizations/` files are what a page reads.
- **The page and the band (#58 Part C; UI `pages/mixer/helpers.rs` `LineupView`/`on_close`, `connection.rs`, `components/lineup_{notice,switch}.rs`):** `GET /api/lineup` answers 204 on a site without a roster, never a 4xx: a browser logs every 4xx answer in its console, on every page load (the switch still answers 404 `NOT_CONFIGURED`; the page also takes that 404 as no roster). `GET /api/lineup?page=<id>` (#61 review I2, `lineup_routes::page_plays`, pure) sets `playing` to whether that page plays now: a person's page while the person plays, a page the site has without a person (`/engineer`, the translator's) always, a page the site lacks 404; the bearer's own page answers as without `page`, another page only to the engineer, who alone may open it (#61 second review m1), anyone else 403; `leader` and `can_switch` stay the bearer's. The page always asks for itself (`api::lineup_url`, percent-encoded), so the engineer on a person's page gets the notice when that person does not play. The page reads it before its first socket and connects only while `LineupView::connects` (a memo, so a new band's name never reconnects; the reconnect tick leaves a page alone while it does not connect): a site without a roster connects as before; a person who does not play gets `LineupNotice` (`lineup-notice`, no status dot) and no socket, which the server would refuse and Chrome would log. A definitive refusal of the read is no failure to wait out (#61 second review m3, `api::LineupError` carries the status): 401 is `LineupView::SignedOut` (the token cleared, the login), 403 or 404 `LineupView::NoPage` (the notice page with `lineup_notice::NO_PAGE`, no socket, no read again, no reconnect). Any other read that fails or hangs (`api::get_lineup` aborts after `NETWORK_TIMEOUT_MS`, 5 s) keeps the view the page knew (`LineupView::apply`, #61 review C2: a notice stays the notice, a page reading again falls back to the band it knew, nothing known is `Unknown`, which connects as before); the tick reads the band again every `LINEUP_RECHECK_MS` (5 s, counted from the last read, `LineupReads::last_at`) while the notice shows or the band is being read or unknown. Every read is numbered (`LineupReads`, a `StoredValue` in `MixerState`): an answer older than one the view took is dropped (#61 review M3). In roster mode a failed close (1006, 4002: a switch missed while the socket was down) reads the band before the reconnect (`LineupView::reads_before_reconnect`, in the reconnect tick when a reconnect is due, so the backoff paces it; #61 review I1). `LineupChanged` puts the new name on the badge (`lineup-badge`) at once and reads the rest again; every roster-mode session opens with one (`mixer_ws::opening`, #61 second review m2), so the badge and the switch's offers follow the socket's band even when the read failed or a switch came between the read and the socket. An answer's writes go through `lineup_writes`: `connected = false` before a view that unmounts the mixer, and no write that changes nothing (#61 second review C1, `.claude/rules/leptos-view-macro.md`). A 4003 close (`OnClose::Lineup`) is never a failed socket (no backoff, no token check), never a reload, and leaves `connected` as it is (no "Reconnecting..."): `LineupView::reread` keeps the band on the badge and the settings' switch (`switch_here`), then the connect effect opens the socket or the notice shows. A switch answer of 202 `SWITCH_PENDING` is no failure (`lineup_switch::PENDING`); the line under the switch follows the band that plays (`SwitchState::follow`, #61 review M2). A `Callback` run after an `.await` panics once its owner is disposed: the switch calls `on_switched` only while its own state signal is still alive (`try_set` gave `None`).
