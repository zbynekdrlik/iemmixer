# Security baseline (program spec §5.3)

- **No compiled-in credentials.** No default PIN, no default JWT key. `jwt_secret` and `vapid_private` are generated on first run in `<config dir>/secrets/` (owner-only, created exclusively, never overwritten). The site config rejects secret and PIN keys (`deny_unknown_fields`; secret fields are `#[serde(skip)]`).
- **PINs** are argon2id PHC strings (m=19456 KiB, t=2, p=1) keyed with a 32-byte pepper (`Argon2::new_with_secret`). `pin_hashes.json` holds only `$argon2id$` values — anything else is a load error. The pepper is DPAPI-protected on Windows (`pepper.dpapi`). **On Linux it is the systemd credential `pepper`** (`pepper::CREDENTIAL`, #72 phase D) whenever systemd gives the process a credentials folder (`$CREDENTIALS_DIRECTORY`; the Gen 3 box: the server's unit `LoadCredentialEncrypted=pepper:…`, the PIN commands through `systemd-run`): exactly 32 bytes, never created or written by us; a missing one or one of another length is an error naming the credential and its folder, never its bytes (`the PIN pepper's systemd credential 'pepper' in <dir> cannot be read: <io error>`, `… holds <n> bytes, not 32`); a `pepper.test` beside it is an error too (`a plain test pepper lies beside the systemd credential: remove <path> and give every PIN again`: PINs set with it never verify), and so is a `dir` where that cannot be told; never a fall back to the file; one info line `PIN pepper from the systemd credential`. Without a credentials folder (CI, local runs) the pepper is a plain owner-only test file (`pepper.test`, with its warning). `pepper::load_from(dir, credentials)` decides (mutated); `load_or_create(dir)` only passes the variable (Windows passes none), so the server, `pin set-*` and the band import follow it (a band import's dry run hashes only when a `pepper.test` exists, `band_import::import_pins`). An unreadable pepper is an error, never regenerated (that would void every PIN); a missing pepper is created only while `pin_hashes.json` holds no hash — next to stored hashes it is an error too (recovery: restore the pepper, or move `pin_hashes.json` aside and re-provision with `iem-server pin set-engineer`). Backups never contain PINs.
- **Imported PINs (S4):** `pin_hashes.json` has an additive `imported` list of owners (member ids, `engineer`) whose hash came from the predecessor (`import_*_hash`, via `band_import::import_pins`); `set_member_hash` / `set_engineer_hash` drop the mark, and an import never replaces an unmarked hash — a later import never overwrites an iemmixer-set PIN (program spec §3.4). The predecessor's default PINs come only from a private file at migration time, never from code.
- **Tokens (`iem_core::jwt`, #74; no JWT crate: jsonwebtoken 11.1's p256/p384 0.13 held crypto-bigint 0.5, RUSTSEC-2026-0387, and its RSA backend RUSTSEC-2023-0071):** login tokens are HS256 over the secret's bytes (`encode_hs256`; the server's login and `iem-soakclient`), the VAPID JWT ES256 with the VAPID key (`encode_es256`, RFC 6979, `r || s`; feature `vapid`). The bytes are jsonwebtoken's (`{"typ":"JWT","alg":"HS256"}`, serde_json claims, base64url without padding), so tokens issued before stay valid. `decode_hs256` keeps jsonwebtoken's default validation: `alg` pinned to `HS256` before the signature is checked (`none`, every other algorithm refused), the HMAC compared by `hmac`'s `verify_slice` (constant time), a whole-second `exp` at most `LEEWAY_SECS` (60 s) past, `aud` refused; stricter only in refusing `crit` and a header or claims part that is no JSON object. Known answers pin it (`jwt::tests`: a Python-computed HS256 token, RFC 7515 A.1, an RFC 6979 ES256 signature checked with OpenSSL; `push::tests`: RFC 8291's example body). A new algorithm, claim check or leeway is a security change: never widen `decode_hs256`.
- **Start-up fails loud:** `start_server` builds its state with `AppState::try_new(…)?`, so a bad pepper or PIN store returns an error before any port is bound, and the tray exits when its server fails before it is ready. `AppState::new` (panicking) exists only for tests (`cfg(test)`).
- **Same-origin only:** no CORS layer (`app_router` in `lib.rs`, tested in `app_router_tests.rs`); the UI, the tray window and the E2E suite all load the UI from the server. Never add `CorsLayer::permissive()` back.
- **No raw REAPER passthrough** (X10): `/api/reaper/*` is gone (404); never add a generic proxy to an engine or REAPER control surface. The engine does no authorisation: the server decides who may change which mix (`view::command`) and only the engineer may touch another mix's EQ, input trim/mute/processing (F29) or the switch.
- **"Back to REAPER"** (`POST /api/mode/event`, §4.3): engineer token AND the engineer PIN through the login guard (`verify_engineer_pin`), then the site's `back_to_reaper` argv is spawned without a shell; 202 (`routes/api_tests.rs`). Its button is in the console of the engineer's settings (`components/back_to_reaper.rs`, shown when `ConsoleInfo.can_switch`; e2e `engineer.spec.ts`), no longer in a banner (#38). The talkback socket binds only with the held talk id (X6).
- **PIN freeze before the cutover (P9):** with `pin_changes = false` (every `dev` and trial site; the guard starts the server only with it before the cutover, and the cutover sets it `true`: `effects::web::pin_policy`, `.claude/rules/guard.md`) `POST /api/auth/change-pin` answers 409 `PIN_CHANGES_FROZEN` with `iem_core::PIN_CHANGES_FROZEN` for members and the engineer, before any PIN is checked (no hashing, no failure counted), and changes nothing; logins and the engineer-PIN check of the switch keep working. The predecessor stays the only place PINs change and every `dev` entry brings them over (`iem-migrate band`). Tests (`auth/login_tests.rs`): `auth::login_tests::{pin_change_is_refused_while_frozen, pin_reset_is_refused_while_frozen, login_still_works_while_frozen}`, E2E `pin-freeze.spec.ts`.
- **Provisioning:** first engineer PIN via `iem-server pin set-engineer` (PIN on stdin, server stopped); members get PINs by engineer reset in the UI (F3) or `iem-server pin set-member <id>`.
- **Login protection** (`login_guard.rs`, tests in `login_guard/tests.rs`; the handlers' in `auth/login_tests.rs`): admission before any hashing; failures only; separate LAN/tunnel origins; `CF-Connecting-IP` trusted only from a peer that is this host — loopback or one of the interface addresses `HostAddrs::read` lists at start (`LoginGuard::for_host`, `LoginGuard::client`): the tunnel connector runs on the PC, whether its origin targets 127.0.0.1 or the host's LAN address (S6 design §6; the shared ingress is never edited); a header from any other peer is ignored and a malformed one falls back to the peer; IPv6 clients keyed by their /64; admission does not reserve (in-flight attempts are bounded by the hashing gate); per (client, member): 3 free failures then 1, 2, 4 … s, forgotten after 15 quiet minutes; per client: 20 failures / 10 min → 60 s spacing; engineer budget per origin: > 30 failures / h → 5 s spacing for the whole origin (every failure may be an engineer-PIN guess); every delay ≤ 60 s, never a lockout; 429 + `Retry-After`; hashing gate 2 running + 8 queued, else 429; issued JWTs untouched. `LoginGuard::stats()` feeds the engineer console (F29). `GET /api/peer` (S7 HIL v2, `peer_route.rs`, public like `/api/version`) answers only how the guard's rule classified the request, `{"origin": "tunnel"|"lan", "peer": "loopback"|"host"|"other"}` (`LoginGuard::client`, `LoginGuard::is_host`), never an address (P6): a foreign peer with a forged `CF-Connecting-IP` reads `lan`/`other` (`peer_route::tests`).
- **Keep these tests:** limiter tables, forged header from a peer that is not the host (unit and route level), IPv6 keyed per /64, the intended LAN-origin spacing, in-flight attempts bounded by the gate, bounded memory, gate cancellation, plaintext store rejected, pepper never regenerated (also not when missing next to PIN hashes), the credential is the pepper and never falls back (missing, another length, a test pepper beside it, nothing written: `pepper::tests`), start-up refuses a bad or missing pepper, a short credential or a bad PIN store (`startup_tests::start_up_refuses_a_short_credential_before_any_port` runs its own test binary again with `--exact <its name>` and `CREDENTIALS_DIRECTORY` set, since the variable is the process's: never `set_var` in a test, which races every other test of the binary; the child prints a line the parent requires, because a filter that matches nothing exits 0), a foreign origin gets no CORS grant, the raw REAPER passthrough stays gone, the CLI never reads the PIN from argv.
- `pepper/dpapi.rs` is Windows-only: excluded from mutation testing and run by the `windows` CI job (`cargo test -p iem-server --lib pepper::`).
- **Removed people (#58; the owner's ruling of 2026-10-24 overruled decision 6's archive):** `people_removal::remove_person` deletes the PIN hash first (`PinStore::remove_member`, its import mark too; no login while the files go), then the photo and every lineup's files (an id that is no lower-case person id is refused before anything goes, #58 review; what a removal could not delete, the next start or reload deletes); nothing is kept, nothing restored, and a person added again gets a PIN only by the engineer's reset or `pin set-member`. The `archived` map an older server wrote into `pin_hashes.json` is read only to be deleted (`PinStore::drop_archived`, run by `roster_watch::follow_people`): its values are still checked as argon2id on load (a plaintext one is a load error), but they are no login, counted by no `has_hashes` (none of them is checked again, so a new pepper voids nothing) and never written back. A token outlives its person: every route keyed by the token's `sub` checks `auth::subject_known` (401 for a person the roster no longer holds; `page_for`, `ws_mixer`, photos, the PIN change, `/api/lineup`), and a new such route must too; in roster mode `auth::member_exists` is a roster person (playing or not) or the site's engineer.
